Adapter

También llamado: Adaptador, Envoltorio, Wrapper

🎯 Propósito

Adapter es un patrón de diseño estructural que permite que objetos con interfaces incompatibles colaboren entre sí mediante un objeto intermediario que traduce las llamadas y formatos de datos.

😟 Problema

Imagina que tu aplicación financiera procesa datos bursátiles en formato XML, o que tu tienda virtual cobra usando una interfaz uniforme ProcesadorPago en dólares. De pronto necesitas integrar una excelente biblioteca de análisis o pasarela de pagos de un tercero, pero esa biblioteca externa solo acepta datos en JSON o importes en centavos enteros con otra firma de método.

No puedes modificar la biblioteca externa (no tienes su código fuente o romperías a otros consumidores), y tampoco quieres ensuciar toda tu lógica de negocio con condicionales y conversiones acopladas al proveedor.

💡 Solución

Crear un Adaptador: una estructura especial que actúa como traductor tras bambalinas. El adaptador:

  1. Implementa la interfaz que el cliente ya conoce y espera.
  2. Envuelve internamente una referencia al objeto de servicio incompatible.
  3. Al recibir una llamada del cliente, transforma los argumentos al formato, unidades y orden que el servicio espera, delega la ejecución y traduce la respuesta si hace falta.
🔌

Analogía en el mundo real

Cuando viajas de América o Europa con tu cargador de portátil a otro continente, la clavija física no entra en el tomacorriente de la pared. No compras otro computador ni cambias el cableado del hotel: colocas un adaptador de enchufe en medio que recibe tus patas planas de un lado y expone clavijas redondas del otro.

                        └─────────────┬────────────┘

                        │ + MetodoEspecial(otro)   │
                        └──────────────────────────┘
  1. Cliente: contiene la lógica de negocio del programa y solo conoce la interfaz objetivo.
  2. Interfaz con el Cliente: protocolo que las estructuras deben cumplir para colaborar con el cliente.
  3. Adaptador: implementa la interfaz del cliente y envuelve al servicio, traduciendo llamadas y formatos.
  4. Servicio (Adaptee): biblioteca de terceros o código legado útil pero con una interfaz incompatible.

🧭 Aplicabilidad

  • Cuando quieres usar un paquete existente (legado o de terceros), pero su interfaz no coincide con el resto de tu diseño.
  • Cuando necesitas reutilizar varios tipos existentes que carecen de cierta funcionalidad común y no puedes modificar su código original.

🛠️ Cómo implementarlo

  1. Identifica el Servicio útil que no puedes cambiar y el Cliente que lo necesita.
  2. Declara la interfaz que el cliente espera consumir.
  3. Crea la estructura adaptadora que implemente dicha interfaz y guarde un campo con referencia al servicio.
  4. Implementa cada método de la interfaz traduciendo tipos/formatos y delegando al servicio.

Ventajas

  • Responsabilidad Única (SRP): separa el código de conversión de datos de la lógica de negocio.
  • Abierto/Cerrado (OCP): puedes añadir nuevos adaptadores para otros proveedores sin tocar el cliente.

Desventajas

  • Aumenta la complejidad general al introducir nuevas interfaces y estructuras envoltorio; si controlas el servicio, a veces es más simple cambiarlo directamente.

🔗 Relación con otros patrones

Adapter cambia la interfaz de un objeto existente para hacerla compatible; Decorator mantiene o amplía la misma interfaz añadiendo responsabilidades; Proxy conserva exactamente la misma interfaz controlando el acceso; Facade define una interfaz nueva y simple para todo un subsistema completo; y Bridge se diseña por anticipado para separar abstracción de implementación.

Adapter en Go

package main

import "fmt"

// 1. Interfaz con el Cliente: protocolo que el código cliente espera usar.
type ProcesadorPago interface {
	Cobrar(montoUSD float64) string
}

// Servicio compatible existente en nuestra aplicación.
type PasarelaLocal struct{}

func (p PasarelaLocal) Cobrar(montoUSD float64) string {
	return fmt.Sprintf("[PasarelaLocal] Cobro directo procesado: $%.2f USD", montoUSD)
}

// 2. Servicio (incompatible): SDK externo de un tercero que no podemos modificar.
// Usa otro nombre de método, recibe centavos enteros y exige código de moneda.
type SDKStripeExterno struct {
	APIKey string
}

func (s *SDKStripeExterno) CreateChargeInCents(cents int, currency string) string {
	return fmt.Sprintf("[Stripe SDK key=%s] Charge OK: %d cents (%s)", s.APIKey, cents, currency)
}

// 3. Adaptador: implementa ProcesadorPago y envuelve (compone) *SDKStripeExterno.
type AdaptadorStripe struct {
	servicio *SDKStripeExterno
	moneda   string
}

func NuevoAdaptadorStripe(sdk *SDKStripeExterno, moneda string) *AdaptadorStripe {
	return &AdaptadorStripe{servicio: sdk, moneda: moneda}
}

// Cobrar traduce la llamada del cliente al formato y firma que espera el SDK externo.
func (a *AdaptadorStripe) Cobrar(montoUSD float64) string {
	centavos := int(montoUSD * 100) // Conversión de formato: dólares (float64) -> centavos (int)
	respuestaSDK := a.servicio.CreateChargeInCents(centavos, a.moneda)
	return fmt.Sprintf("[Adaptador -> Stripe] %s", respuestaSDK)
}

// 4. Cliente: trabaja únicamente con la interfaz ProcesadorPago sin acoplarse al SDK.
func FinalizarCompra(carrito string, total float64, pasarela ProcesadorPago) {
	fmt.Printf("Cliente pagando %s ($%.2f):\n", carrito, total)
	fmt.Println("  ", pasarela.Cobrar(total))
}

func main() {
	// Uso con el servicio local que ya cumple la interfaz
	local := PasarelaLocal{}
	FinalizarCompra("Curso de Compiladores", 29.99, local)

	// Uso con el servicio incompatible a través del Adaptador
	sdkExterno := &SDKStripeExterno{APIKey: "sk_live_987"}
	adaptador := NuevoAdaptadorStripe(sdkExterno, "USD")
	FinalizarCompra("Suscripción Anual Pro", 149.50, adaptador)
}

🔍 Paso a paso

  1. FinalizarCompra (cliente) exige un ProcesadorPago con el método Cobrar(float64).
  2. SDKStripeExterno no cumple esa interfaz: expone CreateChargeInCents(int, string).
  3. AdaptadorStripe envuelve un puntero *SDKStripeExterno, convierte los dólares float64 a centavos int e invoca al SDK.

Salida real

Cliente pagando Curso de Compiladores ($29.99):
   [PasarelaLocal] Cobro directo procesado: $29.99 USD
Cliente pagando Suscripción Anual Pro ($149.50):
   [Adaptador -> Stripe] [Stripe SDK key=sk_live_987] Charge OK: 14950 cents (USD)
🐹

Nota idiomática de Go

Como las interfaces en Go se satisfacen implícitamente, el consumidor puede definir pequeñas interfaces en su propio paquete. Además, la biblioteca estándar usa tipos función como adaptadores: http.HandlerFunc(miFuncion) adapta una función ordinaria a la interfaz http.Handler.

Bridge

También llamado: Puente

🎯 Propósito

Bridge es un patrón de diseño estructural que permite dividir una clase grande, o un grupo de clases estrechamente relacionadas, en dos jerarquías separadas —abstracción e implementación— para que puedan evolucionar de manera independiente.

😟 Problema

Supón que tienes una jerarquía de figuras geométricas (Círculo, Cuadrado) y quieres agregarles colores (Rojo, Azul) mediante herencia. Terminas creando combinaciones como CírculoRojo, CírculoAzul, CuadradoRojo, CuadradoAzul.

Cuando extiendes un diseño en dos dimensiones ortogonales (por ejemplo: Forma × Color, o Control Remoto × Dispositivo, o GUI × Sistema Operativo), el número de tipos explota en progresión geométrica (N × M) y cualquier cambio obliga a tocar decenas de estructuras.

💡 Solución

Sustituir la combinación rígida por composición de objetos:

  1. Extraer una de las dimensiones a una jerarquía aparte llamada Implementación (p. ej. Color o Dispositivo).
  2. Mantener la capa de control de alto nivel como Abstracción (p. ej. Forma o ControlRemoto), que guarda un campo con referencia a la interfaz de implementación.
  3. Esa referencia actúa como el puente (bridge): ahora puedes añadir N abstracciones y M implementaciones creando solo N + M tipos en lugar de N × M.
📺

Analogía en el mundo real

Un control remoto universal (abstracción: básico, avanzado, con pantalla táctil) y los aparatos electrónicos (implementación: televisor, radio, proyector). No fabricas un "ControlAvanzadoExclusivoParaRadioSony": el control remoto define botones de alto nivel (subir volumen, silenciar) y se comunica mediante un protocolo común infrarrojo con cualquier dispositivo compatible.

│ ① Abstracción           │◇───────────────────▶│    <<interface>>        │
│ - impl: Implementacion  │                     │ ② Implementación        │
│ + OperacionAltoNivel()  │                     │ + PrimitivaA()          │
└────────────△────────────┘                     │ + PrimitivaB()          │
             │ embebe / extiende                └────────────△────────────┘
┌────────────┴────────────┐                                  │ implementa
│ ④ AbstracciónRefinada   │                     ┌────────────┴────────────┐
│ + OperacionExtra()      │                     │ ③ ImplConcreta (TV/Radio│
└─────────────────────────┘                     └─────────────────────────┘
             ▲
             │ usa
       ┌─────┴──────┐
       │ ⑤ Cliente  │
       └────────────┘
  1. Abstracción: ofrece lógica de control de alto nivel y delega el trabajo de bajo nivel al objeto de implementación.
  2. Implementación: interfaz común a todas las plataformas concretas con operaciones primitivas.
  3. Implementaciones Concretas: contienen el código específico de cada plataforma o motor subyacente.
  4. Abstracciones Refinadas: variantes de la lógica de control de alto nivel.
  5. Cliente: vincula la abstracción con una implementación y trabaja con la abstracción.

🧭 Aplicabilidad

  • Cuando quieres dividir y organizar una estructura monolítica que tiene múltiples variantes de una funcionalidad (p. ej. distintos motores de base de datos o backends de compilación).
  • Cuando necesitas extender un sistema en varias dimensiones ortogonales (independientes).
  • Cuando necesitas cambiar la implementación subyacente en tiempo de ejecución.

🛠️ Cómo implementarlo

  1. Identifica las dimensiones ortogonales (abstracción/plataforma, dominio/infraestructura, frontend/backend).
  2. Declara las operaciones primitivas en la interfaz Implementación y crea sus tipos concretos.
  3. Crea la Abstracción con un campo de tipo interfaz Implementación y delega en él.
  4. El cliente inyecta la implementación concreta al construir la abstracción.

Ventajas

  • Evita la explosión combinatoria de tipos (N + M en vez de N × M).
  • Cumple OCP y SRP: evolucionas la lógica de alto nivel y los detalles de plataforma por separado.

Desventajas

  • Puede complicar innecesariamente el código si se aplica a una clase muy cohesionada que solo varía en una dimensión.

🔗 Relación con otros patrones

Bridge se diseña desde el principio para separar jerarquías independientes, mientras que Adapter se aplica a posteriori para encajar tipos incompatibles. Su estructura de delegación se parece a Strategy, pero Bridge abarca dos jerarquías completas (estructural) mientras Strategy intercambia algoritmos puntuales (comportamiento). Puede combinarse con Abstract Factory para instanciar pares compatibles.

Bridge en Go

package main

import "fmt"

// 1. Implementación (interfaz de plataforma): operaciones primitivas de bajo nivel.
type Dispositivo interface {
	EstaEncendido() bool
	Encender()
	Apagar()
	Volumen() int
	FijarVolumen(porcentaje int)
	Nombre() string
}

// 2. Implementación Concreta A: Televisor.
type Televisor struct {
	encendido bool
	volumen   int
}

func (t *Televisor) EstaEncendido() bool     { return t.encendido }
func (t *Televisor) Encender()               { t.encendido = true; fmt.Println("  [TV] Encendido") }
func (t *Televisor) Apagar()                 { t.encendido = false; fmt.Println("  [TV] Apagado") }
func (t *Televisor) Volumen() int            { return t.volumen }
func (t *Televisor) FijarVolumen(v int)      { t.volumen = v; fmt.Printf("  [TV] Volumen = %d%%\n", t.volumen) }
func (t *Televisor) Nombre() string          { return "Smart TV 4K" }

// 2. Implementación Concreta B: Radio.
type Radio struct {
	encendido bool
	volumen   int
}

func (r *Radio) EstaEncendido() bool     { return r.encendido }
func (r *Radio) Encender()               { r.encendido = true; fmt.Println("  [Radio] Encendida") }
func (r *Radio) Apagar()                 { r.encendido = false; fmt.Println("  [Radio] Apagada") }
func (r *Radio) Volumen() int            { return r.volumen }
func (r *Radio) FijarVolumen(v int)      { r.volumen = v; fmt.Printf("  [Radio] Volumen = %d%%\n", r.volumen) }
func (r *Radio) Nombre() string          { return "Radio FM Vintage" }

// 3. Abstracción: control de alto nivel que contiene el "puente" (dispositivo).
type ControlRemoto struct {
	dispositivo Dispositivo
}

func NuevoControlRemoto(d Dispositivo) *ControlRemoto {
	return &ControlRemoto{dispositivo: d}
}

func (c *ControlRemoto) BotonEncendido() {
	fmt.Printf("Control -> alternando energía en %s\n", c.dispositivo.Nombre())
	if c.dispositivo.EstaEncendido() {
		c.dispositivo.Apagar()
	} else {
		c.dispositivo.Encender()
	}
}

func (c *ControlRemoto) SubirVolumen() {
	c.dispositivo.FijarVolumen(c.dispositivo.Volumen() + 15)
}

// 4. Abstracción Refinada: extiende la abstracción por composición (embedding).
type ControlAvanzado struct {
	*ControlRemoto
}

func NuevoControlAvanzado(d Dispositivo) *ControlAvanzado {
	return &ControlAvanzado{ControlRemoto: NuevoControlRemoto(d)}
}

func (ca *ControlAvanzado) Silenciar() {
	fmt.Printf("Control Avanzado -> silenciando %s\n", ca.dispositivo.Nombre())
	ca.dispositivo.FijarVolumen(0)
}

func main() {
	tv := &Televisor{volumen: 30}
	controlBasico := NuevoControlRemoto(tv)
	controlBasico.BotonEncendido()
	controlBasico.SubirVolumen()

	radio := &Radio{volumen: 50}
	controlPro := NuevoControlAvanzado(radio)
	controlPro.BotonEncendido()
	controlPro.SubirVolumen()
	controlPro.Silenciar()
}

🔍 Paso a paso

  1. Dispositivo define las operaciones primitivas que cumplen tanto Televisor como Radio.
  2. ControlRemoto guarda el campo dispositivo Dispositivo (el puente) y construye operaciones de alto nivel.
  3. ControlAvanzado embebe *ControlRemoto para reutilizar sus métodos y añade Silenciar().

Salida real

Control -> alternando energía en Smart TV 4K
  [TV] Encendido
  [TV] Volumen = 45%
Control -> alternando energía en Radio FM Vintage
  [Radio] Encendida
  [Radio] Volumen = 65%
Control Avanzado -> silenciando Radio FM Vintage
  [Radio] Volumen = 0%
🐹

Nota idiomática de Go

En Go no hay herencia de clases: las Abstracciones Refinadas se crean mediante struct embedding (*ControlRemoto dentro de ControlAvanzado), promoviendo automáticamente los métodos base mientras el campo interfaz Dispositivo actúa como puente.

Composite

También llamado: Objeto compuesto, Object Tree

🎯 Propósito

Composite es un patrón de diseño estructural que permite componer objetos en estructuras de árbol y trabajar con esas estructuras compuestas exactamente igual que si fueran objetos individuales.

😟 Problema

Imagina un sistema de pedidos con Productos y Cajas, o un sistema de archivos con Archivos y Carpetas, o un árbol sintáctico abstracto (AST) en un compilador. Una caja puede contener productos simples pero también cajas más pequeñas, que a su vez contienen más cajas.

Si el código cliente intenta calcular el precio o tamaño total distinguiendo manualmente tipos concretos y niveles de anidación con bucles y condicionales (if esCaja ...), el código se vuelve frágil y acoplado a la estructura interna del árbol.

💡 Solución

Definir una interfaz Componente común para los objetos simples (Hojas) y los contenedores complejos (Compuestos):

  • En una Hoja (producto o archivo), el método devuelve directamente su valor o realiza el trabajo base.
  • En un Contenedor (caja o carpeta), el método recorre recursivamente todos sus hijos (que son de tipo Componente), les delega la llamada y agrega los resultados.

Para el cliente no hay diferencia entre pedir el tamaño de un archivo suelto o de la carpeta raíz completa.

🪖

Analogía en el mundo real

Los ejércitos se organizan como un árbol jerárquico: un ejército contiene divisiones, las divisiones contienen brigadas, las brigadas pelotones, los pelotones escuadrones y los escuadrones soldados individuales (hojas). Cuando se da una orden en la cima, cada nivel la transmite recursivamente a sus subordinados hasta que cada soldado ejecuta la acción.

🧱 Estructural 2 / 3 · Estructura

Composite · Estructura y uso

┌────────────┐          ┌────────────────────────────┐
│ ④ Cliente  │─────────▶│     <<interface>>          │◀────────────┐
└────────────┘          │ ① Componente               │             │
                        │ + Ejecutar()               │             │
                        └──────△──────────────△──────┘             │
                               │              │                    │ contiene
                  ┌────────────┴───┐    ┌─────┴────────────────┐   │ 0..*
                  │ ② Hoja         │    │ ③ Contenedor         │◇──┘
                  │ + Ejecutar()   │    │ - hijos: []Componente│
                  └────────────────┘    │ + Agregar(c)         │
                                        │ + Ejecutar()         │
                                        └──────────────────────┘
  1. Componente: interfaz que declara las operaciones comunes tanto para nodos simples como para contenedores del árbol.
  2. Hoja (Leaf): elemento básico sin subelementos; realiza el trabajo real directamente.
  3. Contenedor (Composite): almacena un slice de Componente (hojas u otros contenedores) y delega las operaciones recursivamente a sus hijos.
  4. Cliente: manipula todos los elementos uniformemente a través de la interfaz Componente.

🧭 Aplicabilidad

  • Cuando el modelo central de tu dominio puede representarse como una estructura jerárquica en forma de árbol (AST de un compilador, DOM HTML, sistema de archivos, menús UI).
  • Cuando quieres que el código cliente trate objetos simples y composiciones complejas de forma transparente sin distinguir sus tipos concretos.

🛠️ Cómo implementarlo

  1. Verifica que tu dominio se divida naturalmente en hojas simples y contenedores recursivos.
  2. Declara la interfaz Componente con los métodos comunes.
  3. Implementa las estructuras Hoja con el comportamiento elemental.
  4. Implementa la estructura Contenedor con un slice []Componente, métodos para añadir hijos y delegación recursiva en cada operación.

Ventajas

  • Aprovecha el polimorfismo y la recursión para recorrer árboles complejos sin condicionales de tipo.
  • Abierto/Cerrado (OCP): puedes introducir nuevos tipos de hojas o contenedores sin romper el cliente.

Desventajas

  • Si las hojas y los contenedores difieren demasiado en comportamiento, diseñar una interfaz común limpia puede obligar a generalizar en exceso.

🔗 Relación con otros patrones

Composite y Decorator comparten composición recursiva, pero Decorator solo envuelve un único hijo y le agrega comportamiento, mientras Composite agrupa múltiples hijos y recapitula sus resultados. Suele combinarse con Iterator (recorrer el árbol), Visitor (operar sobre nodos de un AST), Builder (construir árboles) y Flyweight (compartir hojas repetidas).

Composite en Go

package main

import "fmt"

// 1. Componente (interfaz común para hojas simples y contenedores complejos).
type NodoSistema interface {
	Nombre() string
	TamanoKB() int
	Mostrar(indent string)
}

// 2. Hoja (Leaf): elemento básico del árbol que no tiene subelementos.
type Archivo struct {
	nombre   string
	tamanoKB int
}

func NuevoArchivo(nombre string, tamanoKB int) *Archivo {
	return &Archivo{nombre: nombre, tamanoKB: tamanoKB}
}

func (a *Archivo) Nombre() string   { return a.nombre }
func (a *Archivo) TamanoKB() int    { return a.tamanoKB }
func (a *Archivo) Mostrar(ind string) {
	fmt.Printf("%s📄 %s (%d KB)\n", ind, a.nombre, a.tamanoKB)
}

// 3. Contenedor / Compuesto (Composite): agrupa hojas u otros contenedores.
type Carpeta struct {
	nombre string
	hijos  []NodoSistema
}

func NuevaCarpeta(nombre string) *Carpeta {
	return &Carpeta{nombre: nombre}
}

func (c *Carpeta) Agregar(nodos ...NodoSistema) {
	c.hijos = append(c.hijos, nodos...)
}

func (c *Carpeta) Nombre() string { return c.nombre }

// TamanoKB delega recursivamente el cálculo a cada hijo del subárbol.
func (c *Carpeta) TamanoKB() int {
	total := 0
	for _, h := range c.hijos {
		total += h.TamanoKB()
	}
	return total
}

func (c *Carpeta) Mostrar(ind string) {
	fmt.Printf("%s📁 %s/ [total: %d KB]\n", ind, c.nombre, c.TamanoKB())
	for _, h := range c.hijos {
		h.Mostrar(ind + "   ")
	}
}

// 4. Cliente: trata igual a un archivo suelto que a todo un árbol de carpetas.
func ImprimirResumen(n NodoSistema) {
	fmt.Printf("Resumen de '%s' -> %d KB\n", n.Nombre(), n.TamanoKB())
}

func main() {
	src := NuevaCarpeta("src")
	src.Agregar(
		NuevoArchivo("lexer.go", 18),
		NuevoArchivo("parser.go", 42),
	)

	raiz := NuevaCarpeta("compilador")
	raiz.Agregar(
		NuevoArchivo("go.mod", 2),
		NuevoArchivo("README.md", 8),
		src,
	)

	raiz.Mostrar("")
	fmt.Println("---")
	ImprimirResumen(NuevoArchivo("lexer.go", 18)) // Hoja individual
	ImprimirResumen(raiz)                         // Árbol compuesto completo
}

🔍 Paso a paso

  1. NodoSistema declara la interfaz común con Nombre(), TamanoKB() y Mostrar().
  2. Archivo (Hoja) devuelve su tamaño directo.
  3. Carpeta (Compuesto) guarda hijos []NodoSistema y suma recursivamente h.TamanoKB().
  4. ImprimirResumen recibe tanto un *Archivo como la *Carpeta raíz sin cambiar una línea.

Salida real

📁 compilador/ [total: 70 KB]
   📄 go.mod (2 KB)
   📄 README.md (8 KB)
   📁 src/ [total: 60 KB]
      📄 lexer.go (18 KB)
      📄 parser.go (42 KB)
---

Decorator

También llamado: Decorador, Envoltorio, Wrapper

🎯 Propósito

Decorator es un patrón de diseño estructural que permite añadir funcionalidades a objetos dinámicamente colocándolos dentro de objetos envoltorio (wrappers) especiales que implementan la misma interfaz.

😟 Problema

Imagina una biblioteca de notificaciones que empieza enviando solo correos electrónicos (Notificador). Luego los usuarios piden SMS, Slack, Telegram, cifrado y formato urgente. Si intentas crear una subclase para cada combinación posible (NotificadorEmailConSMSYSlack, NotificadorEmailConSMS, etc.), sufres una explosión combinatoria.

Además, la herencia es estática: no permite apilar, quitar o decidir qué canales combinar en tiempo de ejecución según la configuración del usuario.

💡 Solución

Usar composición recursiva mediante envoltorios (wrappers):

  1. Tanto el componente base como cada decorador implementan la misma interfaz (p. ej. Notificador).
  2. Cada decorador guarda un campo envuelto de ese tipo interfaz.
  3. Al recibir una llamada, el decorador ejecuta su lógica extra (antes o después) y delega la llamada al objeto envuelto. Así puedes apilar tantas capas como quieras como una muñeca rusa.
🧥

Analogía en el mundo real

Vestirse por capas cuando hace frío: tú eres el componente base; primero te pones un suéter, encima una chaqueta térmica y, si llueve, un impermeable encima. Cada prenda te "envuelve" y extiende tu protección sin modificar tu cuerpo, y puedes combinarlas o quitártelas dinámicamente en cualquier momento.

Decorator · Estructura y uso

┌────────────┐          ┌────────────────────────────┐
│ ⑤ Cliente  │─────────▶│     <<interface>>          │◀────────────┐
└────────────┘          │ ① Componente               │             │
                        │ + Enviar(msg)              │             │
                        └──────△──────────────△──────┘             │
                               │              │                    │ envuelve
                  ┌────────────┴───┐    ┌─────┴────────────────┐   │ (1)
                  │ ② CompConcreto │    │ ③ DecoradorBase      │◇──┘
                  │ (Email)        │    │ - envuelto:Componente│
                  └────────────────┘    └──────────△───────────┘
                                                   │
                                        ┌──────────┴───────────┐
                                        │ ④ DecoradoresConcr.  │
                                        │ (SMS, Slack, Urgente)│
                                        └──────────────────────┘
  1. Componente: interfaz común tanto para el objeto envuelto como para todos los decoradores.
  2. Componente Concreto: define el comportamiento básico que será envuelto y extendido.
  3. Decorador Base: referencia un Componente envuelto y le delega las operaciones.
  4. Decoradores Concretos: añaden responsabilidades antes y/o después de delegar al objeto envuelto.
  5. Cliente: ensambla la pila de decoradores y la usa mediante la interfaz común.

🧭 Aplicabilidad

  • Cuando necesitas asignar responsabilidades adicionales a objetos en tiempo de ejecución sin afectar al código cliente que los utiliza.
  • Cuando quieres combinar comportamientos ortogonales (logging, métricas, compresión, cifrado, reintentos) mediante capas apilables.

🛠️ Cómo implementarlo

  1. Declara la interfaz Componente con los métodos compartidos por el objeto base y las capas opcionales.
  2. Crea el Componente Concreto con la funcionalidad base.
  3. Crea cada Decorador implementando la misma interfaz y guardando un campo envuelto Componente.
  4. En el método del decorador, agrega el comportamiento extra antes o después de llamar a d.envuelto.Metodo().

Ventajas

  • Extiende y combina comportamientos en tiempo de ejecución sin crear subclases.
  • Cumple SRP: cada preocupación transversal (SMS, Slack, formato) vive en su propio tipo pequeño.

Desventajas

  • Es difícil eliminar un wrapper intermedio específico una vez armada la pila.
  • El resultado puede depender del orden exacto en que se apilan los decoradores.

🔗 Relación con otros patrones

Decorator mantiene la misma interfaz y permite apilar capas recursivamente; Adapter cambia la interfaz. Se parece a Chain of Responsibility, pero en Decorator todas las capas se ejecutan sin cortar el flujo. Mientras Decorator cambia la "piel" externa del objeto, Strategy cambia sus "entrañas". A diferencia de Proxy, en Decorator el cliente controla explícitamente qué capas apilar.

Decorator en Go

package main

import (
	"fmt"
	"strings"
)

// 1. Componente: interfaz común para el objeto envuelto y para todos los decoradores.
type Notificador interface {
	Enviar(mensaje string) string
}

// 2. Componente Concreto: define el comportamiento base (enviar por correo).
type NotificadorEmail struct {
	Destinatario string
}

func (n NotificadorEmail) Enviar(mensaje string) string {
	return fmt.Sprintf("📧 Email a <%s>: %q", n.Destinatario, mensaje)
}

// 3. Decorador Concreto A: envuelve un Notificador y añade envío por SMS.
type DecoradorSMS struct {
	envuelto Notificador
	telefono string
}

func ConSMS(n Notificador, telefono string) Notificador {
	return DecoradorSMS{envuelto: n, telefono: telefono}
}

func (d DecoradorSMS) Enviar(mensaje string) string {
	previo := d.envuelto.Enviar(mensaje)
	return fmt.Sprintf("%s\n📱 SMS a [%s]: %q", previo, d.telefono, mensaje)
}

// 4. Decorador Concreto B: añade notificación a un canal de Slack.
type DecoradorSlack struct {
	envuelto Notificador
	canal    string
}

func ConSlack(n Notificador, canal string) Notificador {
	return DecoradorSlack{envuelto: n, canal: canal}
}

func (d DecoradorSlack) Enviar(mensaje string) string {
	previo := d.envuelto.Enviar(mensaje)
	return fmt.Sprintf("%s\n💬 Slack [%s]: %q", previo, d.canal, mensaje)
}

// 5. Decorador Concreto C: transforma el mensaje antes de delegarlo a la pila.
type DecoradorUrgente struct {
	envuelto Notificador
}

func ConFormatoUrgente(n Notificador) Notificador {
	return DecoradorUrgente{envuelto: n}
}

func (d DecoradorUrgente) Enviar(mensaje string) string {
	transformado := "[URGENTE] " + strings.ToUpper(mensaje)
	return d.envuelto.Enviar(transformado)
}

func main() {
	// Pila de decoradores: Urgente -> Slack -> SMS -> Email base
	var alerta Notificador = NotificadorEmail{Destinatario: "ops@empresa.co"}
	alerta = ConSMS(alerta, "+57-300-1234567")
	alerta = ConSlack(alerta, "#incidentes-prod")
	alerta = ConFormatoUrgente(alerta)

	fmt.Println(alerta.Enviar("uso de CPU al 98% en nodo principal"))
}

🔍 Paso a paso

  1. NotificadorEmail es la base de la pila.
  2. ConSMS y ConSlack envuelven cualquier Notificador y agregan su propio envío después de delegar.
  3. ConFormatoUrgente actúa antes de delegar: convierte el texto a mayúsculas y lo pasa a toda la pila interior.

Salida real

📧 Email a <ops@empresa.co>: "[URGENTE] USO DE CPU AL 98% EN NODO PRINCIPAL"
📱 SMS a [+57-300-1234567]: "[URGENTE] USO DE CPU AL 98% EN NODO PRINCIPAL"
💬 Slack [#incidentes-prod]: "[URGENTE] USO DE CPU AL 98% EN NODO PRINCIPAL"

Nota idiomática de Go

En Go no hace falta una "clase Decoradora Base" abstracta: cada decorador compone directamente la interfaz. La biblioteca estándar de Go está llena de Decorators: bufio.NewReader(r) y gzip.NewWriter(w) decoran io.Reader/io.Writer, y los middlewares HTTP func(http.Handler) http.Handler son decoradores puros.

Facade

También llamado: Fachada

🎯 Propósito

Facade es un patrón de diseño estructural que proporciona una interfaz simplificada y de alto nivel a una biblioteca, un framework o cualquier subsistema complejo compuesto por múltiples objetos.

😟 Problema

Imagina que tu aplicación necesita realizar una operación como procesar un pedido en línea o convertir un video o compilar código fuente. Para lograrlo debe interactuar con decenas de objetos de un subsistema: inicializarlos, controlar sus dependencias y llamar a sus métodos en un orden estricto.

Si cada cliente hace esa orquestación por su cuenta, tu lógica de negocio queda fuertemente acoplada a los detalles internos del subsistema y cualquier cambio se propaga por todo el proyecto.

💡 Solución

Crear una estructura Fachada (Facade) que ofrezca unos pocos métodos directos con exactamente lo que la mayoría de los clientes necesitan (por ejemplo, ComprarConUnClic() o ConvertirVideo()).

La fachada conoce a qué piezas internas del subsistema dirigirse y en qué orden coordinarlas, aislando al cliente de la complejidad interna sin impedir que un usuario avanzado acceda al subsistema directamente si lo requiere.

☎️

Analogía en el mundo real

Cuando haces un pedido telefónico a una tienda, el operador de atención al cliente es tu fachada. No hablas por separado con la bodega de inventario, la pasarela antifraude del banco, el departamento de facturación y la empresa de mensajería: hablas un minuto con el operador y él coordina todos los departamentos internos por ti.

Facade · Estructura y uso

┌────────────┐          ┌──────────────────────────┐
│ ④ Cliente  │─────────▶│ ① Fachada (Facade)       │
└────────────┘          │ + OperacionSimple()      │
                        └──┬──────┬──────┬──────┬──┘
                           │      │      │      │
             ┌─────────────┘      │      │      └─────────────┐
             ▼                    ▼      ▼                    ▼
    ┌─────────────────┐  ┌────────────┐ ┌────────────┐ ┌─────────────┐
    │ ③ Subsistema A  │  │ ③ Subsis B │ │ ③ Subsis C │ │ ② Fachada   │
    │ (Inventario)    │  │ (Fraude)   │ │ (Cobros)   │ │   Adicional │
    └─────────────────┘  └────────────┘ └────────────┘ └─────────────┘
  1. Fachada (Facade): ofrece un acceso sencillo a una parte específica de la funcionalidad del subsistema y coordina el orden de llamadas.
  2. Fachada Adicional (opcional): evita que una única fachada crezca demasiado mezclando responsabilidades no relacionadas.
  3. Subsistema Complejo: conjunto de tipos especializados que hacen el trabajo real sin conocer la existencia de la fachada.
  4. Cliente: invoca únicamente a la fachada en vez de manejar los objetos internos del subsistema.

🧭 Aplicabilidad

  • Cuando necesitas una interfaz simple y directa hacia un subsistema complejo o una biblioteca de terceros con decenas de tipos.
  • Cuando quieres estructurar un sistema en capas (por ejemplo, fases de un compilador o módulos de negocio) definiendo una fachada como punto de entrada de cada capa.

🛠️ Cómo implementarlo

  1. Identifica qué operaciones de alto nivel necesita realmente el cliente frente al subsistema existente.
  2. Crea la estructura fachada que agrupe las referencias a los componentes del subsistema e inicialice su ciclo de vida.
  3. Haz que el código cliente se comunique con el subsistema solo a través de la fachada; si esta crece demasiado, divídela en fachadas más pequeñas.

Ventajas

  • Aísla y desacopla el código cliente de la complejidad interna de un subsistema de múltiples piezas.
  • Facilita actualizar o reemplazar el subsistema interno modificando únicamente la fachada.

Desventajas

  • Riesgo de que la fachada se convierta en un objeto todopoderoso (God Object) acoplado a todas las estructuras de la aplicación.

🔗 Relación con otros patrones

Facade define una interfaz nueva y simple para todo un subsistema de objetos, mientras que Adapter reutiliza una interfaz existente envolviendo por lo general un solo objeto. A diferencia de Mediator, en Facade los objetos del subsistema no conocen a la fachada. Abstract Factory puede usarse junto a Facade para ocultar cómo se instancian las piezas del subsistema.

Facade en Go

package main

import "fmt"

// --- Subsistema Complejo: múltiples tipos con orden de inicialización estricto ---

type ServicioInventario struct{}

func (ServicioInventario) VerificarStock(sku string) bool {
	fmt.Printf("  1. [Inventario] Verificando disponibilidad de %s -> OK\n", sku)
	return true
}

type PasarelaFraude struct{}

func (PasarelaFraude) EvaluarRiesgo(cliente string, monto float64) bool {
	fmt.Printf("  2. [Antifraude] Analizando operación de %s por $%.2f -> APROBADO\n", cliente, monto)
	return true
}

type MotorCobros struct{}

func (MotorCobros) Debitar(cliente string, monto float64) string {
	fmt.Printf("  3. [Cobros] Debitando $%.2f a %s -> TX-9081\n", monto, cliente)
	return "TX-9081"
}

type ServicioLogistica struct{}

func (ServicioLogistica) Despachar(sku, cliente string) string {
	fmt.Printf("  4. [Logística] Generando guía de envío para %s (%s) -> GUIA-441\n", sku, cliente)
	return "GUIA-441"
}

// --- Fachada (Facade): interfaz simplificada de alto nivel para el cliente ---

type FachadaCompra struct {
	inventario ServicioInventario
	antifraude PasarelaFraude
	cobros     MotorCobros
	logistica  ServicioLogistica
}

func NuevaFachadaCompra() *FachadaCompra {
	return &FachadaCompra{}
}

// ComprarConUnClic coordina todo el subsistema en el orden correcto.
func (f *FachadaCompra) ComprarConUnClic(cliente, sku string, precio float64) string {
	fmt.Printf("Iniciando compra rápida: %s adquiere %s\n", cliente, sku)
	if !f.inventario.VerificarStock(sku) || !f.antifraude.EvaluarRiesgo(cliente, precio) {
		return "Compra rechazada"
	}
	tx := f.cobros.Debitar(cliente, precio)
	guia := f.logistica.Despachar(sku, cliente)
	return fmt.Sprintf("Pedido completado (Transacción: %s, Guía: %s)", tx, guia)
}

func main() {
	// El cliente solo conoce la Fachada; ignora los 4 subsistemas internos.
	tienda := NuevaFachadaCompra()
	resultado := tienda.ComprarConUnClic("Ana Gómez", "LAPTOP-PRO-16", 1299.00)
	fmt.Println("Resultado:", resultado)
}

🔍 Paso a paso

  1. El subsistema consta de 4 servicios independientes (ServicioInventario, PasarelaFraude, MotorCobros, ServicioLogistica).
  2. FachadaCompra encapsula las 4 piezas y expone un único método de negocio: ComprarConUnClic.
  3. main() realiza la operación completa con una sola llamada sin acoplarse al orden interno del flujo.

Salida real

Iniciando compra rápida: Ana Gómez adquiere LAPTOP-PRO-16
  1. [Inventario] Verificando disponibilidad de LAPTOP-PRO-16 -> OK
  2. [Antifraude] Analizando operación de Ana Gómez por $1299.00 -> APROBADO
  3. [Cobros] Debitando $1299.00 a Ana Gómez -> TX-9081
  4. [Logística] Generando guía de envío para LAPTOP-PRO-16 (Ana Gómez) -> GUIA-441
Resultado: Pedido completado (Transacción: TX-9081, Guía: GUIA-441)

Flyweight

También llamado: Peso mosca, Peso ligero, Cache

🎯 Propósito

Flyweight es un patrón de diseño estructural que permite mantener una enorme cantidad de objetos dentro de la memoria RAM disponible compartiendo las partes comunes del estado entre múltiples objetos en lugar de duplicar toda la información en cada uno.

😟 Problema

Imagina un videojuego que renderiza cientos de miles de partículas (balas, misiles, metralla) o un bosque con un millón de árboles. Si cada objeto Árbol o Partícula guarda su propia copia de la textura 4K, el modelo 3D y el color además de sus coordenadas (x, y), la memoria RAM se agota en segundos y el programa colapsa.

Al inspeccionar los objetos, notas que casi todos repiten exactamente las mismas texturas y colores pesados.

💡 Solución

Separar el estado de cada objeto en dos mitades:

  • Estado intrínseco (Flyweight): datos constantes, pesados y repetidos (especie, color, textura/sprite). Se almacenan en un único objeto inmutable compartido por miles de instancias.
  • Estado extrínseco (Contexto): datos livianos y únicos de cada instancia (coordenadas x, y, velocidad). Se guardan afuera y se pasan por parámetro a los métodos del Flyweight cuando se necesitan.
🌲

Analogía en el mundo real

En un procesador de textos o libro impreso con 500 000 letras, el programa no guarda 500 000 mapas de bits vectoriales de la fuente tipográfica. Guarda una sola definición geométrica inmutable de la letra 'A' (estado intrínseco / flyweight) y en el documento solo anota en qué fila y columna dibujarla (estado extrínseco).

┌──────────────────────┐       ┌──────────────────────────┐
│ ④ Cliente (Bosque)   │──────▶│ ③ FabricaFlyweight       │
└──────────┬───────────┘       │ - pool: map[clave]*Flyw. │
           │ contiene miles    │ + Obtener(estadoIntrins.)│
           ▼                   └─────────────┬────────────┘
┌──────────────────────┐                     │ reutiliza / crea
│ ② Contexto (Arbol)   │                     ▼
│ - x, y (extrínseco)  │       ┌──────────────────────────┐
│ - tipo: *Flyweight   │──────▶│ ① Flyweight (TipoArbol)  │
│ + Dibujar()          │ N a 1 │ - especie, color, textura│
└──────────────────────┘       │   (intrínseco inmutable) │
                               │ + Dibujar(x, y)          │
                               └──────────────────────────┘
  1. Flyweight: almacena solo el estado intrínseco compartido (debe ser inmutable). Recibe el estado extrínseco por parámetro en sus métodos.
  2. Contexto: contiene el estado extrínseco único de cada objeto liviano más un puntero al Flyweight compartido.
  3. Fábrica Flyweight: administra un pool/caché de flyweights existentes; devuelve uno ya creado o lo instancia si aún no existe.
  4. Cliente: calcula o almacena el estado extrínseco y solicita los flyweights a la fábrica.

🧭 Aplicabilidad

  • Úsalo únicamente cuando tu programa deba instanciar una cantidad masiva de objetos similares que agoten la RAM disponible, y gran parte de sus campos contengan datos duplicados que puedan extraerse y compartirse.
  • Muy común en motores gráficos, videojuegos y tablas de internado de cadenas (string interning) en compiladores.

🛠️ Cómo implementarlo

  1. Divide los campos del objeto en estado intrínseco (inmutable, compartido) y extrínseco (único por instancia).
  2. Deja solo el estado intrínseco en el tipo Flyweight e inicialízalo una sola vez.
  3. Pasa el estado extrínseco como argumentos a los métodos del Flyweight y guárdalo en una estructura Contexto.
  4. Crea una Fábrica Flyweight con un mapa en caché para reutilizar instancias.

Ventajas

  • Ahorra enormes cantidades de memoria RAM cuando existen miles o millones de objetos similares.

Desventajas

  • Puede intercambiar ahorro de RAM por ciclos de CPU si el estado extrínseco debe recalcularse en cada llamada.
  • Aumenta la complejidad del código al separar el estado de una entidad en dos estructuras.

🔗 Relación con otros patrones

Las hojas repetidas de un árbol Composite suelen implementarse como Flyweights para ahorrar memoria. Mientras Flyweight muestra cómo tener muchos objetos pequeños compartidos, Facade muestra cómo un solo objeto representa todo un subsistema. A diferencia de Singleton, una clase Flyweight tiene múltiples instancias (una por cada estado intrínseco distinto) y sus objetos deben ser inmutables.

Flyweight en Go

package main

import "fmt"

// 1. Flyweight (Estado Intrínseco): inmutable y compartido entre miles de instancias.
type TipoArbol struct {
	especie string
	color   string
	textura string // Simula un recurso pesado en RAM (malla 3D / textura HD)
}

func (t *TipoArbol) Dibujar(x, y int) {
	fmt.Printf("  🌳 [%s | %s | %s] en (%d, %d) (ptr=%p)\n",
		t.especie, t.color, t.textura, x, y, t)
}

// 2. Fábrica Flyweight: gestiona el pool/caché de objetos compartidos.
type FabricaTiposArbol struct {
	tipos map[string]*TipoArbol
}

func NuevaFabricaTipos() *FabricaTiposArbol {
	return &FabricaTiposArbol{tipos: make(map[string]*TipoArbol)}
}

func (f *FabricaTiposArbol) ObtenerTipo(especie, color, textura string) *TipoArbol {
	clave := especie + "_" + color
	if tipo, existe := f.tipos[clave]; existe {
		return tipo // Reutiliza el flyweight existente en memoria
	}
	fmt.Printf("➕ Creando nuevo Flyweight en RAM para: %s (%s)\n", especie, color)
	nuevo := &TipoArbol{especie: especie, color: color, textura: textura}
	f.tipos[clave] = nuevo
	return nuevo
}

// 3. Contexto (Estado Extrínseco): liviano, único para cada árbol del mapa.
type Arbol struct {
	x, y int
	tipo *TipoArbol // Referencia al flyweight compartido
}

// 4. Cliente / Contenedor: almacena los contextos livianos.
type Bosque struct {
	arboles []Arbol
	fabrica *FabricaTiposArbol
}

func (b *Bosque) Plantar(x, y int, especie, color, textura string) {
	tipoCompartido := b.fabrica.ObtenerTipo(especie, color, textura)
	b.arboles = append(b.arboles, Arbol{x: x, y: y, tipo: tipoCompartido})
}

func main() {
	bosque := &Bosque{fabrica: NuevaFabricaTipos()}

	bosque.Plantar(10, 20, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(15, 25, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(50, 80, "Cerezo", "Rosa", "textura_cerezo_4k.png")
	bosque.Plantar(12, 30, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(55, 85, "Cerezo", "Rosa", "textura_cerezo_4k.png")

	fmt.Printf("\nRenderizando %d árboles usando solo %d objetos TipoArbol en RAM:\n",
		len(bosque.arboles), len(bosque.fabrica.tipos))
	for _, a := range bosque.arboles {
		a.tipo.Dibujar(a.x, a.y)
	}
}

🔍 Paso a paso

  1. TipoArbol tiene campos privados (no exportados) para garantizar su inmutabilidad.

Proxy

También llamado: Representante, Sustituto, Surrogate

🎯 Propósito

Proxy es un patrón de diseño estructural que proporciona un sustituto o marcador de posición para otro objeto. Un proxy controla el acceso al objeto original, permitiéndote ejecutar lógica (seguridad, caché, carga diferida, auditoría) antes o después de que la solicitud llegue al servicio real.

😟 Problema

Imagina que tienes un objeto de servicio masivo que consume muchos recursos (una conexión a base de datos, un cliente de almacenamiento remoto S3 o un descargador de video). Lo necesitas ocasionalmente, pero no quieres inicializarlo al arrancar si nadie lo usa, ni repetir consultas idénticas por red, ni permitir que usuarios sin permisos lo invoquen.

Si incrustas esa lógica de inicialización diferida, caché y permisos en cada cliente, duplicarás código por toda la aplicación.

💡 Solución

Crear una estructura Proxy que implemente exactamente la misma interfaz que el servicio original:

  • El proxy se camufla ante los clientes como si fuera el servicio real.
  • Intercepta cada petición: verifica permisos, consulta su caché o crea el objeto pesado solo en el instante en que realmente se necesita (lazy initialization), y luego le delega el trabajo.
💳

Analogía en el mundo real

Una tarjeta de crédito o débito es un proxy de una cuenta bancaria, que a su vez es un proxy de un fajo de billetes en efectivo. Ambos implementan la misma interfaz ("realizar un pago"), pero la tarjeta controla el acceso (verifica tu PIN y cupo disponible) antes de descontar el dinero real del banco.

Proxy · Estructura y uso

┌────────────┐          ┌────────────────────────────┐
│ ④ Cliente  │─────────▶│     <<interface>>          │
└────────────┘          │ ① InterfazServicio         │
                        │ + Operacion(id)            │
                        └──────△──────────────△──────┘
                               │              │
                     implementa│              │implementa
                  ┌────────────┴───┐    ┌─────┴────────────────┐
                  │ ③ Proxy        │───▶│ ② ServicioReal       │
                  │ - real:*Serv.  │    │ + Operacion(id)      │
                  │ + Operacion(id)│    └──────────────────────┘
                  └────────────────┘      (delega tras validar)
  1. Interfaz de Servicio: declara el contrato común que el Proxy debe seguir para camuflarse como el servicio real.
  2. Servicio Real: estructura que contiene la lógica de negocio pesada o sensible.
  3. Proxy: mantiene una referencia al servicio real, gestiona su ciclo de vida y controla el acceso antes/después de delegar.
  4. Cliente: trabaja tanto con el Servicio Real como con el Proxy de forma transparente a través de la interfaz.

🧭 Aplicabilidad (tipos de Proxy)

  • Proxy virtual (inicialización diferida): retrasa la creación de un objeto muy costoso hasta que se usa por primera vez.
  • Proxy de protección (control de acceso): valida credenciales o roles antes de pasar la solicitud.
  • Proxy de caché: almacena en memoria resultados de operaciones remotas o lentas recurrentes.
  • Proxy de registro / remoto: audita llamadas o encapsula comunicación por red (gRPC/HTTP).

🛠️ Cómo implementarlo

  1. Asegúrate de tener una Interfaz de Servicio para que el proxy y el servicio real sean intercambiables.
  2. Crea la estructura Proxy con un campo que apunte al servicio real (a menudo creado por el propio proxy).
  3. Implementa los métodos de la interfaz ejecutando validaciones, caché o lazy init antes de delegar al servicio.

Ventajas

  • Controla el acceso y el ciclo de vida del objeto de servicio sin que el cliente lo note.
  • Abierto/Cerrado (OCP): puedes introducir nuevos proxies sin modificar el servicio ni los clientes.

Desventajas

  • La respuesta del servicio puede experimentar cierta latencia adicional por las validaciones o inicialización diferida.

🔗 Relación con otros patrones

Proxy mantiene exactamente la misma interfaz que su servicio; Adapter la cambia y Decorator la amplía por capas. Aunque Proxy y Decorator se construyen por composición, un Proxy suele gestionar por su cuenta el ciclo de vida del servicio real (creándolo en diferido), mientras que en Decorator el cliente inyecta y apila explícitamente los objetos.

Proxy en Go

package main

import "fmt"

// 1. Interfaz de Servicio: implementada tanto por el Servicio Real como por el Proxy.
type RepositorioDocumentos interface {
	ObtenerDocumento(id string, rolUsuario string) string
}

// 2. Servicio Real: operación costosa (consulta a BD o descarga remota).
type AlmacenRemotoS3 struct{}

func (a *AlmacenRemotoS3) ObtenerDocumento(id string, _ string) string {
	fmt.Printf("  🌐 [AlmacenRemotoS3] Descargando '%s' desde el servidor remoto...\n", id)
	return fmt.Sprintf("Contenido confidencial del archivo [%s]", id)
}

// 3. Proxy: controla acceso (protección), guarda en caché e inicializa en diferido (virtual).
type ProxyRepositorio struct {
	servicioReal *AlmacenRemotoS3 // Se crea solo cuando realmente hace falta (lazy init)
	cache        map[string]string
}

func NuevoProxyRepositorio() *ProxyRepositorio {
	return &ProxyRepositorio{cache: make(map[string]string)}
}

func (p *ProxyRepositorio) ObtenerDocumento(id string, rolUsuario string) string {
	fmt.Printf("-> Solicitud de '%s' por rol '%s'\n", id, rolUsuario)

	// a) Proxy de protección: control de acceso
	if rolUsuario != "admin" && rolUsuario != "editor" {
		return "⛔ ACCESO DENEGADO: permisos insuficientes"
	}

	// b) Proxy de caché: evita descargas repetidas
	if contenido, ok := p.cache[id]; ok {
		fmt.Printf("  ⚡ [Proxy Cache] Devolviendo '%s' desde memoria caché\n", id)
		return contenido
	}

	// c) Proxy virtual: inicialización diferida del servicio pesado
	if p.servicioReal == nil {
		fmt.Println("  🔧 [Proxy Virtual] Inicializando conexión con AlmacenRemotoS3...")
		p.servicioReal = &AlmacenRemotoS3{}
	}

	resultado := p.servicioReal.ObtenerDocumento(id, rolUsuario)
	p.cache[id] = resultado
	return resultado
}

func main() {
	var repo RepositorioDocumentos = NuevoProxyRepositorio()

	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "invitado"))
	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "admin"))
	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "editor"))
}

🔍 Paso a paso

  1. En la primera llamada (invitado), el Proxy de protección rechaza la petición sin siquiera instanciar AlmacenRemotoS3.
  2. En la segunda llamada (admin), el Proxy virtual inicializa el servicio en diferido, descarga el documento y lo guarda en caché.
  3. En la tercera llamada (editor), el Proxy de caché responde al instante desde memoria sin tocar la red.

Nota idiomática de Go

En entornos concurrentes en Go, un proxy virtual suele usar sync.Once para inicializar servicioReal de forma segura entre goroutines, y sync.RWMutex para proteger el mapa de caché. Además, httputil.ReverseProxy en la biblioteca estándar es una implementación de producción de este patrón.
