🧱 Principios SOLID

Los principios SOLID

Cinco reglas para escribir código más comprensible, flexible y fácil de mantener

📜 Un poco de historia

Robert C. Martin ("Uncle Bob") presentó estos principios en su artículo de 2000 Design Principles and Design Patterns. Más tarde, Michael Feathers propuso el acrónimo SOLID.

Su objetivo: evitar que el software se vuelva rígido (difícil de cambiar), frágil (se rompe al cambiarlo) e inmóvil (imposible de reutilizar).

🔗 ¿Por qué antes de los patrones?

Los patrones de diseño son, en gran medida, aplicaciones concretas de SOLID. Cuando veas Strategy, Decorator u Observer, pregúntate: ¿qué principio está aplicando?

Usaremos el ejemplo del artículo: una pequeña librería que vende libros y emite facturas.

🧱 SOLIDS · 1 / 2

S — Principio de Responsabilidad Única

Single Responsibility Principle (SRP)

📏 Enunciado

Un módulo (en Go: un tipo o un paquete) debe tener una sola responsabilidad, es decir, una única razón para cambiar.

type Factura struct {
    Libro         Libro
    Cantidad      int
    TasaDescuento float64
    TasaImpuesto  float64
}

// Responsabilidad 1: reglas de negocio ✔
func (f Factura) Total() float64 { ... }

// Responsabilidad 2: presentación  ✘
func (f Factura) Imprimir() {
    fmt.Printf("%dx %s ...", f.Cantidad, ...)
}

// Responsabilidad 3: persistencia  ✘
func (f Factura) GuardarArchivo(nombre string) {
    // abre archivo, escribe...
}

😟 ¿Qué está mal?

Factura tiene tres razones para cambiar:

  • Cambian las reglas de descuento o impuestos → negocio.
  • Cambia el formato de impresión (PDF, HTML...) → presentación.
  • Queremos guardar en base de datos o llamar a una API → persistencia.

Mezclar lógica de negocio con impresión o persistencia es uno de los errores más comunes: un cambio en el formato puede romper el cálculo.

💡 Solución

Separar cada responsabilidad en su propio tipo: Factura (calcula), FacturaImpresion (muestra) y FacturaPersistencia (guarda).

🧱 SOLIDS · 2 / 2 · Go

SRP aplicado en Go

type Libro struct {
    Nombre, Autor string
    Precio        float64
}

// Factura: SOLO sabe calcular. Su única razón para cambiar
// es un cambio en las reglas de negocio de la facturación.
type Factura struct {
    Libro         Libro
    Cantidad      int
    TasaDescuento float64
    TasaImpuesto  float64
}

func (f Factura) Total() float64 {
    precio := (f.Libro.Precio - f.Libro.Precio*f.TasaDescuento) * float64(f.Cantidad)
    return precio * (1 + f.TasaImpuesto)
}

// FacturaImpresion: única responsabilidad -> presentar la factura.
type FacturaImpresion struct{ factura Factura }

func (fi FacturaImpresion) Imprimir() {
    f := fi.factura
    fmt.Printf("%dx %s %.2f$\n", f.Cantidad, f.Libro.Nombre, f.Libro.Precio)
    fmt.Printf("Descuento: %.0f%%  Impuesto: %.0f%%\n", f.TasaDescuento*100, f.TasaImpuesto*100)
    fmt.Printf("Total: %.2f$\n", f.Total())
}

// FacturaPersistencia: única responsabilidad -> guardar la factura.
type FacturaPersistencia struct{ factura Factura }

func (fp FacturaPersistencia) GuardarArchivo(nombre string) {
    fmt.Printf("Guardando factura de %q en %s\n", fp.factura.Libro.Nombre, nombre)
}

func main() {
    libro := Libro{Nombre: "El Quijote", Autor: "Cervantes", Precio: 50}
    f := Factura{Libro: libro, Cantidad: 2, TasaDescuento: 0.10, TasaImpuesto: 0.19}

    FacturaImpresion{f}.Imprimir()
    FacturaPersistencia{f}.GuardarArchivo("factura.txt")
}
  1. Factura conserva solo los datos y el cálculo de Total().
  2. FacturaImpresion recibe una factura y decide cómo se ve.
  3. FacturaPersistencia decide dónde se guarda.
  4. Cambiar el formato de impresión ya no puede romper el cálculo del total.
2x El Quijote 50.00$
Descuento: 10%  Impuesto: 19%
Total: 107.10$
Guardando factura de "El Quijote" en factura.txt

🧱 SOLIDO · 1 / 2

O — Principio Abierto / Cerrado

Open/Closed Principle (OCP) — Bertrand Meyer, 1988

📏 Enunciado

Las entidades de software deben estar abiertas a la extensión (agregar comportamiento nuevo) pero cerradas a la modificación (sin cambiar el código existente, ya probado).

type FacturaPersistencia struct {
    factura Factura
}

func (p FacturaPersistencia) GuardarArchivo(nombre string) { ... }

// El jefe pide base de datos -> EDITAMOS el tipo
func (p FacturaPersistencia) GuardarEnBaseDatos() { ... }

// Luego MongoDB -> EDITAMOS otra vez...
func (p FacturaPersistencia) GuardarEnMongo() { ... }

// ...y todo el que lo usa debe cambiar con un switch:
switch destino {
case "archivo": p.GuardarArchivo("f.txt")
case "bd":      p.GuardarEnBaseDatos()
case "mongo":   p.GuardarEnMongo()
}

😟 El problema

Cada vez que modificamos código existente corremos el riesgo de introducir errores en algo que ya funcionaba. Además, los switch por tipo se riegan por todo el programa.

💡 La solución: abstracción

Convertir FacturaPersistencia en una interfaz con un método Guardar. Cada nuevo destino es un tipo nuevo que la implementa: extendemos agregando código, no editándolo.

Este es el principio detrás de Strategy, Decorator, Observer, Visitor...

🧱 SOLIDO · 2 / 2 · Go

OCP aplicado en Go

type Factura struct {
    ID    int
    Total float64
}

// Abstracción estable: CERRADA a modificación.
type FacturaPersistencia interface {
    Guardar(f Factura) error
}

// Extensiones: cada nueva forma de guardar es un tipo NUEVO.
type ArchivoPersistencia struct{ Ruta string }

func (a ArchivoPersistencia) Guardar(f Factura) error {
    fmt.Printf("[archivo] factura #%d -> %s\n", f.ID, a.Ruta)
    return nil
}

type BaseDeDatosPersistencia struct{ Tabla string }

func (b BaseDeDatosPersistencia) Guardar(f Factura) error {
    fmt.Printf("[postgres] INSERT INTO %s VALUES (%d, %.2f)\n", b.Tabla, f.ID, f.Total)
    return nil
}

// Agregado meses después SIN tocar nada de lo anterior.
type MongoPersistencia struct{ Coleccion string }

func (m MongoPersistencia) Guardar(f Factura) error {
    fmt.Printf("[mongo] %s.insertOne({id: %d})\n", m.Coleccion, f.ID)
    return nil
}

// Este código nunca cambia aunque aparezcan nuevos almacenamientos.
func GuardarTodas(p FacturaPersistencia, facturas []Factura) {
    for _, f := range facturas {
        if err := p.Guardar(f); err != nil {
            fmt.Println("error:", err)
        }
    }
}

func main() {
    facturas := []Factura{{1, 107.1}, {2, 59.5}}
    destinos := []FacturaPersistencia{
        ArchivoPersistencia{"facturas.txt"},
        BaseDeDatosPersistencia{"facturas"},
        MongoPersistencia{"facturas"},
    }
    for _, d := range destinos {
        GuardarTodas(d, facturas)
    }
}
  1. La interfaz FacturaPersistencia es el punto de extensión.
  2. GuardarTodas depende solo de la interfaz: está cerrada.
  3. Agregar MongoPersistencia no requirió modificar ninguna línea existente: el sistema está abierto.
[archivo] factura #1 -> facturas.txt
[archivo] factura #2 -> facturas.txt
[postgres] INSERT INTO facturas VALUES (1, 107.10)
[postgres] INSERT INTO facturas VALUES (2, 59.50)
[mongo] facturas.insertOne({id: 1})
[mongo] facturas.insertOne({id: 2})

io.Writer es OCP puro: fmt.Fprintf escribe en archivos, sockets, buffers o tu propio tipo sin haber cambiado nunca.

🧱 SOLIDL · 1 / 2

L — Principio de Sustitución de Liskov

Liskov Substitution Principle (LSP) — Barbara Liskov, 1987

📏 Enunciado

Los subtipos deben poder sustituir a su tipo base sin alterar el correcto funcionamiento del programa. Si B es un subtipo de A, cualquier código que use un A debe funcionar igual con un B, sin resultados extraños.

🟥 El ejemplo clásico: Rectángulo vs. Cuadrado

En matemáticas un cuadrado "es un" rectángulo. Así que en Java hacemos Cuadrado extends Rectangulo y sobrescribimos los setters para que setAncho también cambie el alto (y viceversa).

Un cliente que hace setAncho(5); setAlto(4) espera un área de 20... pero con un cuadrado obtiene 16. 💥

El subtipo reduce las garantías del tipo base en lugar de extenderlas. El error es difícil de detectar porque el código compila perfectamente.

🐹 ¿Y en Go, que no tiene herencia?

LSP aplica igual a las interfaces: un tipo que satisface una interfaz debe respetar su contrato implícito, no solo sus firmas.

  • No lanzar panic("no implementado") en métodos de la interfaz.
  • No exigir más precondiciones que el contrato.
  • No entregar menos de lo prometido (postcondiciones).
  • Ej: un io.Reader debe devolver io.EOF al terminar, como todos.

⚠️ Regla práctica

Si para que un tipo "encaje" tienes que sobrescribir un método para que haga algo distinto o nada, o tu cliente necesita preguntar if _, ok := x.(Cuadrado), probablemente estás violando LSP.

🧱 SOLIDL · 2 / 2 · Go

LSP en Go: violación y corrección

// ❌ VIOLACIÓN: una interfaz con setters que Cuadrado no puede cumplir.
type RectanguloMutable interface {
    SetAncho(w float64)
    SetAlto(h float64)
    Area() float64
}

type Rectangulo struct{ ancho, alto float64 }

func (r *Rectangulo) SetAncho(w float64) { r.ancho = w }
func (r *Rectangulo) SetAlto(h float64)  { r.alto = h }
func (r *Rectangulo) Area() float64      { return r.ancho * r.alto }

type Cuadrado struct{ lado float64 }

func (c *Cuadrado) SetAncho(w float64) { c.lado = w } // cambia ambos lados
func (c *Cuadrado) SetAlto(h float64)  { c.lado = h } // cambia ambos lados
func (c *Cuadrado) Area() float64      { return c.lado * c.lado }

// El cliente confía en el contrato: "ancho y alto son independientes".
func PruebaArea(r RectanguloMutable) {
    r.SetAncho(5)
    r.SetAlto(4)
    fmt.Printf("%-16T área esperada 20, obtenida %.0f\n", r, r.Area())
}

// ✅ SOLUCIÓN: un contrato que TODOS pueden cumplir.
type Forma interface{ Area() float64 }

type Rect struct{ Ancho, Alto float64 }
type Cuad struct{ Lado float64 }

func (r Rect) Area() float64 { return r.Ancho * r.Alto }
func (c Cuad) Area() float64 { return c.Lado * c.Lado }

func AreaTotal(formas ...Forma) (t float64) {
    for _, f := range formas {
        t += f.Area()
    }
    return
}

func main() {
    PruebaArea(&Rectangulo{})
    PruebaArea(&Cuadrado{}) // 💥 rompe la expectativa del cliente

    fmt.Println("Área total:", AreaTotal(Rect{5, 4}, Cuad{3}))
}
  1. Cuadrado compila como RectanguloMutable, pero no respeta su contrato.
  2. PruebaArea obtiene 16 en lugar de 20: la sustitución no es segura.
  3. La corrección: modelar una abstracción más honesta (Forma) que todos los tipos pueden cumplir sin trucos, y valores inmutables.
*main.Rectangulo área esperada 20, obtenida 20
*main.Cuadrado   área esperada 20, obtenida 16
Área total: 29
🐹

Lección

"Es un" en el mundo real no implica "es sustituible" en el código. Diseña interfaces por comportamiento que el cliente necesita, no por taxonomías.

🧱 SOLIDI · 1 / 2

I — Principio de Segregación de Interfaces

Interface Segregation Principle (ISP)

📏 Enunciado

Ningún cliente debe ser forzado a depender de métodos que no utiliza. Es mejor tener muchas interfaces pequeñas y específicas que una interfaz grande de propósito general.

type Estacionamiento interface {
    // lógica de estacionamiento
    Aparcar(c Coche)
    Sacar(c Coche)
    Capacidad() int
    // lógica de pagos
    CalcularTarifa(c Coche) float64
    HacerPago(c Coche)
}

type EstacionamientoGratis struct{ ... }

// Obligado a implementar pagos que no tienen sentido 😩
func (e *EstacionamientoGratis) CalcularTarifa(c Coche) float64 {
    return 0
}
func (e *EstacionamientoGratis) HacerPago(c Coche) {
    panic("¡este estacionamiento es gratis!")
}

😟 El problema

La interfaz mezcla dos responsabilidades: estacionar y cobrar. El estacionamiento gratuito queda obligado a escribir métodos vacíos o que hacen panic (¡lo que además viola Liskov!).

💡 La solución

Separar (segregar) la interfaz en Estacionamiento y Pagable. Cada tipo implementa solo lo que necesita. Incluso podríamos dividir Pagable por tipo de pago.

🐹

Go ama el ISP

io.Reader, io.Writer, fmt.Stringer, error: interfaces de un solo método que se combinan (io.ReadWriter).

🧱 SOLIDI · 2 / 2 · Go

ISP aplicado en Go

type Coche struct{ Placa string }

// ✅ Interfaces pequeñas y enfocadas (en vez de una "Estacionamiento" gigante).
type Estacionamiento interface {
    Aparcar(c Coche)
    Sacar(c Coche)
    Capacidad() int
}

type Pagable interface {
    CalcularTarifa(c Coche, horas int) float64
}

// base reutilizable por composición (embedding)
type base struct {
    cupos   int
    ocupado map[string]bool
}

func (b *base) Aparcar(c Coche) { b.ocupado[c.Placa] = true; fmt.Println("  entra", c.Placa) }
func (b *base) Sacar(c Coche)   { delete(b.ocupado, c.Placa); fmt.Println("  sale ", c.Placa) }
func (b *base) Capacidad() int  { return b.cupos - len(b.ocupado) }

// Gratis: implementa SOLO lo que necesita. Nada de métodos de pago vacíos.
type EstacionamientoGratis struct{ *base }

// Pagado: implementa Estacionamiento + Pagable.
type EstacionamientoPagado struct {
    *base
    precioHora float64
}

func (e EstacionamientoPagado) CalcularTarifa(_ Coche, horas int) float64 {
    return float64(horas) * e.precioHora
}

func nuevaBase(n int) *base { return &base{cupos: n, ocupado: map[string]bool{}} }

func main() {
    auto := Coche{"ABC-123"}
    lugares := []Estacionamiento{
        EstacionamientoGratis{nuevaBase(10)},
        EstacionamientoPagado{nuevaBase(5), 3000},
    }
    for _, e := range lugares {
        fmt.Printf("%T\n", e)
        e.Aparcar(auto)
        // Solo preguntamos por el pago a quien lo soporta
        if p, ok := e.(Pagable); ok {
            fmt.Printf("  tarifa 2h: $%.0f\n", p.CalcularTarifa(auto, 2))
        }
        e.Sacar(auto)
        fmt.Println("  cupos libres:", e.Capacidad())
    }
}
  1. Dos interfaces pequeñas: Estacionamiento y Pagable.
  2. La lógica común vive en base y se embebe (composición en lugar de herencia).
  3. EstacionamientoGratis ni siquiera sabe que existen los pagos.
  4. La type assertion e.(Pagable) permite preguntar por una capacidad opcional.

  sale  ABC-123
  cupos libres: 10
main.EstacionamientoPagado

D — Principio de Inversión de Dependencias

Dependency Inversion Principle (DIP)

📏 Enunciado

Los módulos de alto nivel no deben depender de módulos de bajo nivel: ambos deben depender de abstracciones. Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones.

SIN DIP (la dependencia apunta al detalle) ┌──────────────────────────┐ │ AdministradorPersistencia│ alto nivel └────────────┬─────────────┘ │ usa directamente ▼ ┌──────────────────────────┐ │ MySQLFacturas │ bajo nivel └──────────────────────────┘ CON DIP (ambos dependen de la abstracción) ┌──────────────────────────┐ │ AdministradorPersistencia│ └────────────┬─────────────┘ │ depende de ▼ ┌──────────────────────────┐ │ «interface» │ │ FacturaPersistencia │ └────────────▲─────────────┘ │ implementa (¡la flecha se invierte!) ┌─────────┴─────────┐ MySQLFacturas FakeFacturas

🔁 ¿Qué se "invierte"?

Normalmente la lógica de negocio llama al código de infraestructura y por tanto depende de él. Con DIP, la lógica de negocio define la interfaz que necesita y la infraestructura se adapta a ella.

🤝 Relación con OCP

Como dice el artículo citando al tío Bob: "si OCP establece el objetivo de la arquitectura OO, DIP establece el mecanismo principal".

💉 Inyección de dependencias

La técnica habitual para aplicar DIP: el objeto recibe sus dependencias (por constructor) en vez de crearlas. Esto permite cambiar MySQL por un fake en las pruebas.

🧱 SOLIDD · 2 / 2 · Go

DIP aplicado en Go

type Factura struct{ ID int }
type Libro struct{ ISBN string }

// Abstracciones (las define quien las USA, no quien las implementa)
type FacturaPersistencia interface{ Guardar(Factura) }
type LibroPersistencia interface{ Guardar(Libro) }

// Módulo de ALTO nivel: depende solo de interfaces.
type AdministradorPersistencia struct {
    facturas FacturaPersistencia
    libros   LibroPersistencia
}

// Inyección de dependencias por constructor
func NewAdministrador(f FacturaPersistencia, l LibroPersistencia) *AdministradorPersistencia {
    return &AdministradorPersistencia{facturas: f, libros: l}
}

func (a *AdministradorPersistencia) Respaldar(fs []Factura, ls []Libro) {
    for _, f := range fs {
        a.facturas.Guardar(f)
    }
    for _, l := range ls {
        a.libros.Guardar(l)
    }
}

// Módulos de BAJO nivel: detalles intercambiables.
type MySQLFacturas struct{}

func (MySQLFacturas) Guardar(f Factura) { fmt.Println("MySQL   <- factura", f.ID) }

type MemoriaLibros struct{ datos []Libro }

func (m *MemoriaLibros) Guardar(l Libro) {
    m.datos = append(m.datos, l)
    fmt.Println("Memoria <- libro", l.ISBN)
}

// Un doble de prueba: cambiar el detalle no toca el alto nivel.
type FakeFacturas struct{ n int }

func (f *FakeFacturas) Guardar(Factura) { f.n++ }

func main() {
    admin := NewAdministrador(MySQLFacturas{}, &MemoriaLibros{})
    admin.Respaldar([]Factura{{1}, {2}}, []Libro{{"978-84"}})

    fake := &FakeFacturas{}
    NewAdministrador(fake, &MemoriaLibros{}).Respaldar([]Factura{{1}, {2}, {3}}, nil)
    fmt.Println("En pruebas se guardaron", fake.n, "facturas")
}
  1. AdministradorPersistencia (alto nivel) solo conoce interfaces.
  2. Las dependencias se inyectan en NewAdministrador.
  3. MySQL, memoria o un fake son detalles intercambiables.
  4. Probar la lógica no requiere una base de datos real.
