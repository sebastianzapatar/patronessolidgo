Factory Method

También llamado: Método fábrica, Constructor virtual

🎯 Propósito

Define una interfaz o contrato para crear objetos en una abstracción base, pero delega en los tipos concretos (subclases o implementaciones) la decisión de qué estructura o clase específica instanciar.

😟 Problema

Imagina que desarrollas una aplicación de gestión logística. Al inicio sólo transportas carga por tierra, así que todo tu código instancia directamente objetos Camion. Cuando tu sistema crece y necesitas incorporar transporte marítimo con objetos Barco, descubres que el código cliente está fuertemente acoplado a Camion.

Añadir barcos o aviones obligaría a llenar el código de condicionales (if/switch) preguntando el tipo de transporte en decenas de archivos, haciendo el mantenimiento frágil y costoso.

💡 Solución

Sustituir las llamadas directas de construcción (&Camion{}) por invocaciones a un método fábrica especial (CrearTransporte()) declarado en una interfaz creadora común (Logistica).

Cada variante creadora (LogisticaTerrestre, LogisticaMaritima) implementa ese método devolviendo un producto concreto diferente (Camion o Barco), pero ambos cumplen la misma interfaz Transporte. El código cliente opera con Transporte sin saber cómo fue construido ni de qué tipo concreto se trata.

🌍

Analogía en el mundo real

En una empresa de mensajería nacional, el gerente de envíos sigue siempre el mismo protocolo: "preparar paquete, asignar medio de transporte y despachar". Si la sucursal es terrestre, el encargado de flota asigna un camión; si es portuaria, asigna un buque de carga. El protocolo de despacho no cambia porque confía en que cualquier transporte sabe cómo entregar la mercancía.

└──────────────┘ └──────────────┘    └────────────┘   └────────────┘

🔗 Relación con otros patrones

  • Muchos diseños empiezan con Factory Method (más simple) y evolucionan hacia Abstract Factory, Prototype o Builder cuando necesitan mayor flexibilidad.
  • Abstract Factory suele implementarse como un conjunto de varios Factory Methods.
  • Es una especialización de Template Method para el paso específico de creación de objetos.

🧩 Participantes

  1. Producto (Transporte): declara la interfaz común a todos los objetos que los creadores pueden producir.
  2. Productos Concretos (Camion, Barco): proveen distintas implementaciones de la interfaz del producto.
  3. Creador (Logistica): declara el método fábrica que retorna objetos del tipo Producto; suele acompañarse de lógica de negocio que opera sobre esos productos.
  4. Creadores Concretos (LogisticaTerrestre, LogisticaMaritima): implementan el método fábrica retornando una instancia de un producto concreto específico.

🧭 Aplicabilidad

  • Cuando no conoces de antemano los tipos concretos ni las dependencias exactas de los objetos con los que debe operar tu sistema.
  • Cuando deseas ofrecer a los usuarios de tu biblioteca o paquete un punto de extensión limpio para enchufar sus propios componentes.
  • Cuando necesitas reutilizar objetos existentes (p. ej., desde un pool o caché de conexiones) en vez de instanciar nuevos cada vez.

🛠️ Cómo implementarlo

  1. Haz que todos los productos implementen una misma interfaz con métodos que tengan sentido para todos ellos.
  2. Declara el método fábrica en la interfaz o estructura creadora con tipo de retorno igual a la interfaz del producto.
  3. Sustituye en la lógica de negocio las creaciones directas por llamadas al método fábrica.
  4. Crea un creador concreto para cada variante de producto para que instancie y devuelva el tipo adecuado.

✅ Pros

  • Elimina el acoplamiento fuerte entre la lógica creadora y los productos concretos.
  • Principio de Responsabilidad Única (SRP): concentra el código de creación en un único lugar fácil de mantener.
  • Principio Abierto/Cerrado (OCP): incorpora nuevos tipos de productos sin modificar el código cliente existente.

❌ Contras

  • Puede incrementar la cantidad de tipos y estructuras si se exige crear un creador concreto por cada producto sencillo.

Factory Method en Go

package main

import "fmt"

// 1. Producto (interfaz común a todos los transportes)
type Transporte interface {
	Entregar(carga string) string
}

// 2. Productos Concretos
type Camion struct{ Placa string }

func (c *Camion) Entregar(carga string) string {
	return fmt.Sprintf("🚚 Camión [%s] entrega %q por carretera", c.Placa, carga)
}

type Barco struct{ Nombre string }

func (b *Barco) Entregar(carga string) string {
	return fmt.Sprintf("🚢 Barco %q entrega %q por vía marítima", b.Nombre, carga)
}

// 3. Creador (interfaz con el Factory Method)
type Logistica interface {
	CrearTransporte() Transporte // Factory Method
}

// Lógica de negocio común que trabaja con la interfaz Creador
// sin conocer el tipo concreto de transporte que se creará.
func PlanificarEntrega(l Logistica, carga string) {
	transporte := l.CrearTransporte()
	fmt.Println("📦 Planificando:", transporte.Entregar(carga))
}

// 4. Creadores Concretos (sobrescriben el Factory Method)
type LogisticaTerrestre struct{ PlacaAsignada string }

func (lt *LogisticaTerrestre) CrearTransporte() Transporte {
	return &Camion{Placa: lt.PlacaAsignada}
}

type LogisticaMaritima struct{ BuqueAsignado string }

func (lm *LogisticaMaritima) CrearTransporte() Transporte {
	return &Barco{Nombre: lm.BuqueAsignado}
}

func main() {
	terrestre := &LogisticaTerrestre{PlacaAsignada: "ABC-123"}
	maritima := &LogisticaMaritima{BuqueAsignado: "El Navegante"}

	PlanificarEntrega(terrestre, "Electrónicos")
	PlanificarEntrega(maritima, "Contenedores de grano")
}

🔍 Explicación paso a paso

  1. Transporte define el contrato del Producto con el método Entregar.
  2. Camion y Barco implementan implícitamente Transporte cada uno a su manera.
  3. Logistica declara el Factory Method CrearTransporte() Transporte.
  4. PlanificarEntrega contiene la lógica de negocio reutilizable: pide un transporte a la fábrica y lo usa sin acoplarse a camiones ni barcos.
  5. Si mañana agregamos LogisticaAerea y Avion, PlanificarEntrega no sufre ni un solo cambio.
📦 Planificando: 🚚 Camión [ABC-123] entrega "Electrónicos" por carretera
📦 Planificando: 🚢 Barco "El Navegante" entrega "Contenedores de grano" por vía marítima
🐹

Nota idiomática en Go

Como Go no tiene clases abstractas ni herencia, la lógica común (PlanificarEntrega) se escribe como una función que recibe la interfaz Logistica (o mediante embedding), y a menudo un simple constructor NewTransporte(tipo) o un tipo función type CreadorTransporte func() Transporte basta cuando no hay estado adicional en el creador.

Abstract Factory

También llamado: Fábrica abstracta, Kit

🎯 Propósito

Permite producir familias de objetos relacionados o dependientes entre sí sin especificar sus tipos o clases concretas, garantizando que los objetos creados sean siempre compatibles.

😟 Problema

Imagina un simulador de tienda de muebles o un toolkit de interfaz gráfica multiplataforma. Tienes una familia de productos que trabajan juntos (p. ej. Boton + Casilla, o Silla + Sofa + Mesilla) y varias variantes o estilos (Windows vs. macOS, o Moderno vs. Victoriano).

Si el código cliente instancia widgets o muebles sueltos directamente, es muy fácil mezclar por error un botón de Windows con una casilla de macOS, o llenar la aplicación de condicionales cada vez que se agrega un nuevo sistema operativo o catálogo.

💡 Solución

Declarar primero una interfaz para cada producto de la familia (Boton, Casilla) y luego una interfaz Fábrica Abstracta (FabricaGUI) con métodos de creación para todos los productos de la familia (CrearBoton(), CrearCasilla()).

Por cada variante o estilo se implementa una Fábrica Concreta (FabricaWindows, FabricaMac) que produce únicamente objetos de esa misma familia. El cliente recibe una fábrica abstracta al iniciar y todos los elementos que solicita combinan entre sí automáticamente.

🛋️

Analogía en el mundo real

Cuando compras un juego de sala por catálogo, eliges primero la línea de diseño (por ejemplo, Escandinava o Industrial). A partir de ese proveedor pides una silla, un sofá y una mesa de centro: sin importar qué pieza pidas, todas comparten materiales, colores y proporciones compatibles entre sí.

🔗 Relación con otros patrones

  • Suele construirse a partir de varios Factory Methods o apoyarse en Prototype para clonar familias de productos.
  • Mientras Abstract Factory devuelve familias de objetos de inmediato, Builder construye un único objeto complejo paso a paso.
  • Las fábricas concretas suelen implementarse como Singletons.

🧩 Participantes

  1. Productos Abstractos (Boton, Casilla): interfaces para cada tipo de componente distinto que integra la familia.
  2. Productos Concretos (BotonWindows, BotonMac, etc.): implementaciones de los productos agrupadas por variante.
  3. Fábrica Abstracta (FabricaGUI): declara los métodos para crear cada uno de los productos abstractos de la familia.
  4. Fábricas Concretas (FabricaWindows, FabricaMac): implementan los métodos de creación devolviendo productos de una única variante compatible.
  5. Cliente (RenderizarPantalla): trabaja exclusivamente con las interfaces FabricaGUI, Boton y Casilla.

🧭 Aplicabilidad

  • Cuando el código necesita trabajar con diversas familias de productos relacionados sin depender de sus clases concretas.
  • Cuando es indispensable garantizar que los productos creados en un contexto pertenezcan siempre a la misma variante o tema.
  • Cuando una clase acumula múltiples Factory Methods que empañan su responsabilidad principal.

🛠️ Cómo implementarlo

  1. Traza una matriz de tipos de productos (filas) frente a variantes de familia (columnas).
  2. Declara interfaces de producto abstracto para cada tipo e impleméntalas en las variantes concretas.
  3. Define la interfaz de la fábrica abstracta con un método de creación por cada producto abstracto.
  4. Crea una estructura de fábrica concreta por cada variante e inyéctala al código cliente durante la inicialización.

✅ Pros

  • Garantiza al 100% que los productos que recibe el cliente sean compatibles entre sí.
  • Desacopla el código cliente de los tipos concretos (cumple SRP y OCP al agregar nuevas variantes completas).

❌ Contras

  • Añade bastantes interfaces y tipos nuevos; además, agregar un nuevo tipo de producto a la familia requiere modificar la interfaz de la fábrica y todas sus implementaciones.

Abstract Factory en Go

package main

import "fmt"

// 1. Productos Abstractos (familia de objetos relacionados)
type Boton interface {
	Dibujar() string
}

type Casilla interface {
	Marcar(activo bool) string
}

// 2. Productos Concretos — Variante Windows
type BotonWindows struct{}

func (BotonWindows) Dibujar() string { return "[ 🪟 Botón estilo Windows ]" }

type CasillaWindows struct{}

func (CasillaWindows) Marcar(ok bool) string {
	return fmt.Sprintf("[🪟 Casilla Windows: %v]", ok)
}

// 2. Productos Concretos — Variante Mac
type BotonMac struct{}

func (BotonMac) Dibujar() string { return "( 🍎 Botón estilo macOS )" }

type CasillaMac struct{}

func (CasillaMac) Marcar(ok bool) string {
	return fmt.Sprintf("(🍎 Casilla macOS: %v)", ok)
}

// 3. Fábrica Abstracta (crea una familia completa de productos)
type FabricaGUI interface {
	CrearBoton() Boton
	CrearCasilla() Casilla
}

// 4. Fábricas Concretas (garantizan compatibilidad de la familia)
type FabricaWindows struct{}

func (FabricaWindows) CrearBoton() Boton     { return BotonWindows{} }
func (FabricaWindows) CrearCasilla() Casilla { return CasillaWindows{} }

type FabricaMac struct{}

func (FabricaMac) CrearBoton() Boton     { return BotonMac{} }
func (FabricaMac) CrearCasilla() Casilla { return CasillaMac{} }

// 5. Cliente: usa únicamente las interfaces abstractas
func RenderizarPantalla(f FabricaGUI) {
	boton := f.CrearBoton()
	casilla := f.CrearCasilla()
	fmt.Println(boton.Dibujar(), "->", casilla.Marcar(true))
}

func main() {
	fmt.Println("=== Entorno Windows ===")
	RenderizarPantalla(FabricaWindows{})

	fmt.Println("=== Entorno macOS ===")
	RenderizarPantalla(FabricaMac{})
}

🔍 Explicación paso a paso

  1. Definimos dos productos de una misma familia UI: Boton y Casilla.
  2. Implementamos las variantes Windows y Mac para cada producto.
  3. FabricaGUI agrupa la creación de ambos productos en una sola interfaz cohesiva.
  4. RenderizarPantalla recibe cualquier FabricaGUI: es imposible que mezcle un botón Windows con una casilla Mac.
=== Entorno Windows ===
[ 🪟 Botón estilo Windows ] -> [🪟 Casilla Windows: true]
=== Entorno macOS ===
( 🍎 Botón estilo macOS ) -> (🍎 Casilla macOS: true)
🐹

Nota idiomática en Go

En Go, las fábricas concretas sin estado como FabricaWindows{} son estructuras vacías (zero-size structs, 0 bytes en memoria). Cumplen la interfaz FabricaGUI sin sobrecarga de memoria y permiten inyección de dependencias limpia en tests.

Builder

También llamado: Constructor paso a paso

🎯 Propósito

Permite construir objetos complejos paso a paso, produciendo distintos tipos y representaciones de un objeto empleando exactamente el mismo proceso de construcción.

😟 Problema

Imagina crear un objeto complejo como una Casa o una petición HTTP/SQL con docenas de opciones: paredes, tipo de techo, número de ventanas, calefacción, jardín, piscina, garaje, etc.

Si creas una subclase por cada combinación posible, la jerarquía explota. Y si pones todo en un único constructor gigante de 15 parámetros (constructor telescópico), las llamadas quedan ilegibles y propensas a errores porque la mayoría de los parámetros serán nulos o irrelevantes en el 90% de los casos.

💡 Solución

Extraer el código de ensamblaje fuera del producto y llevarlo a objetos independientes llamados constructores (builders), dividiendo la creación en pasos claros (ConstruirParedes, ConstruirTecho, ConstruirPiscina).

Se pueden definir distintos constructores concretos (p. ej. ConstructorCabana, ConstructorMansion) que ejecutan los mismos pasos con materiales diferentes, y opcionalmente una clase Directora que encapsula recetas u órdenes de construcción reutilizables sin exponer el producto hasta que esté terminado.

🏗️

Analogía en el mundo real

Un maestro de obra (Director) conoce el orden exacto para levantar una vivienda: primero cimientos, luego muros, después techo y finalmente acabados. Si contrata a una cuadrilla rústica (Constructor A), esos mismos pasos producen una cabaña de madera; si contrata a una cuadrilla de lujo (Constructor B), la misma secuencia entrega una mansión moderna con piscina.

🔗 Relación con otros patrones

  • Builder construye un objeto complejo paso a paso y entrega el resultado al final; Abstract Factory entrega familias de objetos inmediatamente.
  • Es muy útil para construir árboles Composite complejos dado que sus pasos pueden invocarse recursivamente.
  • Al combinarlo con Bridge, el Director actúa como la abstracción y los distintos Builders como las implementaciones.

🧩 Participantes

  1. Interfaz Constructora (ConstructorCasa): declara los pasos de construcción comunes a todas las representaciones.
  2. Constructores Concretos (ConstructorCabana, ConstructorMansion): implementan cada paso de manera específica y guardan el estado intermedio.
  3. Producto (Casa): el objeto complejo resultante tras completar los pasos.
  4. Director: define el orden en que se ejecutan los pasos para crear configuraciones estándar reutilizables.
  5. Cliente: asocia un constructor concreto con el director (o invoca los pasos directamente) y recoge el producto final.

🧭 Aplicabilidad

  • Para eliminar constructores con largas listas de parámetros opcionales (constructor telescópico).
  • Cuando el código debe crear distintas representaciones de un mismo producto (p. ej. cabaña vs. mansión, o automóvil vs. manual) cuyos pasos de montaje son similares.
  • Para ensamblar estructuras complejas o árboles Composite aplazando o repitiendo pasos sin exponer un objeto incompleto.

🛠️ Cómo implementarlo

  1. Identifica y declara en la interfaz constructora los pasos de producción comunes a todas las representaciones.
  2. Crea un constructor concreto por cada representación e incluye un método para extraer el producto terminado y reiniciar el estado.
  3. Opcionalmente, crea una estructura Director que reciba el constructor y ejecute rutinas de pasos predefinidas.

✅ Pros

  • Permite construir objetos paso a paso, aplazar pasos o ejecutarlos de forma condicional/recursiva.
  • Reutiliza el mismo proceso de montaje para distintas representaciones y aísla la construcción compleja de la lógica del producto (SRP).

❌ Contras

  • Aumenta la complejidad general cuando se requiere crear múltiples interfaces y estructuras constructoras para objetos simples.

Builder en Go

package main

import "fmt"

// 3. Producto complejo resultante
type Casa struct {
	Paredes    string
	Techo      string
	Ventanas   int
	ConPiscina bool
}

func (c Casa) String() string {
	return fmt.Sprintf("🏠 Casa [Paredes: %s | Techo: %s | Ventanas: %d | Piscina: %v]",
		c.Paredes, c.Techo, c.Ventanas, c.ConPiscina)
}

// 1. Interfaz Constructora (define los pasos comunes)
type ConstructorCasa interface {
	Reiniciar()
	ConstruirParedes()
	ConstruirTecho()
	ConstruirVentanas()
	ConstruirPiscina()
	ObtenerCasa() Casa
}

// 2. Constructor Concreto A: Cabaña de madera
type ConstructorCabana struct{ casa Casa }

func (b *ConstructorCabana) Reiniciar()         { b.casa = Casa{} }
func (b *ConstructorCabana) ConstruirParedes()  { b.casa.Paredes = "Troncos de pino" }
func (b *ConstructorCabana) ConstruirTecho()    { b.casa.Techo = "Tejas de madera" }
func (b *ConstructorCabana) ConstruirVentanas() { b.casa.Ventanas = 2 }
func (b *ConstructorCabana) ConstruirPiscina()  { b.casa.ConPiscina = false }
func (b *ConstructorCabana) ObtenerCasa() Casa  { return b.casa }

// 2. Constructor Concreto B: Mansión moderna
type ConstructorMansion struct{ casa Casa }

func (b *ConstructorMansion) Reiniciar()         { b.casa = Casa{} }
func (b *ConstructorMansion) ConstruirParedes()  { b.casa.Paredes = "Hormigón y cristal" }
func (b *ConstructorMansion) ConstruirTecho()    { b.casa.Techo = "Terraza solar" }
func (b *ConstructorMansion) ConstruirVentanas() { b.casa.Ventanas = 12 }
func (b *ConstructorMansion) ConstruirPiscina()  { b.casa.ConPiscina = true }
func (b *ConstructorMansion) ObtenerCasa() Casa  { return b.casa }

// 4. Director (define el orden de los pasos de construcción)
type Director struct{ constructor ConstructorCasa }

func (d *Director) CambiarConstructor(c ConstructorCasa) { d.constructor = c }

func (d *Director) ConstruirCompleta() Casa {
	d.constructor.Reiniciar()
	d.constructor.ConstruirParedes()
	d.constructor.ConstruirTecho()
	d.constructor.ConstruirVentanas()
	d.constructor.ConstruirPiscina()
	return d.constructor.ObtenerCasa()
}

func main() {
	director := &Director{}

	cabana := &ConstructorCabana{}
	director.CambiarConstructor(cabana)
	fmt.Println(director.ConstruirCompleta())

	mansion := &ConstructorMansion{}
	director.CambiarConstructor(mansion)
	fmt.Println(director.ConstruirCompleta())
}

🔍 Explicación paso a paso

  1. Casa es el producto con múltiples atributos configurables.
  2. ConstructorCasa declara los pasos de ensamblaje que cualquier variante debe cumplir.
  3. ConstructorCabana y ConstructorMansion usan receptores de puntero (*Constructor...) para ir mutando su campo interno casa paso a paso.
  4. Director.ConstruirCompleta() ejecuta la misma receta exacta en ambos constructores produciendo resultados totalmente distintos.
🏠 Casa [Paredes: Troncos de pino | Techo: Tejas de madera | Ventanas: 2 | Piscina: false]
🏠 Casa [Paredes: Hormigón y cristal | Techo: Terraza solar | Ventanas: 12 | Piscina: true]
🐹

Nota idiomática en Go

En Go, además del Builder clásico con Director o encadenamiento fluido (b.ConParedes(...).ConTecho(...)), es muy popular el patrón Functional Options (NewServidor(ConPuerto(8080), ConTLS(true))) para evitar constructores telescópicos cuando sólo hay una representación del producto.

Prototype

También llamado: Prototipo, Clon, Clone

🎯 Propósito

Permite copiar objetos existentes de forma independiente a sus clases o estructuras concretas, delegando el proceso de clonación al propio objeto que se desea duplicar.

😟 Problema

Supón que tienes un objeto complejo configurado en memoria y necesitas crear una copia exacta de él. Si intentas copiarlo "desde fuera", tu código cliente primero debe conocer la estructura concreta para instanciarla (acoplándose a ella) y luego recorrer todos sus campos.

Peor aún: muchos campos pueden ser privados (no exportados en Go) e inaccesibles desde otros paquetes, o el código cliente sólo recibe el objeto a través de una interfaz general y ni siquiera sabe cuál es su tipo concreto real.

💡 Solución

El patrón Prototype declara una interfaz común (p. ej. Prototipo) con un método Clonar(). Cada estructura concreta implementa Clonar() creando una nueva instancia de su propio tipo y copiando todos sus campos internos (incluidos los privados y las estructuras anidadas).

Así, el cliente puede duplicar cualquier objeto o árbol de objetos llamando simplemente a objeto.Clonar(), o mantener un registro de prototipos preconfigurados listos para clonarse bajo demanda.

🧬

Analogía en el mundo real

La división mitótica de una célula en biología: ningún agente externo ensambla una célula nueva átomo por átomo desde fuera; es la propia célula original (el prototipo) quien duplica su ADN e información interna para dar origen a un clon idéntico e independiente.

🔗 Relación con otros patrones

  • Abstract Factory puede almacenar un catálogo de prototipos y clonarlos en lugar de usar Factory Methods.
  • Los diseños con árboles Composite o Decorator usan Prototype para clonar estructuras complejas enteras de una sola vez.
  • Puede servir como alternativa sencilla a Memento o para guardar copias de Command en un historial.

🧩 Participantes

  1. Interfaz Prototipo (Prototipo): declara el método de clonación (Clonar()) que retorna la propia abstracción.
  2. Prototipos Concretos (Archivo, Carpeta): implementan Clonar() copiando sus valores primitivos y duplicando recursivamente sus referencias (slices, mapas, punteros) para evitar efectos colaterales.
  3. Cliente: solicita una copia invocando Clonar() en cualquier objeto que cumpla la interfaz, o consulta un Registro de Prototipos por nombre.

🧭 Aplicabilidad

  • Cuando tu código necesita copiar objetos pero no debe depender de sus tipos concretos (porque los recibe mediante una interfaz).
  • Cuando quieres evitar crear subclases que sólo difieren en cómo inicializan sus atributos, usando en su lugar un catálogo de prototipos preconfigurados.

🛠️ Cómo implementarlo

  1. Declara la interfaz Prototipo con el método Clonar().
  2. Implementa Clonar() en cada estructura concreta instanciando un nuevo objeto del mismo tipo y copiando todos sus campos (cuidando la copia profunda en punteros, slices y mapas).
  3. Opcionalmente, crea un mapa o registro de prototipos frecuentes indexado por clave para clonarlos cuando el cliente los pida.

✅ Pros

  • Permite clonar objetos sin acoplarse a sus clases o estructuras concretas.
  • Evita repetir código de inicialización costoso y facilita duplicar estructuras jerárquicas complejas.

❌ Contras

  • Clonar objetos complejos con punteros compartidos o referencias circulares requiere implementar copias profundas (deep copy) cuidadosas.

Prototype en Go

package main

import "fmt"

// 1. Interfaz Prototipo (declara el método de clonación)
type Prototipo interface {
	Clonar() Prototipo
	Mostrar(indent string)
}

// 2. Prototipo Concreto A: Archivo
type Archivo struct {
	Nombre   string
	Etiqueta []string // slice para demostrar copia profunda (deep copy)
}

func (a *Archivo) Mostrar(indent string) {
	fmt.Printf("%s📄 %s (tags: %v)\n", indent, a.Nombre, a.Etiqueta)
}

func (a *Archivo) Clonar() Prototipo {
	copiaTags := make([]string, len(a.Etiqueta))
	copy(copiaTags, a.Etiqueta)
	return &Archivo{Nombre: a.Nombre + "_copia", Etiqueta: copiaTags}
}

// 2. Prototipo Concreto B: Carpeta (contiene otros Prototipos)
type Carpeta struct {
	Nombre    string
	Elementos []Prototipo
}

func (c *Carpeta) Mostrar(indent string) {
	fmt.Printf("%s📁 %s/\n", indent, c.Nombre)
	for _, elem := range c.Elementos {
		elem.Mostrar(indent + "   ")
	}
}

func (c *Carpeta) Clonar() Prototipo {
	clon := &Carpeta{
		Nombre:    c.Nombre + "_clon",
		Elementos: make([]Prototipo, len(c.Elementos)),
	}
	for i, elem := range c.Elementos {
		clon.Elementos[i] = elem.Clonar() // clona recursivamente sin saber el tipo concreto
	}
	return clon
}

func main() {
	doc := &Archivo{Nombre: "informe.pdf", Etiqueta: []string{"v1", "oficial"}}
	orig := &Carpeta{
		Nombre:    "Proyecto",
		Elementos: []Prototipo{doc, &Archivo{Nombre: "datos.csv", Etiqueta: []string{"raw"}}},
	}

	// 3. El cliente clona la estructura completa a través de la interfaz Prototipo
	copia := orig.Clonar()
	doc.Etiqueta[0] = "MODIFICADO" // no afecta al clon gracias a la copia profunda

	fmt.Println("--- Original (tras modificar doc) ---")
	orig.Mostrar("")
	fmt.Println("--- Clon independiente ---")
	copia.Mostrar("")
}

🔍 Explicación paso a paso

  1. Prototipo declara Clonar() Prototipo.
  2. En Archivo.Clonar() creamos un nuevo slice con make y copy para hacer una copia profunda de Etiqueta.
  3. Carpeta.Clonar() recorre sus hijos []Prototipo e invoca polimórficamente elem.Clonar() sin saber si cada elemento es un archivo o una subcarpeta.
  4. Al mutar doc.Etiqueta[0] en el original, el clon permanece intacto.
--- Original (tras modificar doc) ---
📁 Proyecto/
   📄 informe.pdf (tags: [MODIFICADO oficial])
   📄 datos.csv (tags: [raw])
--- Clon independiente ---
📁 Proyecto_clon/
   📄 informe.pdf_copia (tags: [v1 oficial])
   📄 datos.csv_copia (tags: [raw])
🐹

Nota idiomática en Go

En Go, asignar un struct por valor (copia := *original) realiza una copia superficial (shallow copy): los campos slice, map o punteros seguirán apuntando a la misma memoria subyacente. Por eso un método Clonar() explícito con copy() o slices.Clone() es esencial.

Singleton

También llamado: Instancia única

🎯 Propósito

Garantiza que una estructura o clase tenga una única instancia en toda la ejecución del programa y proporciona un punto de acceso global y seguro a dicha instancia.

😟 Problema

El patrón Singleton aborda dos problemas a la vez:

  1. Garantizar una única instancia: recursos compartidos como un pool de base de datos, un registro de configuración o un sistema de archivos no deben instanciarse decenas de veces desperdiciando memoria o desincronizando el estado.
  2. Acceso global controlado: una variable global ordinaria permite acceder al objeto desde cualquier lugar, pero es peligrosa porque cualquier paquete podría sobrescribirla accidentalmente o provocar condiciones de carrera entre hilos/goroutines.

💡 Solución

Ocultar o restringir la construcción directa del tipo y exponer una función de acceso global (como ObtenerBD()) que actúa como único punto de entrada.

La primera vez que se invoca esta función, se crea el objeto de forma perezosa (lazy initialization) con bloqueo seguro para concurrencia y se guarda en una variable privada del paquete; todas las llamadas posteriores devuelven exactamente la misma referencia almacenada en caché.

🏛️

Analogía en el mundo real

El Gobierno oficial de un país es un Singleton natural: un país sólo puede tener un gobierno activo a la vez. Sin importar qué ciudadanos o instituciones interactúen con él, la figura "Gobierno de Colombia" funciona como el punto de acceso global que refiere siempre a la misma entidad institucional.

                                │ + ObtenerBD(): *ConexionBD       │
                                │ + Ejecutar(sql string)           │
                                └──────────────────────────────────┘

🔗 Relación con otros patrones

  • Una estructura Facade suele convertirse en Singleton porque un único objeto fachada basta en casi todos los casos.
  • A diferencia de Flyweight (que puede tener múltiples instancias inmutables con estado intrínseco distinto), Singleton tiene una sola instancia que suele ser mutable.
  • Abstract Factory, Builder y Prototype frecuentemente se implementan como Singletons.

🧩 Participantes

  1. Singleton (ConexionBD + ObtenerBD()): mantiene en variables privadas a nivel de paquete la referencia única (instancia) y el mecanismo de sincronización (sync.Once). La función pública ObtenerBD() garantiza que la inicialización ocurra una sola vez incluso ante miles de goroutines concurrentes.

🛠️ Cómo implementarlo

  1. Declara una variable privada en el paquete para guardar el puntero a la instancia única y un sync.Once.
  2. Escribe la función pública ObtenerInstancia() que inicializa el objeto dentro de once.Do(func() { ... }) y retorna la variable privada.
  3. Sustituye en el código cliente las creaciones directas por llamadas a ObtenerInstancia().

🧭 Aplicabilidad

  • Cuando un recurso del programa debe tener estrictamente una única instancia compartida por todos los componentes (p. ej. gestor de conexión a BD, logger centralizado, configuración en memoria).
  • Cuando necesitas reemplazar variables globales desprotegidas por un punto de acceso con inicialización diferida y protegida contra escritura externa.

✅ Pros

  • Certeza absoluta de tener una única instancia y un punto de acceso global conocido.
  • Se inicializa solo cuando se solicita por primera vez (lazy initialization).

❌ Contras

  • Vulnera el Principio de Responsabilidad Única (SRP) al resolver dos problemas a la vez.
  • Puede ocultar acoplamiento global excesivo y dificultar las pruebas unitarias (estado compartido entre tests).

Singleton en Go

package main

import (
	"fmt"
	"sync"
)

// 1. Estructura Singleton (no exportada o con inicialización controlada)
type ConexionBD struct {
	DSN       string
	Consultas int
}

var (
	instancia *ConexionBD
	once      sync.Once // garantiza ejecución única y segura entre goroutines
)

// ObtenerBD es el punto de acceso global al Singleton.
func ObtenerBD() *ConexionBD {
	once.Do(func() {
		fmt.Println("🔌 [sync.Once] Creando la ÚNICA conexión a la base de datos...")
		instancia = &ConexionBD{DSN: "postgres://localhost:5432/produccion"}
	})
	return instancia
}

func (db *ConexionBD) Ejecutar(sql string) {
	db.Consultas++
	fmt.Printf("   [Consulta #%d en %s] -> %s\n", db.Consultas, db.DSN, sql)
}

func main() {
	// Primera llamada: inicializa la instancia única
	bd1 := ObtenerBD()
	bd1.Ejecutar("SELECT * FROM usuarios")

	// Segunda llamada: reutiliza exactamente la misma instancia
	bd2 := ObtenerBD()
	bd2.Ejecutar("INSERT INTO logs VALUES ('login')")

	fmt.Printf("¿bd1 y bd2 apuntan al mismo objeto? %v (total consultas: %d)\n",
		bd1 == bd2, bd1.Consultas)
}

🔍 Explicación paso a paso

  1. instancia y once son variables privadas del paquete (minúscula inicial).
  2. ObtenerBD() envuelve la creación dentro de once.Do(...): la biblioteca estándar de Go garantiza con operaciones atómicas y mutex interno que esa función anónima se ejecute exactamente una vez, incluso si 1000 goroutines llaman a ObtenerBD() al mismo tiempo.
  3. bd1 == bd2 evalúa a true y el contador de consultas refleja que ambas variables apuntan a la misma dirección de memoria.
🔌 [sync.Once] Creando la ÚNICA conexión a la base de datos...
   [Consulta #1 en postgres://localhost:5432/produccion] -> SELECT * FROM usuarios
   [Consulta #2 en postgres://localhost:5432/produccion] -> INSERT INTO logs VALUES ('login')
¿bd1 y bd2 apuntan al mismo objeto? true (total consultas: 2)
🐹

Nota idiomática en Go

Olvídate del complejo patrón double-checked locking manual de Java/C++. En Go, sync.Once (o sync.OnceValue desde Go 1.21) es la forma estándar, ultrarrápida y 100% libre de condiciones de carrera para implementar un Singleton perezoso.
