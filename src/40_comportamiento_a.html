Chain of Responsibility

También llamado: Cadena de responsabilidad, CoR, Chain of Command

🎯 Propósito

Permite enviar solicitudes a lo largo de una cadena de manejadores potenciales. Al recibir una petición, cada eslabón decide si la procesa por su cuenta, si la bloquea o si la delega al siguiente manejador de la fila.

😟 Problema

Imagina un sistema de compras en línea que debe aplicar controles secuenciales antes de registrar un pedido: primero autenticar al usuario, luego verificar permisos de rol, sanear los datos de entrada, limitar intentos repetidos por IP (fuerza bruta) y consultar si ya existe respuesta en caché.

Si programas todas estas validaciones dentro de una sola función gigante llena de condicionales anidados, el código se vuelve rígido, frágil ante cambios y casi imposible de reutilizar parcialmente en otros módulos que solo requieran un subconjunto de controles.

💡 Solución

Extrae cada control en un objeto autónomo llamado manejador (handler) que implemente una interfaz común con un método de procesamiento y una referencia al siguiente eslabón.

Las peticiones recorren la cadena eslabón por eslabón: cada manejador ejecuta su verificación y decide si detiene el flujo (por ejemplo, cuando falla la autenticación o ya resolvió el evento GUI) o si pasa la solicitud al siguiente manejador, desacoplando al emisor de los receptores concretos.

☎️

Analogía en el mundo real

Cuando llamas al soporte técnico por un driver incompatible en Linux, tu llamada atraviesa una cadena de atención: primero responde un contestador automático con opciones pregrabadas; como ninguna aplica, te transfiere a un operador de primer nivel que lee respuestas estándar del manual; al no poder resolverlo, finalmente escala la llamada a un ingeniero especialista en el sótano de servidores, quien da con la solución exacta y cierra el caso.

Chain of Responsibility — Estructura

Arquitectura en eslabones, cuándo aplicarlo y evaluación del diseño

┌──────────────┐        ┌───────────────────────────────────┐
│ 4. Cliente   │───────▶│      <<interface>>                │
└──────────────┘        │     1. Manejador                  │
                        ├───────────────────────────────────┤
                        │ + EstablecerSiguiente(m)          │
                        │ + Manejar(solicitud)              │
                        └─────────────────△─────────────────┘
                                          │ implementa
                        ┌─────────────────┴─────────────────┐
                        │        2. ManejadorBase           │◇───┐
                        ├───────────────────────────────────┤    │ siguiente
                        │ - siguiente: Manejador            │◀───┘
                        ├───────────────────────────────────┤
                        │ + EstablecerSiguiente(m)          │
                        │ + PasarAlSiguiente(solicitud)     │
                        └─────────────────△─────────────────┘
                                          │ embebe
                        ┌─────────────────┴─────────────────┐
                        │     3. ManejadoresConcretos       │
                        ├───────────────────────────────────┤
                        │ + Manejar(solicitud):             │
                        │   si no cumple -> cortar          │
                        │   si cumple    -> PasarAlSiguiente│
                        └───────────────────────────────────┘
  1. Manejador (Interfaz): declara el contrato común para procesar peticiones y enlazar el siguiente eslabón.
  2. Manejador Base: estructura opcional que almacena la referencia al siguiente manejador e implementa el reenvío por defecto para ahorrar código repetitivo.
  3. Manejadores Concretos: contienen la regla de negocio real; deciden si procesan/detienen la solicitud o la delegan hacia adelante.
  4. Cliente: ensambla la cadena estática o dinámicamente y dispara la petición hacia el primer eslabón (o cualquiera de la cadena).

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando debas procesar distintas solicitudes sin conocer de antemano qué eslabón las atenderá, cuando sea obligatorio ejecutar filtros en un orden estricto, o cuando la tubería de manejadores deba reconfigurarse en tiempo de ejecución.
  • Paso 1: Define la interfaz Manejador y encapsula los datos de entrada en un struct Solicitud.
  • Paso 2: Crea un ManejadorBase con el campo siguiente y un método auxiliar para delegar si siguiente != nil.
  • Paso 3: Implementa cada manejador concreto decidiendo si corta la ejecución o invoca al siguiente, y conecta los eslabones desde el cliente.

Pros

  • Control total sobre el orden de ejecución de las validaciones.
  • Cumple SRP: desacopla quien inicia la petición de quien la valida o procesa.
  • Cumple OCP: puedes insertar nuevos filtros sin modificar los existentes.

Contras

  • Algunas solicitudes pueden recorrer toda la cadena y terminar sin que ningún eslabón las procese.
  • Rastrear el flujo en cadenas muy largas puede requerir depuración cuidadosa.

🔗 Relación con otros patrones

Suele combinarse con Composite (los eventos suben desde una hoja hacia sus contenedores padres), con Command (representando cada solicitud como comando), y se parece estructuralmente a Decorator, con la diferencia clave de que cualquier eslabón de CoR puede cortar el flujo libremente.

Chain of Responsibility en Go

Pipeline de seguridad y validación de pedidos con composición de structs

package main

import "fmt"

// Solicitud contiene los datos que viajan a lo largo de la cadena.
type Solicitud struct {
	Usuario     string
	Autenticado bool
	Intentos    int
	Datos       string
}

// 1. Manejador (interfaz común a todos los eslabones)
type Manejador interface {
	EstablecerSiguiente(m Manejador) Manejador
	Manejar(s *Solicitud)
}

// 2. ManejadorBase (evita duplicar el enlace al siguiente eslabón)
type ManejadorBase struct {
	siguiente Manejador
}

func (b *ManejadorBase) EstablecerSiguiente(m Manejador) Manejador {
	b.siguiente = m
	return m
}

func (b *ManejadorBase) PasarAlSiguiente(s *Solicitud) {
	if b.siguiente != nil {
		b.siguiente.Manejar(s)
	}
}

// 3a. Manejador Concreto: protege contra fuerza bruta
type FiltroFuerzaBruta struct{ ManejadorBase }

func (f *FiltroFuerzaBruta) Manejar(s *Solicitud) {
	if s.Intentos >= 3 {
		fmt.Printf("  [FuerzaBruta] ✘ IP bloqueada para %q (%d intentos fallidos)\n", s.Usuario, s.Intentos)
		return // Corta la cadena
	}
	fmt.Println("  [FuerzaBruta] ✔ Intentos dentro del límite")
	f.PasarAlSiguiente(s)
}

// 3b. Manejador Concreto: verifica credenciales
type FiltroAutenticacion struct{ ManejadorBase }

func (a *FiltroAutenticacion) Manejar(s *Solicitud) {
	if !s.Autenticado {
		fmt.Printf("  [Autenticación] ✘ Acceso denegado a %q: sesión no iniciada\n", s.Usuario)
		return // Corta la cadena
	}
	fmt.Printf("  [Autenticación] ✔ Usuario %q autenticado\n", s.Usuario)
	a.PasarAlSiguiente(s)
}

// 3c. Manejador Concreto: valida y sanea el payload
type FiltroValidacion struct{ ManejadorBase }

func (v *FiltroValidacion) Manejar(s *Solicitud) {
	if s.Datos == "" {
		fmt.Println("  [Validación] ✘ Solicitud rechazada: datos del pedido vacíos")
		return
	}
	fmt.Println("  [Validación] ✔ Datos del pedido saneados")
	v.PasarAlSiguiente(s)
}

// 3d. Manejador Concreto final: procesa el pedido
type ProcesadorPedidos struct{ ManejadorBase }

func (p *ProcesadorPedidos) Manejar(s *Solicitud) {
	fmt.Printf("  [Pedidos] 🎉 Pedido procesado con éxito para %q: %s\n", s.Usuario, s.Datos)
}

func main() {
	// 4. Cliente: ensambla la cadena de responsabilidad
	fuerzaBruta := &FiltroFuerzaBruta{}
	autenticacion := &FiltroAutenticacion{}
	validacion := &FiltroValidacion{}
	procesador := &ProcesadorPedidos{}

	fuerzaBruta.EstablecerSiguiente(autenticacion).
		EstablecerSiguiente(validacion).
		EstablecerSiguiente(procesador)

	casos := []*Solicitud{
		{Usuario: "atacante", Autenticado: false, Intentos: 5, Datos: "2x Laptop"},
		{Usuario: "invitado", Autenticado: false, Intentos: 1, Datos: "1x Teclado"},
		{Usuario: "ana", Autenticado: true, Intentos: 0, Datos: "1x Monitor 4K"},
	}

	for i, req := range casos {
		fmt.Printf("Solicitud #%d (usuario=%q):\n", i+1, req.Usuario)
		fuerzaBruta.Manejar(req)
	}
}

🔍 Explicación paso a paso

  1. ManejadorBase guarda el puntero siguiente y devuelve el manejador recibido en EstablecerSiguiente para permitir encadenamiento fluido.
  2. Cada filtro concreto (FiltroFuerzaBruta, FiltroAutenticacion, FiltroValidacion) embebe ManejadorBase para heredar la lógica de enlace sin usar herencia de clases.
  3. Si una regla falla, el manejador hace return inmediato cortando la cadena; si aprueba, invoca PasarAlSiguiente(s).
Solicitud #1 (usuario="atacante"):
  [FuerzaBruta] ✘ IP bloqueada para "atacante" (5 intentos fallidos)
Solicitud #2 (usuario="invitado"):
  [FuerzaBruta] ✔ Intentos dentro del límite
  [Autenticación] ✘ Acceso denegado a "invitado": sesión no iniciada
Solicitud #3 (usuario="ana"):
  [FuerzaBruta] ✔ Intentos dentro del límite
  [Autenticación] ✔ Usuario "ana" autenticado
  [Validación] ✔ Datos del pedido saneados
  [Pedidos] 🎉 Pedido procesado con éxito para "ana": 1x Monitor 4K
🐹

Nota idiomática en Go

En lugar de clases abstractas, en Go embebemos el struct ManejadorBase en cada manejador concreto. Además, este patrón es la base de los middlewares HTTP en la librería estándar (func(http.Handler) http.Handler).

Command

También llamado: Comando, Orden, Action, Transaction

🎯 Propósito

Convierte una solicitud o acción en un objeto independiente que encapsula toda la información necesaria para ejecutarla (el receptor, el método y sus argumentos), permitiendo parametrizar invocadores, encolar o diferir tareas y soportar operaciones reversibles (deshacer/rehacer).

😟 Problema

Supón que construyes un editor de texto con una barra de herramientas, menús contextuales y atajos de teclado. Si colocas la lógica de negocio (copiar, cortar, pegar) dentro de subclases como BotonCopiar, acoplas la interfaz gráfica directamente a la lógica de negocio.

Peor aún: cuando quieras activar la misma operación desde el menú contextual o con Ctrl+C, tendrás que duplicar el código en múltiples componentes o forzar a que los menús dependan de los botones.

💡 Solución

Separa por completo la capa que inicia la acción (Emisor / Invocador) de la capa que sabe cómo hacer el trabajo (Receptor) extrayendo cada petición en un objeto Comando que implementa una interfaz con un método Ejecutar().

El botón, menú o atajo solo guarda una referencia a la interfaz Comando y la dispara sin saber qué receptor actúa por detrás. Además, puedes apilar los comandos ejecutados en un historial para revertir sus efectos cuando el usuario pulse Ctrl+Z.

🍽️

Analogía en el mundo real

En un restaurante, el camarero (Invocador) toma tu orden y la escribe en una comanda de papel (Comando). Luego coloca ese papel en la fila de la cocina. El chef (Receptor) lee la comanda cuando tiene turno y cocina el plato porque el papel ya contiene todos los detalles necesarios, sin que el cliente tenga que entrar a hablar directamente con el cocinero.

Command — Estructura

Desacoplamiento entre emisores, comandos empaquetados y receptores

┌──────────────────┐       ┌──────────────────────────┐
│ 1. Emisor / App  │──────▶│      <<interface>>       │
├──────────────────┤       │       2. Comando         │
│ - historial      │       ├──────────────────────────┤
│ + EjecutarCmd(c) │       │ + Ejecutar(): bool       │
│ + Deshacer()     │       │ + Deshacer()             │
└──────────────────┘       └────────────△─────────────┘
                                        │ implementa
┌──────────────────┐       ┌────────────┴─────────────┐
│   5. Cliente     │──────▶│   3. ComandoConcreto     │
└────────┬─────────┘       ├──────────────────────────┤
         │                 │ - receptor: *Receptor    │
         │ configura       │ - args / estadoPrevio    │
         ▼                 ├──────────────────────────┤
┌──────────────────┐       │ + Ejecutar()             │
│   4. Receptor    │◀──────│ + Deshacer()             │
├──────────────────┤llama a└──────────────────────────┘
│ + Accion(args)   │
└──────────────────┘
  1. Emisor (Invocador): inicia la solicitud llamando al comando asignado (sin conocer al receptor) y puede registrar el historial de comandos.
  2. Comando (Interfaz): declara el método único de ejecución (y opcionalmente Deshacer()).
  3. Comandos Concretos: guardan la referencia al receptor, los argumentos de la operación y el respaldo necesario para deshacerla.
  4. Receptor: objeto de dominio que contiene la lógica real de negocio (p. ej. el EditorTexto).
  5. Cliente: instancia el receptor, crea los comandos concretos inyectándoles los parámetros y los asocia al invocador.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: para parametrizar objetos UI con acciones intercambiables, para encolar/programar tareas o enviarlas por red (serializando el comando), y para implementar deshacer/rehacer mediante un historial.
  • Paso 1: Declara la interfaz Comando con su método Ejecutar().
  • Paso 2: Crea structs de comando concretos que almacenen al receptor y los argumentos de la llamada.
  • Paso 3: Haz que el invocador reciba y dispare la interfaz Comando en vez de llamar directamente al receptor.

Pros

  • Cumple SRP y OCP: separa quien invoca de quien ejecuta y permite añadir comandos sin romper clases existentes.
  • Facilita implementar undo/redo, ejecución diferida, colas de trabajo y comandos compuestos (macros).

Contras

  • Introduce una capa adicional de structs e interfaces entre los emisores y los receptores.

🔗 Relación con otros patrones

Se combina con Memento para guardar instantáneas antes de ejecutar un comando reversible; a diferencia de Strategy (que cambia cómo se hace una tarea), Command convierte cualquier acción y sus argumentos en un objeto ejecutable.

🧠 Comportamiento 3 / 3 · Go

Command en Go

Editor de texto con comandos parametrizados e historial de reversión (Ctrl+Z)

package main

import "fmt"

// 2. Comando (interfaz con método de ejecución y reversión)
type Comando interface {
	Ejecutar() bool
	Deshacer()
	Nombre() string
}

// 4. Receptor: contiene la lógica de negocio real
type EditorTexto struct {
	Texto string
}

func (e *EditorTexto) Agregar(fragmento string) { e.Texto += fragmento }
func (e *EditorTexto) BorrarUltimos(n int) {
	if n > len(e.Texto) {
		n = len(e.Texto)
	}
	e.Texto = e.Texto[:len(e.Texto)-n]
}

// 3a. Comando Concreto: insertar texto
type ComandoEscribir struct {
	editorRespaldo *EditorTexto
	nuevoTexto     string
	estadoPrevio   string
}

func (c *ComandoEscribir) Ejecutar() bool {
	c.estadoPrevio = c.editorRespaldo.Texto
	c.editorRespaldo.Agregar(c.nuevoTexto)
	return true // modifica el estado -> guardar en historial
}

func (c *ComandoEscribir) Deshacer()      { c.editorRespaldo.Texto = c.estadoPrevio }
func (c *ComandoEscribir) Nombre() string { return "Escribir(" + c.nuevoTexto + ")" }

// 3b. Comando Concreto: borrar los últimos N caracteres
type ComandoBorrar struct {
	editor       *EditorTexto
	cantidad     int
	estadoPrevio string
}

func (c *ComandoBorrar) Ejecutar() bool {
	c.estadoPrevio = c.editor.Texto
	c.editor.BorrarUltimos(c.cantidad)
	return true
}

func (c *ComandoBorrar) Deshacer()      { c.editor.Texto = c.estadoPrevio }
func (c *ComandoBorrar) Nombre() string { return fmt.Sprintf("Borrar(%d)", c.cantidad) }

// 1. Emisor / Invocador: dispara comandos y administra la pila de historial
type Aplicacion struct {
	historial []Comando
}

func (a *Aplicacion) EjecutarComando(c Comando) {
	if c.Ejecutar() {
		a.historial = append(a.historial, c)
	}
	fmt.Printf("  ▶ Ejecutado %-20s →", c.Nombre())
}

func (a *Aplicacion) DeshacerUltimo() {
	if len(a.historial) == 0 {
		return
	}
	ultimo := a.historial[len(a.historial)-1]
	a.historial = a.historial[:len(a.historial)-1]
	ultimo.Deshacer()
	fmt.Printf("  ⮌ Deshecho  %-20s →", ultimo.Nombre())
}

func main() {
	// 5. Cliente: crea el receptor, los comandos y el invocador
	editor := &EditorTexto{}
	app := &Aplicacion{}

	pasos := []Comando{
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Hola "},
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Mundo"},
		&ComandoBorrar{editor: editor, cantidad: 5},
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Patrones en Go!"},
	}

	for _, cmd := range pasos {
		app.EjecutarComando(cmd)
		fmt.Printf(" %q\n", editor.Texto)
	}

	fmt.Println("\nRevirtiendo las últimas 2 operaciones (Ctrl+Z):")
	app.DeshacerUltimo()
	fmt.Printf(" %q\n", editor.Texto)
	app.DeshacerUltimo()
	fmt.Printf(" %q\n", editor.Texto)
}

🔍 Explicación paso a paso

  1. EditorTexto actúa como Receptor: expone operaciones primitivas sobre el texto sin preocuparse por botones ni historiales.
  2. ComandoEscribir y ComandoBorrar guardan una copia de seguridad en estadoPrevio justo antes de mutar al receptor.
  3. Aplicacion apila cada comando ejecutado en un slice []Comando y desapila en orden LIFO cuando se llama a DeshacerUltimo().
  ▶ Ejecutado Escribir(Hola )      → "Hola "
  ▶ Ejecutado Escribir(Mundo)      → "Hola Mundo"
  ▶ Ejecutado Borrar(5)            → "Hola "
  ▶ Ejecutado Escribir(Patrones en Go!) → "Hola Patrones en Go!"

Revirtiendo las últimas 2 operaciones (Ctrl+Z):
  ⮌ Deshecho  Escribir(Patrones en Go!) → "Hola "
  ⮌ Deshecho  Borrar(5)            → "Hola Mundo"
🐹

Nota idiomática en Go

Cuando no necesitas método Deshacer() ni metadatos adicionales, en Go un comando suele representarse directamente como una función clausura (type Comando func() error), capturando al receptor y sus argumentos en el closure.

Iterator

También llamado: Iterador

🎯 Propósito

Permite recorrer secuencialmente los elementos de una colección compleja sin exponer su representación interna subyacente (ya sea un arreglo, lista enlazada, pila, árbol o grafo).

😟 Problema

Las colecciones almacenan datos en estructuras muy diversas: listas simples, árboles binarios o grafos. Incluso sobre un mismo árbol o grafo, un día necesitas un recorrido en profundidad (DFS), al siguiente en anchura (BFS) y luego un recorrido filtrado.

Si metes todos esos algoritmos de recorrido dentro de la propia colección, contaminas su responsabilidad principal (almacenar datos eficientemente). Además, el cliente quedaría acoplado a los detalles internos de cada estructura para poder iterarla.

💡 Solución

Extrae la lógica y el estado del recorrido hacia un objeto independiente llamado iterador. Este objeto lleva la cuenta de la posición actual y de qué elementos faltan por visitar.

Como cada iterador mantiene su propio cursor de avance, múltiples iteradores pueden recorrer la misma colección en paralelo sin interferirse. Y como todos implementan la misma interfaz, el cliente puede cambiar de algoritmo de recorrido sin tocar su propio bucle.

🗺️

Analogía en el mundo real

Imagina que visitas Roma: la ciudad con todos sus monumentos es la Colección. Puedes recorrerla caminando al azar por tu cuenta, usando una app GPS turística en tu teléfono o contratando a un guía local experto en historia. Los tres actúan como iteradores distintos sobre la misma colección de atracciones, cada uno con su propio orden y criterio sin cambiar la ciudad.

🧠 Comportamiento 2 / 3 · Estructura

Iterator — Estructura

Separación entre el contenedor de datos y el estado del cursor de recorrido

┌────────────────────────────┐         ┌────────────────────────┐
│       <<interface>>        │         │     <<interface>>      │
│       3. Colección         │────────▶│      1. Iterador       │
├────────────────────────────┤  crea   ├────────────────────────┤
│ + CrearIterador(): Iterador│         │ + HayMas(): bool       │
└─────────────△──────────────┘         │ + Siguiente(): Elem    │
              │                        └───────────△────────────┘
              │ implementa                         │ implementa
┌─────────────┴──────────────┐         ┌───────────┴────────────┐
│   4. ColecciónConcreta     │◀────────│  2. IteradorConcreto   │
├────────────────────────────┤referencia├────────────────────────┤
│ - datosInternos            │         │ - coleccion            │
│ + CrearIterador()          │         │ - posicionActual: int  │
└────────────────────────────┘         └────────────────────────┘
              ▲                                    ▲
              └──────────┬─────────────────────────┘
                   ┌─────┴──────┐
                   │ 5. Cliente │
                   └────────────┘
  1. Iterador (Interfaz): declara las operaciones esenciales de avance: consultar si quedan elementos (HayMas()) y obtener el siguiente (Siguiente()).
  2. Iterador Concreto: implementa un algoritmo específico de recorrido y guarda su propio estado de progreso (índice, pila de nodos o caché).
  3. Colección (Interfaz): declara uno o más métodos fábrica que devuelven iteradores compatibles usando la interfaz abstracta.
  4. Colección Concreta: almacena los elementos y crea instancias del iterador concreto pasándose a sí misma como referencia.
  5. Cliente: consume tanto la colección como el iterador a través de sus interfaces, sin conocer la estructura interna de datos.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando quieras ocultar la complejidad interna de una estructura de datos, evitar duplicar lógica de recorrido por toda la aplicación, o recorrer colecciones heterogéneas bajo un contrato uniforme.
  • Paso 1: Declara la interfaz Iterador con al menos HayMas() y Siguiente().
  • Paso 2: Declara la interfaz Coleccion con métodos que fabriquen iteradores.
  • Paso 3: Implementa cada iterador concreto vinculándolo a la colección y sustituye los bucles acoplados del cliente por llamadas al iterador.

Pros

  • Cumple SRP y OCP: aísla algoritmos de recorrido complejos y permite agregar nuevas vistas sin modificar la colección.
  • Permite recorridos simultáneos e independientes sobre la misma colección y pausar/reanudar la iteración.

Contras

  • Puede ser excesivo si la aplicación solo recorre slices o listas simples de forma directa.

🔗 Relación con otros patrones

Se usa frecuentemente para recorrer árboles Composite, emplea Factory Method en las colecciones para instanciar el iterador adecuado, y puede apoyarse en Memento o Visitor durante el recorrido.

Iterator en Go

Iterador clásico con interfaz frente a iteradores nativos con iter.Seq (Go 1.23+)

package main

import (
	"fmt"
	"iter"
)

type Libro struct {
	Titulo string
	Tema   string
}

// 1. Iterador (interfaz común para recorrer elementos)
type Iterador interface {
	HayMas() bool
	Siguiente() Libro
}

// 3. Colección (interfaz que fabrica iteradores)
type ColeccionLibros interface {
	CrearIteradorPorTema(tema string) Iterador
}

// 4. Colección Concreta
type Biblioteca struct {
	libros []Libro
}

func (b *Biblioteca) Agregar(l Libro) { b.libros = append(b.libros, l) }

func (b *Biblioteca) CrearIteradorPorTema(tema string) Iterador {
	return &IteradorPorTema{biblio: b, tema: tema, posicion: 0}
}

// Método idiomático en Go 1.23+: iterador funcional compatible con for-range
func (b *Biblioteca) TodosEnOrdenInverso() iter.Seq[Libro] {
	return func(yield func(Libro) bool) {
		for i := len(b.libros) - 1; i >= 0; i-- {
			if !yield(b.libros[i]) {
				return
			}
		}
	}
}

// 2. Iterador Concreto: guarda su propio cursor de recorrido
type IteradorPorTema struct {
	biblio   *Biblioteca
	tema     string
	posicion int
}

func (it *IteradorPorTema) HayMas() bool {
	for it.posicion < len(it.biblio.libros) {
		if it.biblio.libros[it.posicion].Tema == it.tema {
			return true
		}
		it.posicion++
	}
	return false
}

func (it *IteradorPorTema) Siguiente() Libro {
	libro := it.biblio.libros[it.posicion]
	it.posicion++
	return libro
}

func main() {
	// 5. Cliente: usa la interfaz Iterador sin conocer el slice interno
	biblio := &Biblioteca{}
	biblio.Agregar(Libro{Titulo: "Diseño de Compiladores", Tema: "Sistemas"})
	biblio.Agregar(Libro{Titulo: "Patrones de Diseño GoF", Tema: "Arquitectura"})
	biblio.Agregar(Libro{Titulo: "El Lenguaje Go", Tema: "Sistemas"})
	biblio.Agregar(Libro{Titulo: "Arquitectura Limpia", Tema: "Arquitectura"})

	fmt.Println("Recorrido con Iterador clásico (Tema = Sistemas):")
	it := biblio.CrearIteradorPorTema("Sistemas")
	for it.HayMas() {
		l := it.Siguiente()
		fmt.Printf("  📖 %s [%s]\n", l.Titulo, l.Tema)
	}

	fmt.Println("\nRecorrido con iter.Seq de Go 1.23+ (orden inverso):")
	for l := range biblio.TodosEnOrdenInverso() {
		fmt.Printf("  🔄 %s [%s]\n", l.Titulo, l.Tema)
	}
}

🔍 Explicación paso a paso

  1. Biblioteca encapsula el slice privado libros y ofrece dos formas de recorrerlo sin exponerlo.
  2. IteradorPorTema implementa el patrón GoF clásico: mantiene su índice posicion y salta los libros que no coincidan con el tema buscado.
  3. TodosEnOrdenInverso() devuelve un iter.Seq[Libro] que empuja cada elemento a la función yield dentro de un for ... range nativo.
Recorrido con Iterador clásico (Tema = Sistemas):
  📖 Diseño de Compiladores [Sistemas]
  📖 El Lenguaje Go [Sistemas]

Recorrido con iter.Seq de Go 1.23+ (orden inverso):
  🔄 Arquitectura Limpia [Arquitectura]
  🔄 El Lenguaje Go [Sistemas]
  🔄 Patrones de Diseño GoF [Arquitectura]
  🔄 Diseño de Compiladores [Sistemas]
🐹

Iteradores en Go: de Next() a iter.Seq

En la librería estándar verás el estilo pull en bufio.Scanner o sql.Rows (for rows.Next()). Desde Go 1.23+ existen los iteradores range-over-func con el paquete iter (iter.Seq[V] e iter.Seq2[K, V]), que integran el patrón directamente con el bucle for v := range col.All().

Mediator

También llamado: Mediador, Intermediary, Controller

🎯 Propósito

Reduce las dependencias caóticas (todos contra todos) entre objetos. Restringe la comunicación directa entre los componentes y los fuerza a colaborar únicamente a través de un objeto mediador central.

😟 Problema

Imagina un formulario complejo de perfil de usuario donde marcar la casilla "Tengo mascota" muestra un campo oculto, cambiar el país recarga la lista de ciudades y el botón "Guardar" valida una docena de controles distintos.

Si cada control conoce y llama directamente a los demás componentes, se forma una telaraña de dependencias cruzadas: modificar un componente rompe los otros y resulta imposible reutilizar un botón o casilla en otra ventana de la aplicación.

💡 Solución

Corta toda comunicación directa entre los componentes y haz que cada uno conozca únicamente la interfaz de un Mediador.

Cuando ocurre un evento en un componente (por ejemplo, un clic o una solicitud de recurso), este simplemente notifica al mediador. El mediador encapsula toda la coordinación y decide qué otros componentes deben reaccionar, transformando una red caótica muchos-a-muchos en una estrella limpia uno-a-muchos.

🗼

Analogía en el mundo real

Los pilotos de decenas de aviones que se aproximan a un aeropuerto no negocian entre sí por radio quién aterriza primero (lo que causaría un caos aéreo). En su lugar, todos se comunican exclusivamente con la torre de control de tráfico aéreo (el Mediador), que conoce el estado de la pista y coordina el orden de aterrizaje y despegue de forma segura.

│       <<interface>>         │         │       <<interface>>         │
│        2. Mediador          │◀────────│       1. Componente         │

└──────────────△──────────────┘         └──────────────△──────────────┘
               │ implementa                            │ implementa
┌──────────────┴──────────────┐         ┌──────────────┴──────────────┐
│     3. MediadorConcreto     │────────▶│    4. ComponenteConcreto    │
│       (TorreControl)        │coordina │          (Avion)            │
├─────────────────────────────┤         ├─────────────────────────────┤
│ - pistaLibre: bool          │         │ - codigo: string            │
│ - colaEspera: []Aeronave    │         │ - torre: Mediador           │
└─────────────────────────────┘         └─────────────────────────────┘
  1. Componentes: clases o structs con lógica de dominio que guardan una referencia a la interfaz del mediador sin saber qué concreto hay detrás.
  2. Mediador (Interfaz): declara los métodos de notificación mediante los cuales los componentes informan cualquier evento relevante.
  3. Mediador Concreto: encapsula las reglas de coordinación, mantiene referencias a los componentes administrados y redirige las acciones.
  4. Aislamiento entre colegas: los componentes concretos jamás se referencian entre sí; para cada uno, el resto del sistema es una caja negra detrás del mediador.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando un grupo de clases esté tan acoplado que sea difícil modificarlo, cuando no puedas reutilizar un componente porque arrastra dependencias hacia muchos colegas, o para evitar crear decenas de subclases solo para variar cómo colaboran.
  • Paso 1: Identifica el grupo de componentes acoplados y declara la interfaz Mediador con su protocolo de notificación.
  • Paso 2: Implementa el mediador concreto que guarde las referencias o colas de coordinación entre componentes.
  • Paso 3: Inyecta la interfaz mediadora al construir cada componente y reemplaza las llamadas directas entre colegas por notificaciones al mediador.

Pros

  • Cumple SRP: concentra la lógica de comunicación en un solo lugar fácil de auditar.
  • Cumple OCP: puedes cambiar las reglas de colaboración creando otro mediador sin tocar los componentes.
  • Reduce drásticamente el acoplamiento y facilita reutilizar componentes individuales.

Contras

  • Con el tiempo, el mediador puede acumular demasiadas responsabilidades y convertirse en un Objeto Todopoderoso (God Object).

🔗 Relación con otros patrones

A diferencia de Facade (que solo simplifica la interfaz hacia un subsistema sin que los objetos internos la conozcan), en Mediator los componentes conocen al mediador y colaboran bidireccionalmente; además, suele apoyarse en Observer para recibir eventos.

Mediator en Go

Torre de control de tráfico aéreo coordinando aterrizajes y cola de espera

package main

import "fmt"

// 2. Mediador (interfaz de comunicación centralizada)
type MediadorTorre interface {
	SolicitarPista(a Aeronave) bool
	NotificarDespegue(a Aeronave)
}

// 1. Componente (interfaz de las aeronaves que colaboran sin conocerse)
type Aeronave interface {
	Identificador() string
	Aterrizar()
	Despegar()
	PermitirAterrizaje()
}

// 3. Mediador Concreto: coordina la pista y la cola de espera
type TorreControl struct {
	pistaLibre bool
	colaEspera []Aeronave
}

func NuevaTorreControl() *TorreControl {
	return &TorreControl{pistaLibre: true}
}

func (t *TorreControl) SolicitarPista(a Aeronave) bool {
	if t.pistaLibre {
		t.pistaLibre = false
		return true
	}
	t.colaEspera = append(t.colaEspera, a)
	return false
}

func (t *TorreControl) NotificarDespegue(a Aeronave) {
	if len(t.colaEspera) > 0 {
		siguiente := t.colaEspera[0]
		t.colaEspera = t.colaEspera[1:]
		siguiente.PermitirAterrizaje()
	} else {
		t.pistaLibre = true
	}
}

// 4. Componente Concreto: solo se comunica con el mediador
type Avion struct {
	codigo string
	torre  MediadorTorre
}

func (av *Avion) Identificador() string { return av.codigo }

func (av *Avion) Aterrizar() {
	if av.torre.SolicitarPista(av) {
		fmt.Printf("  ✈️  [%s] Pista asignada → aterrizando ahora\n", av.codigo)
	} else {
		fmt.Printf("  ⏳ [%s] Pista ocupada → esperando turno en el aire\n", av.codigo)
	}
}

func (av *Avion) Despegar() {
	fmt.Printf("  🛫 [%s] Ha liberado la pista → notificando a la torre\n", av.codigo)
	av.torre.NotificarDespegue(av)
}

func (av *Avion) PermitirAterrizaje() {
	fmt.Printf("  🗼 [Torre → %s] Pista libre, autorizado para aterrizar\n", av.codigo)
	fmt.Printf("  ✈️  [%s] Aterrizando tras espera\n", av.codigo)
}

func main() {
	torre := NuevaTorreControl()
	vuelo1 := &Avion{codigo: "AV-101", torre: torre}
	vuelo2 := &Avion{codigo: "LA-205", torre: torre}
	vuelo3 := &Avion{codigo: "CM-309", torre: torre}

	vuelo1.Aterrizar()
	vuelo2.Aterrizar()
	vuelo3.Aterrizar()
	fmt.Println()
	vuelo1.Despegar()
	vuelo2.Despegar()
}

🔍 Explicación paso a paso

  1. Ningún Avion guarda referencias a otros aviones; su único campo de enlace es la interfaz MediadorTorre.
  2. Cuando vuelo2 y vuelo3 intentan aterrizar mientras la pista está ocupada por vuelo1, la TorreControl los encola en colaEspera.
  3. Al despegar un avión, este invoca NotificarDespegue y el mediador autoriza automáticamente al siguiente vuelo en espera.
  ✈️  [AV-101] Pista asignada → aterrizando ahora
  ⏳ [LA-205] Pista ocupada → esperando turno en el aire
  ⏳ [CM-309] Pista ocupada → esperando turno en el aire

  🛫 [AV-101] Ha liberado la pista → notificando a la torre
  🗼 [Torre → LA-205] Pista libre, autorizado para aterrizar
  ✈️  [LA-205] Aterrizando tras espera
  🛫 [LA-205] Ha liberado la pista → notificando a la torre
  🗼 [Torre → CM-309] Pista libre, autorizado para aterrizar
  ✈️  [CM-309] Aterrizando tras espera

Memento

También llamado: Recuerdo, Instantánea, Snapshot

🎯 Propósito

Permite capturar, externalizar y restaurar el estado interno previo de un objeto sin violar su encapsulación ni revelar los detalles privados de su implementación.

😟 Problema

Quieres implementar la función "Deshacer" o puntos de control transaccionales en un editor que maneja texto, posición del cursor, selección y estilos. Si un objeto externo intenta hacer la copia de seguridad leyendo campo por campo, chocará con los atributos privados del editor.

Si decides volver públicos todos los campos internos del editor y de la copia de seguridad para que cualquiera los lea o escriba, rompes por completo la encapsulación y acoplas el historial a cada cambio interno del editor.

💡 Solución

Delega la creación de la instantánea al propio dueño del estado: el objeto Originador. Este empaqueta una copia de sus campos privados dentro de un objeto inmutable llamado Memento.

Otro objeto llamado Cuidador (Caretaker, p. ej. el historial) almacena la pila de mementos, pero solo puede ver sus metadatos públicos (fecha, etiqueta) sin poder leer ni alterar el estado interno guardado. Cuando hay que revertir, el cuidador devuelve el memento al originador para que se restaure a sí mismo.

💾

Analogía en el mundo real

Piensa en los puntos de guardado (savegames) de un videojuego: el motor de la partida (Originador) empaqueta la vida, inventario y coordenadas exactas del jugador en una ranura de guardado sellada (Memento). El menú de partidas guardadas (Cuidador) te muestra la lista con la hora y el nombre del nivel para que elijas cuál cargar, pero el menú no modifica las estadísticas internas del archivo.

Memento — Estructura

Encapsulación estricta entre Originador, Instantánea inmutable y Cuidador

┌───────────────────────────┐        ┌───────────────────────────┐
│      1. Originador        │───────▶│        2. Memento         │
│         (Editor)          │  crea  │       (Instantánea)       │
├───────────────────────────┤        ├───────────────────────────┤
│ - texto: string           │        │ - etiqueta: string        │
│ - cursor: int             │        │ - texto: string (privado) │
├───────────────────────────┤        │ - cursor: int   (privado) │
│ + Guardar(): *Memento     │        ├───────────────────────────┤
│ + Restaurar(m: *Memento)  │        │ + Etiqueta(): string      │
└───────────────────────────┘        └─────────────▲─────────────┘
              ▲                                    │
              │ pide Guardar /                     │ almacena pila
              │ pasa a Restaurar                   │ (sin ver estado)
              └──────────────┬─────────────────────┘
                     ┌───────┴───────────────────┐
                     │       3. Cuidador         │
                     │       (Historial)         │
                     ├───────────────────────────┤
                     │ - instantaneas: []*Memento│
                     ├───────────────────────────┤
                     │ + Registrar(m)            │
                     │ + ExtraerUltima():*Memento│
                     └───────────────────────────┘
  1. Originador: objeto cuyo estado cambia con el tiempo; sabe crear instantáneas de sus propios campos y restaurarse a partir de ellas.
  2. Memento: objeto de valor inmutable que guarda el estado capturado; oculta los datos internos a todos excepto al originador y solo expone metadatos seguros (como nombre o fecha).
  3. Cuidador (Caretaker): administra cuándo capturar y cuándo restaurar el estado manteniendo una pila de mementos, sin inspeccionar ni mutar su contenido interno.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando necesites producir instantáneas para deshacer operaciones o hacer rollback ante errores transaccionales, y cuando exponer getters/setters directos del estado interno violaría la encapsulación del objeto.
  • Paso 1: Identifica la clase originadora y crea el struct Memento con campos privados que reflejen el estado del originador.
  • Paso 2: Haz que el memento sea inmutable (inicializado solo al crearse, sin setters) y expón únicamente métodos de metadatos.
  • Paso 3: Añade Guardar() y Restaurar(m) en el originador y haz que el Cuidador gestione la pila de mementos.

Pros

  • Captura copias de seguridad completas sin romper la encapsulación de los campos privados.
  • Simplifica al originador delegando la gestión del historial al cuidador.

Contras

  • Puede consumir bastante memoria RAM si se crean instantáneas de objetos grandes con demasiada frecuencia.

🔗 Relación con otros patrones

Trabaja de la mano con Command para implementar undo/redo (el comando ejecuta la acción y guarda un memento previo), con Iterator para congelar el estado de un recorrido, y tiene a Prototype como alternativa cuando el objeto es simple de clonar.

Memento en Go

Puntos de control inmutables y restauración segura del estado de un editor

package main

import "fmt"

// 1. Originador: objeto cuyo estado interno queremos salvaguardar
type Editor struct {
	texto  string
	cursor int
}

func (e *Editor) Escribir(fragmento string) {
	e.texto += fragmento
	e.cursor = len(e.texto)
}

func (e *Editor) Mostrar() string {
	return fmt.Sprintf("texto=%q (cursor=%d)", e.texto, e.cursor)
}

// Crea una instantánea inmutable de su estado actual
func (e *Editor) Guardar(etiqueta string) *Memento {
	return &Memento{
		etiqueta: etiqueta,
		texto:    e.texto,
		cursor:   e.cursor,
	}
}

// Restaura su estado interno a partir de un memento
func (e *Editor) Restaurar(m *Memento) {
	if m == nil {
		return
	}
	e.texto = m.texto
	e.cursor = m.cursor
}

// 2. Memento: almacena el estado del originador en campos privados
type Memento struct {
	etiqueta string
	texto    string
	cursor   int
}

// El cuidador solo puede consultar metadatos públicos, nunca alterar el estado
func (m *Memento) Etiqueta() string { return m.etiqueta }

// 3. Cuidador (Caretaker): administra la pila de instantáneas
type Historial struct {
	instantaneas []*Memento
}

func (h *Historial) Registrar(m *Memento) {
	fmt.Printf("  💾 Guardada instantánea [%s]\n", m.Etiqueta())
	h.instantaneas = append(h.instantaneas, m)
}

func (h *Historial) ExtraerUltima() *Memento {
	if len(h.instantaneas) == 0 {
		return nil
	}
	idx := len(h.instantaneas) - 1
	m := h.instantaneas[idx]
	h.instantaneas = h.instantaneas[:idx]
	return m
}

func main() {
	editor := &Editor{}
	historial := &Historial{}

	editor.Escribir("package main; ")
	historial.Registrar(editor.Guardar("v1: encabezado"))

	editor.Escribir("func main() { ")
	historial.Registrar(editor.Guardar("v2: firma main"))

	editor.Escribir("syntax_error??? }")
	fmt.Println("  Estado actual:", editor.Mostrar())

	fmt.Println("\nRestaurando estados previos desde el historial:")
	snap := historial.ExtraerUltima()
	editor.Restaurar(snap)
	fmt.Printf("  ⮌ Restaurado [%s] → %s\n", snap.Etiqueta(), editor.Mostrar())

	snap = historial.ExtraerUltima()
	editor.Restaurar(snap)
	fmt.Printf("  ⮌ Restaurado [%s] → %s\n", snap.Etiqueta(), editor.Mostrar())
}

🔍 Explicación paso a paso

  1. Editor (Originador) mantiene los campos no exportados texto y cursor y produce un *Memento en Guardar().
  2. Memento mantiene sus campos en minúscula (no exportados) y ofrece únicamente el método de lectura de metadatos Etiqueta().
  3. Historial (Cuidador) apila punteros *Memento y, cuando ocurre un error en el código editado, desapila las instantáneas para que editor.Restaurar(snap) recupere el estado exacto anterior.
  💾 Guardada instantánea [v1: encabezado]
  💾 Guardada instantánea [v2: firma main]
  Estado actual: texto="package main; func main() { syntax_error??? }" (cursor=45)

Restaurando estados previos desde el historial:
  ⮌ Restaurado [v2: firma main] → texto="package main; func main() { " (cursor=28)
  ⮌ Restaurado [v1: encabezado] → texto="package main; " (cursor=14)
🐹

Nota idiomática en Go

En Go la visibilidad es a nivel de paquete (identificadores con minúscula inicial). Colocar Editor y Memento en su propio paquete permite que Editor acceda a los campos privados de Memento, mientras que un Historial externo solo ve el método exportado Etiqueta().
