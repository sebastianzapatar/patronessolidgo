Observer

También llamado: Observador, Publicación-Suscripción (Pub/Sub), Event-Subscriber, Listener

🎯 Propósito

Observer es un patrón de diseño de comportamiento que define un mecanismo de suscripción para notificar automáticamente a múltiples objetos (suscriptores) sobre cualquier evento o cambio de estado que ocurra en el objeto que están observando (notificador o sujeto).

😟 Problema

Imagina dos objetos: un Cliente interesado en un producto nuevo y una Tienda que lo recibirá pronto. Si el cliente consulta a la tienda cada pocos minutos (polling activo), desperdicia tiempo y recursos en viajes inútiles mientras el producto no llega.

Si, por el contrario, la tienda envía correos masivos a absolutamente todos los usuarios registrados cada vez que entra mercancía, inundará de spam a quienes no les interesa ese artículo. Surge una disyuntiva clara: o el interesado gasta recursos preguntando sin parar, o el emisor acopla y satura a receptores equivocados.

💡 Solución

El objeto cuyo estado es relevante se denomina Notificador (Subject / Publisher) y quienes desean reaccionar a sus cambios son los Suscriptores (Observers). El patrón añade al notificador una lista dinámica de suscripción con métodos públicos para registrarse (Suscribir) y darse de baja (Desuscribir).

Para no acoplar el notificador a decenas de clases concretas distintas, todos los observadores implementan una misma interfaz Suscriptor con un único método de aviso (Actualizar). Cuando ocurre un evento importante, el notificador recorre su lista e invoca esa interfaz común pasándole los datos contextuales del evento.

🌍

Analogía en el mundo real

Cuando te suscribes a una revista o periódico impreso, dejas de ir todos los días al quiosco a preguntar si ya salió la nueva edición. La editorial (notificador) mantiene un padrón de suscriptores por temática y entrega cada ejemplar directamente en tu buzón tan pronto se publica. En cualquier momento puedes cancelar tu suscripción y dejarás de recibir números sin afectar a la editorial ni a los demás lectores.

│  + Abrir(ruta) / Guardar()   │  │ + Actualizar()  │   │ + Actualizar()   │
└──────────────────────────────┘  └─────────────────┘   └──────────────────┘

  1. Notificador (Publisher / Subject): mantiene la infraestructura de suscripción (mapa o lista de oyentes) y permite agregar o quitar suscriptores en tiempo de ejecución.
  2. Emisión de notificaciones: al cambiar su estado o ejecutar una acción de negocio, recorre la lista de suscriptores e invoca el método de la interfaz común.
  3. Interfaz Suscriptora (Observer): declara el contrato de notificación (p. ej., Actualizar(evento, datos)).
  4. Suscriptores Concretos: ejecutan reacciones específicas ante el evento sin que el notificador conozca sus tipos concretos.
  5. Contexto del evento: parámetros que el notificador envía en la llamada (tipo de evento, archivo afectado o referencia a sí mismo).
  6. Cliente: instancia por separado al notificador y a los suscriptores, y los conecta mediante Suscribir.

🧭 Aplicabilidad

  • Cuando el cambio de estado de un objeto requiere actualizar a otros objetos cuyo conjunto es desconocido de antemano o varía dinámicamente (p. ej., eventos de interfaz gráfica, hooks de compilación o guardado en un IDE).
  • Cuando algunos objetos de la aplicación deben observar a otros únicamente durante un tiempo limitado o bajo condiciones específicas, pudiendo darse de baja en caliente.

🛠️ Cómo implementarlo

  1. Divide la lógica en dos: el núcleo de negocio independiente será el notificador y las reacciones secundarias serán suscriptores.
  2. Declara la interfaz Suscriptor con el método Actualizar.
  3. Crea el componente gestor de suscripciones (por composición, ideal en Go) con métodos para suscribir, desuscribir y notificar.
  4. Implementa cada reacción en un struct suscriptor concreto y regístralos desde el cliente.

Ventajas

  • Principio Abierto/Cerrado (OCP): puedes añadir nuevos tipos de suscriptores sin modificar jamás el código del notificador.
  • Permite establecer y romper relaciones entre objetos dinámicamente en tiempo de ejecución.

Desventajas

  • Los suscriptores suelen ser notificados en un orden arbitrario o sin garantías de precedencia entre ellos.
  • Si no se dan de baja, las referencias retenidas en la lista pueden causar fugas de memoria (lapsed listener).

🔗 Relación con otros patrones

Chain of Responsibility, Command, Mediator y Observer conectan emisores y receptores de formas distintas: Observer permite suscripción dinámica unidireccional a múltiples oyentes, mientras que Mediator centraliza la comunicación bidireccional entre componentes para eliminar dependencias mutuas (aunque un Mediator suele implementarse internamente apoyándose en un Observer).

Observer en Go

package main

import "fmt"

// Suscriptor (Observer): interfaz común para todos los observadores.
type Suscriptor interface {
	ID() string
	Actualizar(evento, archivo string)
}

// Notificador (Subject / Publisher): gestiona suscripciones y emite eventos.
type GestorEventos struct {
	oyentes map[string][]Suscriptor
}

func NuevoGestorEventos() *GestorEventos {
	return &GestorEventos{oyentes: make(map[string][]Suscriptor)}
}

func (g *GestorEventos) Suscribir(evento string, s Suscriptor) {
	g.oyentes[evento] = append(g.oyentes[evento], s)
}

func (g *GestorEventos) Desuscribir(evento string, id string) {
	lista := g.oyentes[evento]
	for i, s := range lista {
		if s.ID() == id {
			g.oyentes[evento] = append(lista[:i], lista[i+1:]...)
			return
		}
	}
}

func (g *GestorEventos) Notificar(evento, archivo string) {
	for _, s := range g.oyentes[evento] {
		s.Actualizar(evento, archivo)
	}
}

// Notificador concreto: Editor de código que delega la suscripción por composición.
type EditorCodigo struct {
	Eventos *GestorEventos
	archivo string
}

func NuevoEditor() *EditorCodigo {
	return &EditorCodigo{Eventos: NuevoGestorEventos()}
}

func (e *EditorCodigo) Abrir(ruta string) {
	e.archivo = ruta
	e.Eventos.Notificar("abrir", e.archivo)
}

func (e *EditorCodigo) Guardar() {
	e.Eventos.Notificar("guardar", e.archivo)
}

// Suscriptor Concreto 1: registra eventos en bitácora.
type LoggerListener struct{ nombre string }

func (l *LoggerListener) ID() string { return l.nombre }
func (l *LoggerListener) Actualizar(ev, arch string) {
	fmt.Printf("[LOG:%s] evento=%q sobre %s\n", l.nombre, ev, arch)
}

// Suscriptor Concreto 2: ejecuta análisis estático al guardar.
type LinterListener struct{ regla string }

func (l *LinterListener) ID() string { return "linter-" + l.regla }
func (l *LinterListener) Actualizar(ev, arch string) {
	fmt.Printf("[LINTER:%s] verificando sintaxis de %s tras %q\n", l.regla, arch, ev)
}

func main() {
	editor := NuevoEditor()
	logger := &LoggerListener{nombre: "auditoria"}
	linter := &LinterListener{regla: "gofmt"}

	editor.Eventos.Suscribir("abrir", logger)
	editor.Eventos.Suscribir("guardar", logger)
	editor.Eventos.Suscribir("guardar", linter)

	editor.Abrir("parser.go")
	editor.Guardar()

	fmt.Println("--- Dando de baja al linter ---")
	editor.Eventos.Desuscribir("guardar", linter.ID())
	editor.Guardar()
}

🔎 Explicación paso a paso

  1. Suscriptor define la interfaz mínima: un identificador único ID() para poder desuscribirse con seguridad y Actualizar(evento, archivo).
  2. GestorEventos encapsula un mapa map[string][]Suscriptor que permite suscribirse por tipo de evento ("abrir", "guardar").
  3. EditorCodigo compone a *GestorEventos en lugar de heredar de una clase base, manteniendo limpia su lógica de archivos.
  4. En main() suscribimos tanto el LoggerListener como el LinterListener al evento "guardar", y luego demostramos la baja en caliente con Desuscribir.

Salida real

[LOG:auditoria] evento="abrir" sobre parser.go
[LOG:auditoria] evento="guardar" sobre parser.go
[LINTER:gofmt] verificando sintaxis de parser.go tras "guardar"
--- Dando de baja al linter ---
[LOG:auditoria] evento="guardar" sobre parser.go
🐹

Nota idiomática en Go

En Go, además de interfaces como Suscriptor, es muy común implementar Observer usando funciones callback (type Handler func(ev string)) o canales (chan Evento) cuando los suscriptores procesan eventos de forma concurrente en sus propias goroutines.

State

También llamado: Estado, Objects for States

🎯 Propósito

State es un patrón de diseño de comportamiento que permite a un objeto alterar su comportamiento cuando su estado interno cambia. Desde afuera, parece como si el objeto hubiera cambiado su propia clase.

😟 Problema

Está estrechamente ligado al concepto de Máquina de Estados Finitos (FSM): un objeto puede encontrarse en un conjunto finito de estados (p. ej. un Documento en Borrador, Moderación o Publicado) y sus métodos se comportan distinto según el estado activo.

Cuando se implementa con enormes bloques switch o cadenas de if/else repetidas dentro de cada método del objeto, el código se vuelve frágil y difícil de mantener: añadir un nuevo estado o cambiar una regla de transición obliga a editar todos los métodos de la clase.

💡 Solución

El patrón State propone crear una clase (o struct) separada para cada estado posible del objeto y extraer allí toda la lógica dependiente de ese estado. El objeto original, denominado Contexto, conserva una referencia a un objeto estado activo y le delega todo el trabajo.

Para transicionar a otro estado, basta con sustituir el objeto de estado referenciado en el contexto por la instancia del nuevo estado. A diferencia de Strategy, en State los estados concretos sí suelen conocerse entre sí y disparan ellos mismos las transiciones en el contexto.

🌍

Analogía en el mundo real

Los botones físicos de tu smartphone reaccionan de forma completamente distinta según el estado en que se encuentre el teléfono: si está desbloqueado, pulsar un botón abre aplicaciones o sube el volumen; si está bloqueado, el mismo botón solo enciende la pantalla de PIN; y si tiene la batería agotada, muestra únicamente el ícono de carga.

State — Estructura y análisis

┌─────────────────────────────┐         ┌──────────────────────────────┐
│      (1) Documento          │────────▶│  <<interface>>               │
│         (Contexto)          │ estado  │  (2) EstadoDocumento         │
├─────────────────────────────┤         ├──────────────────────────────┤
│ - estado: EstadoDocumento   │         │ + Nombre() string            │
│ + CambiarEstado(nuevo)  (4) │         │ + Revisar(d *Documento)      │
│ + Revisar()                 │         │ + Publicar(d *Doc, admin)    │
│ + Publicar(esAdmin)         │         └──────────────△───────────────┘
└──────────────▲──────────────┘                        │
               │ (3) pasa *Documento      ┌────────────┼────────────┐
               └────────────────────┐     │            │            │
                               ┌────┴─────┴───┐ ┌──────┴──────┐ ┌───┴──────────┐
                               │EstadoBorrador│ │EstadoModera.│ │EstadoPublica.│
                               └──────────────┘ └─────────────┘ └──────────────┘
  1. Contexto (Documento): almacena la referencia al objeto de estado actual, delega en él las operaciones dependientes del estado y ofrece un setter (CambiarEstado) para actualizar el estado activo.
  2. Interfaz Estado (EstadoDocumento): declara los métodos específicos del estado que tienen sentido para todos los estados concretos.
  3. Estados Concretos: cada struct implementa el comportamiento propio de un estado y recibe o guarda una referencia al contexto para consultar datos e iniciar transiciones.
  4. Transiciones de estado: tanto el contexto como los propios estados concretos pueden sustituir el objeto estado activo llamando a d.CambiarEstado(...).

🧭 Aplicabilidad

  • Cuando un objeto se comporta de manera drásticamente distinta según su estado actual, el número de estados es considerable y su lógica cambia con frecuencia.
  • Cuando una clase está contaminada con condicionales masivos (switch / if-else) que inspeccionan banderas o campos internos para decidir qué hacer en cada método (como en un analizador léxico o el ciclo de vida de una conexión TCP).

🛠️ Cómo implementarlo

  1. Identifica la clase Contexto y declara la interfaz Estado con las operaciones dependientes del estado.
  2. Por cada estado de la máquina, crea un struct concreto que implemente la interfaz.
  3. Añade en el contexto un campo del tipo de la interfaz Estado y delega allí las llamadas en vez de usar condicionales.
  4. Pasa una referencia del contexto a los métodos del estado para que cada estado pueda disparar transiciones hacia el siguiente estado.

Ventajas

  • Principio de Responsabilidad Única (SRP): aísla el código de cada estado en su propio tipo.
  • Principio Abierto/Cerrado (OCP): añade nuevos estados sin alterar el contexto ni los estados ya existentes.
  • Elimina condicionales gigantescos y simplifica el contexto.

Desventajas

  • Puede resultar excesivo (sobreingeniería) si la máquina solo tiene dos o tres estados muy simples que rara vez cambian.

🔗 Relación con otros patrones

State puede verse como una extensión de Strategy: ambos usan composición y delegación, pero en Strategy los algoritmos son independientes y no se conocen entre sí, mientras que en State los estados concretos conocen las reglas de transición y cambian activamente el estado del contexto.

State en Go

package main

import "fmt"

// Estado (State): interfaz con las acciones dependientes del estado.
type EstadoDocumento interface {
	Nombre() string
	Revisar(d *Documento)
	Publicar(d *Documento, esAdmin bool)
}

// Contexto (Context): mantiene referencia al estado actual y delega en él.
type Documento struct {
	Titulo string
	estado EstadoDocumento
}

func NuevoDocumento(titulo string) *Documento {
	doc := &Documento{Titulo: titulo}
	doc.CambiarEstado(&EstadoBorrador{})
	return doc
}

func (d *Documento) CambiarEstado(nuevo EstadoDocumento) {
	d.estado = nuevo
	fmt.Printf("  -> [%s] ahora está en estado: %s\n", d.Titulo, nuevo.Nombre())
}

func (d *Documento) Revisar()                 { d.estado.Revisar(d) }
func (d *Documento) Publicar(esAdmin bool)    { d.estado.Publicar(d, esAdmin) }

// Estado Concreto 1: Borrador
type EstadoBorrador struct{}

func (e *EstadoBorrador) Nombre() string { return "Borrador" }
func (e *EstadoBorrador) Revisar(d *Documento) {
	fmt.Println("[Borrador] Enviando documento a moderación...")
	d.CambiarEstado(&EstadoModeracion{})
}
func (e *EstadoBorrador) Publicar(d *Documento, esAdmin bool) {
	fmt.Println("[Borrador] No se puede publicar directamente sin revisión.")
}

// Estado Concreto 2: Moderación
type EstadoModeracion struct{}

func (e *EstadoModeracion) Nombre() string { return "Moderación" }
func (e *EstadoModeracion) Revisar(d *Documento) {
	fmt.Println("[Moderación] El documento ya está en revisión.")
}
func (e *EstadoModeracion) Publicar(d *Documento, esAdmin bool) {
	if !esAdmin {
		fmt.Println("[Moderación] Permiso denegado: solo un admin puede aprobar. Vuelve a borrador.")
		d.CambiarEstado(&EstadoBorrador{})
		return
	}
	fmt.Println("[Moderación] Aprobado por administrador.")
	d.CambiarEstado(&EstadoPublicado{})
}

// Estado Concreto 3: Publicado
type EstadoPublicado struct{}

func (e *EstadoPublicado) Nombre() string { return "Publicado" }
func (e *EstadoPublicado) Revisar(d *Documento) {
	fmt.Println("[Publicado] Ya está publicado; no requiere revisión.")
}
func (e *EstadoPublicado) Publicar(d *Documento, esAdmin bool) {
	fmt.Println("[Publicado] Operación ignorada: el documento ya es público.")
}

func main() {
	doc := NuevoDocumento("Especificación Gramática LL(1)")
	doc.Publicar(false)
	doc.Revisar()
	doc.Publicar(false) // Falla y regresa a Borrador
	doc.Revisar()
	doc.Publicar(true)  // Admin aprueba -> Publicado
	doc.Revisar()
}

🔎 Explicación paso a paso

  1. EstadoDocumento define las operaciones del ciclo de vida (Revisar y Publicar) recibiendo el puntero *Documento como contexto.
  2. Documento no tiene ni un solo if ni switch: delega en d.estado.Revisar(d) y d.estado.Publicar(d, esAdmin).
  3. Cada estado concreto (EstadoBorrador, EstadoModeracion, EstadoPublicado) decide qué acción ejecutar y a qué estado transicionar invocando d.CambiarEstado(...).

Salida real

  -> [Especificación Gramática LL(1)] ahora está en estado: Borrador
[Borrador] No se puede publicar directamente sin revisión.
[Borrador] Enviando documento a moderación...
  -> [Especificación Gramática LL(1)] ahora está en estado: Moderación
[Moderación] Permiso denegado: solo un admin puede aprobar. Vuelve a borrador.
  -> [Especificación Gramática LL(1)] ahora está en estado: Borrador
[Borrador] Enviando documento a moderación...
  -> [Especificación Gramática LL(1)] ahora está en estado: Moderación
[Moderación] Aprobado por administrador.
  -> [Especificación Gramática LL(1)] ahora está en estado: Publicado
[Publicado] Ya está publicado; no requiere revisión.

Strategy

También llamado: Estrategia, Policy

🎯 Propósito

Strategy es un patrón de diseño de comportamiento que te permite definir una familia de algoritmos, encapsular cada uno de ellos en una clase (o struct) separada y hacer que sus objetos sean completamente intercambiables en tiempo de ejecución.

😟 Problema

Imagina que desarrollas una aplicación de navegación con mapas. Empiezas calculando rutas solo para automóviles por carretera, pero pronto los usuarios piden rutas a pie, luego en transporte público, después en bicicleta y finalmente rutas turísticas.

Cada vez que agregas un algoritmo de enrutamiento dentro de la clase principal Navegador, su tamaño se duplica. Cualquier ajuste en el cálculo de bicicletas arriesga romper el código de automóviles y genera constantes conflictos de integración (merge conflicts) en el equipo.

💡 Solución

Extrae cada variante del algoritmo a su propia clase llamada Estrategia, todas implementando una interfaz común (p. ej., EstrategiaRuta con el método CalcularRuta(origen, destino)).

La clase original Navegador actúa como Contexto: guarda una referencia a una estrategia y delega en ella el cálculo sin saber cómo funciona por dentro. El cliente puede inyectar o cambiar en caliente la estrategia activa según la preferencia del usuario.

🌍

Analogía en el mundo real

Necesitas ir desde la universidad hasta el aeropuerto. Puedes elegir entre varias estrategias de transporte: tomar el metro/autobús, pedir un taxi o ir en bicicleta. El objetivo es idéntico (trasladarte del punto A al punto B), pero eliges e intercambias el algoritmo según tu presupuesto, equipaje o prisa del momento.

┌─────────────────────────────┐         ┌────────────────────────────────┐
│      (1) Navegador          │────────▶│  <<interface>>                 │
│         (Contexto)          │         │  (2) EstrategiaRuta            │
├─────────────────────────────┤         ├────────────────────────────────┤
│ - estrategia: EstrategiaRuta│         │ + Nombre() string              │
│ + CambiarEstrategia(e)      │         │ + CalcularRuta(o, d) ([]str,i) │
│ + MostrarRuta(o, d)     (4) │         └───────────────△────────────────┘
└──────────────▲──────────────┘                         │
               │ (5) Cliente configura     ┌────────────┼────────────┐
               │     e intercambia         │            │            │
                                 ┌─────────┴─────┐ ┌────┴─────────┐ ┌┴──────────────┐
                                 │(3) RutaAuto   │ │(3) RutaTransp│ │(3) RutaBici   │
                                 └───────────────┘ └──────────────┘ └───────────────┘
  1. Contexto (Navegador): mantiene una referencia a una de las estrategias concretas y se comunica con ella únicamente a través de la interfaz común.
  2. Interfaz Estrategia (EstrategiaRuta): declara el método común que el contexto usa para ejecutar cualquier variante del algoritmo.
  3. Estrategias Concretas: implementan las distintas variaciones del algoritmo (enrutamiento en auto, transporte público, bicicleta; o p. ej. distintos pases de optimización en un compilador).
  4. Ejecución delegada: el contexto invoca el método de la estrategia sin conocer cómo se calcula internamente.
  5. Cliente: elige la estrategia concreta adecuada, la pasa al contexto y puede sustituirla en cualquier momento con un modificador (CambiarEstrategia).

🧭 Aplicabilidad

  • Cuando necesitas usar distintas variantes de un algoritmo dentro de un objeto y poder intercambiarlas durante el tiempo de ejecución.
  • Cuando tienes muchas clases similares que solo difieren en cómo ejecutan cierto comportamiento, o un condicional enorme que selecciona entre variantes del mismo algoritmo.
  • Para aislar la lógica de negocio principal de los detalles complejos y estructuras de datos internas de los algoritmos (p. ej. algoritmos de grafos, compresión o asignación de registros).

🛠️ Cómo implementarlo

  1. Identifica en el contexto el algoritmo que cambia con frecuencia o está atrapado en un gran switch.
  2. Declara la interfaz Estrategia común a todas las variantes.
  3. Extrae cada algoritmo en un struct independiente que implemente dicha interfaz.
  4. Añade en el contexto un campo para la interfaz y un método setter para cambiarla en tiempo de ejecución.

Ventajas

  • Permite intercambiar algoritmos dentro de un objeto en caliente (en tiempo de ejecución).
  • Aísla los detalles internos del algoritmo del código que lo consume.
  • Sustituye la herencia por composición y cumple el Principio Abierto/Cerrado (OCP).

Desventajas

  • Los clientes deben conocer las diferencias entre estrategias para poder elegir la adecuada.
  • Si solo existen un par de algoritmos que casi nunca cambian, crear tipos e interfaces extra puede ser innecesario.

🔗 Relación con otros patrones

Decorator cambia la piel de un objeto envolviéndolo en capas, mientras que Strategy cambia sus entrañas sustituyendo el algoritmo interno. Frente a Template Method (que varía pasos mediante herencia/esqueleto fijo), Strategy reemplaza el algoritmo entero por composición en tiempo de ejecución.

package main

import (
	"fmt"
	"strings"
)

// Estrategia (Strategy): interfaz común para toda la familia de algoritmos.
type EstrategiaRuta interface {
	Nombre() string
	CalcularRuta(origen, destino string) ([]string, int)
}

// Estrategia Concreta 1: Automóvil (prioriza autopistas y velocidad).
type RutaAutomovil struct{}

func (r RutaAutomovil) Nombre() string { return "Automóvil" }
func (r RutaAutomovil) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Autopista Central", "Peaje Norte", destino}, 25
}

// Estrategia Concreta 2: Transporte Público (combina metro y bus).
type RutaTransportePublico struct{}

func (r RutaTransportePublico) Nombre() string { return "Transporte Público" }
func (r RutaTransportePublico) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Estación Metro A", "Transbordo Línea B", destino}, 40
}

// Estrategia Concreta 3: Bicicleta (prioriza ciclovías y parques).
type RutaBicicleta struct{}

func (r RutaBicicleta) Nombre() string { return "Bicicleta" }
func (r RutaBicicleta) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Ciclovía del Río", "Parque Lineal", destino}, 55
}

// Contexto (Context): delega el cálculo en la estrategia activa sin usar switch.
type Navegador struct {
	estrategia EstrategiaRuta
}

func NuevoNavegador(e EstrategiaRuta) *Navegador {
	return &Navegador{estrategia: e}
}

func (n *Navegador) CambiarEstrategia(e EstrategiaRuta) {
	n.estrategia = e
}

func (n *Navegador) MostrarRuta(origen, destino string) {
	tramos, minutos := n.estrategia.CalcularRuta(origen, destino)
	fmt.Printf("[%s] (%d min): %s\n",
		n.estrategia.Nombre(), minutos, strings.Join(tramos, " -> "))
}

	nav := NuevoNavegador(RutaAutomovil{})
	nav.MostrarRuta("Campus", "Aeropuerto")

	nav.CambiarEstrategia(RutaTransportePublico{})
	nav.MostrarRuta("Campus", "Aeropuerto")

	nav.CambiarEstrategia(RutaBicicleta{})
	nav.MostrarRuta("Campus", "Aeropuerto")
}

  2. RutaAutomovil, RutaTransportePublico y RutaBicicleta implementan de forma autónoma cada algoritmo sin tocar a las demás.
  3. Navegador (Contexto) recibe cualquier EstrategiaRuta y permite intercambiarla en caliente con CambiarEstrategia.

Template Method

También llamado: Método plantilla

🎯 Propósito

Template Method es un patrón de diseño de comportamiento que define el esqueleto invariante de un algoritmo en una operación plantilla, delegando o permitiendo redefinir ciertos pasos específicos en implementaciones concretas sin alterar la estructura ni el orden general del algoritmo.

😟 Problema

Imagina una aplicación de minería de datos que procesa documentos corporativos en formatos CSV, DOC y PDF. Aunque la lectura y extracción de bytes cambia según el formato, la secuencia global (Abrir → Extraer → Parsear → Analizar → Cerrar) y el análisis estadístico final son idénticos en los tres casos.

Si cada formato duplica todo el flujo por separado, cualquier cambio en el orden de etapas o en el análisis común obliga a editar todas las clases, rompiendo el principio DRY.

💡 Solución (y cómo se adapta a Go)

Se descompone el algoritmo en pasos bien definidos: pasos obligatorios (variables según el formato), pasos comunes fijos y ganchos (hooks) opcionales con comportamiento por defecto vacío antes o después de etapas críticas.

¿Cómo se resuelve en Go si no hay herencia ni clases abstractas? En Go se define una interfaz de pasos (PasosMineria) junto con una función o struct ejecutor (MineroDatos.Ejecutar) que codifica el esqueleto fijo e invoca la interfaz en orden. Los pasos opcionales o hooks por defecto se reutilizan embebiendo un struct base (BaseMineria) por composición.

🌍

Analogía en el mundo real

En la construcción residencial en serie, un plano arquitectónico maestro fija la secuencia obligatoria de etapas: colocar cimientos, levantar estructura, instalar plomería/electricidad y pintar acabados. No puedes instalar el techo antes que los cimientos (el esqueleto es fijo), pero cada propietario puede personalizar pasos específicos como el tipo de piso o el diseño de las ventanas.

│   (Esqueleto / Método Plantilla)     │invoca │  (2) PasosMineria           │

│     2. p.ExtraerDatos(raw)           │       │ + Parsear(crudos) map       │

│     4. p.AntesDeAnalizar() [hook]    │       │ + Cerrar(ruta)              │
│     5. m.analizarYReportar() [fijo]  │       └──────────────△──────────────┘
│     6. p.Cerrar(ruta)                │                      │ implementan
└──────────────────────────────────────┘          ┌───────────┴───────────┐
                                                  │                       │
┌──────────────────────────────────────┐   ┌──────┴─────────┐   ┌─────────┴────────┐
│ (3) BaseMineria (pasos por defecto)  │──▶│ (4) MineroCSV  │   │ (4) MineroPDF    │
│ + AntesDeAnalizar() {}  / + Cerrar() │   │ embebe Base    │   │ sobrescribe Hook │
└──────────────────────────────────────┘   └────────────────┘   └──────────────────┘
  1. Método Plantilla (MineroDatos.Ejecutar): define el esqueleto invariante del algoritmo invocando los pasos en un orden estricto y ejecutando directamente los pasos comunes fijos.
  2. Interfaz de Pasos (PasosMineria): sustituye a los métodos abstractos de POO clásica; declara las operaciones primitivas que cada variante debe suministrar.
  3. Struct Base opcional (BaseMineria): proporciona implementaciones por defecto para pasos comunes y ganchos (hooks) mediante struct embedding.
  4. Implementaciones Concretas (MineroCSV, MineroPDF): implementan los pasos de su formato y, si lo necesitan, redefinen los hooks sin poder alterar el método plantilla.

🧭 Aplicabilidad

  • Cuando quieres que los clientes personalicen únicamente ciertos pasos de un algoritmo (p. ej., fases específicas del pipeline de un compilador o exportador) sin permitirles modificar la estructura ni el orden general.
  • Cuando tienes varios tipos con algoritmos casi idénticos que solo varían en pasos puntuales y deseas eliminar la duplicación de código.

🛠️ Cómo implementarlo en Go

  1. Divide el algoritmo en pasos e identifica cuáles son fijos, cuáles son obligatorios por variante y cuáles son ganchos (hooks) opcionales.
  2. Declara la interfaz de pasos (PasosMineria) con los pasos variables y hooks.
  3. Crea un struct Base con métodos por defecto para los hooks (para embeberlo en los structs concretos).
  4. Escribe el método plantilla Ejecutar(p PasosMineria, ...) que orquesta la secuencia completa.

Ventajas

  • Permite redefinir solo ciertas partes de un algoritmo grande sin verse afectado por cambios en el resto del flujo.
  • Concentra el código compartido y el orden de ejecución en un único lugar (evita duplicación).

Desventajas

  • Algunos clientes pueden verse limitados por la rigidez del esqueleto predefinido.
  • Cuantos más pasos y hooks tenga la plantilla, más difícil resulta mantenerla y comprenderla.

🔗 Relación con otros patrones

Factory Method es una especialización de Template Method aplicada a la creación de objetos. En Go, como no existe herencia de clases, Template Method converge estructuralmente con Strategy (usa interfaces y composición), con la diferencia de que aquí el esqueleto multi-paso es el protagonista.

Template Method en Go

package main

import (
	"fmt"
	"strings"
)

// PasosMineria define los pasos primitivos y ganchos (hooks) del algoritmo.
// En Go no hay herencia ni métodos abstractos: modelamos los pasos variables con una interfaz.
type PasosMineria interface {
	Abrir(ruta string) string
	ExtraerDatos(contenido string) []string
	Parsear(crudos []string) map[string]int
	Cerrar(ruta string)
	AntesDeAnalizar() // Gancho (hook) opcional
}

// BaseMineria aporta implementaciones por defecto para pasos opcionales y hooks
// mediante composición (struct embedding).
type BaseMineria struct{}

func (BaseMineria) AntesDeAnalizar() {}
func (BaseMineria) Cerrar(ruta string) {
	fmt.Printf("  [Base] Cerrando descriptor de %s\n", ruta)
}

// MineroDatos contiene el "Método Plantilla" (Ejecutar) que fija el esqueleto del algoritmo.
type MineroDatos struct{}

func (m MineroDatos) Ejecutar(p PasosMineria, ruta string) {
	fmt.Printf("=== Procesando %s ===\n", ruta)
	raw := p.Abrir(ruta)
	crudos := p.ExtraerDatos(raw)
	datos := p.Parsear(crudos)
	p.AntesDeAnalizar() // Hook
	m.analizarYReportar(datos)
	p.Cerrar(ruta)
}

// Paso común fijo en el esqueleto (no sobrescribible).
func (MineroDatos) analizarYReportar(datos map[string]int) {
	fmt.Printf("  [Análisis común] Total claves=%d -> %v\n", len(datos), datos)
}

// Implementación Concreta 1: CSV (embebe BaseMineria y usa el hook por defecto).
type MineroCSV struct{ BaseMineria }

func (MineroCSV) Abrir(ruta string) string {
	fmt.Println("  [CSV] Leyendo texto separado por comas")
	return " compilador,3 ; lexer,2 ; parser,5 "
}
func (MineroCSV) ExtraerDatos(c string) []string { return strings.Split(c, ";") }
func (MineroCSV) Parsear(crudos []string) map[string]int {
	res := make(map[string]int)
	for _, fila := range crudos {
		partes := strings.Split(strings.TrimSpace(fila), ",")
		res[partes[0]] = len(partes[0])
	}
	return res
}

// Implementación Concreta 2: PDF (sobrescribe el hook AntesDeAnalizar).
type MineroPDF struct{ BaseMineria }

func (MineroPDF) Abrir(ruta string) string {
	fmt.Println("  [PDF] Descomprimiendo flujos de objetos PDF")
	return "AST|SSA|IR"
}
func (MineroPDF) ExtraerDatos(c string) []string { return strings.Split(c, "|") }
func (MineroPDF) Parsear(crudos []string) map[string]int {
	res := make(map[string]int)
	for i, tok := range crudos {
		res[tok] = (i + 1) * 10
	}
	return res
}
func (MineroPDF) AntesDeAnalizar() {
	fmt.Println("  [Hook PDF] Limpiando metadatos OCR antes del análisis")
}

func main() {
	plantilla := MineroDatos{}
	plantilla.Ejecutar(MineroCSV{}, "metricas.csv")
	plantilla.Ejecutar(MineroPDF{}, "articulo.pdf")
}

🔎 Explicación paso a paso

  1. PasosMineria declara los pasos personalizables del algoritmo y el gancho AntesDeAnalizar().
  2. BaseMineria ofrece un cuerpo vacío para el hook y un cierre estándar. MineroCSV y MineroPDF lo embeben para no repetir código.
  3. MineroDatos.Ejecutar es el Método Plantilla: fija el orden de los 6 pasos e invoca el paso privado invariante analizarYReportar.
  4. MineroPDF redefine AntesDeAnalizar() para limpiar metadatos OCR, mientras MineroCSV conserva el gancho silencioso por defecto.

Salida real

  [Análisis común] Total claves=3 -> map[compilador:10 lexer:5 parser:6]
  [Base] Cerrando descriptor de metricas.csv
=== Procesando articulo.pdf ===
  [PDF] Descomprimiendo flujos de objetos PDF
  [Hook PDF] Limpiando metadatos OCR antes del análisis
  [Análisis común] Total claves=3 -> map[AST:10 IR:30 SSA:20]
  [Base] Cerrando descriptor de articulo.pdf

Nota idiomática en Go

¡Cuidado con el embedding en Go! Si pusieras el método plantilla Ejecutar() dentro de BaseMineria, el receptor sería siempre BaseMineria y no llamaría a los métodos sobrescritos del struct hijo (en Go no hay despacho virtual sobre el struct embebido). Por eso el esqueleto Ejecutar(p PasosMineria, ...) recibe explícitamente la interfaz PasosMineria.

Visitor

También llamado: Visitante

🎯 Propósito

Visitor es un patrón de diseño de comportamiento que te permite separar los algoritmos de la estructura de objetos sobre la que operan, pudiendo añadir nuevas operaciones a una jerarquía de tipos (como un Árbol Sintáctico Abstracto — AST) sin modificar sus estructuras.

😟 Problema

En un compilador tienes una jerarquía de nodos del AST (Numero, Suma, Multiplicacion, etc.). Primero necesitas evaluar las expresiones; luego te piden imprimir el árbol en formato infijo; después verificar tipos, exportar a XML/JSON y generar código intermedio.

Si añades un método nuevo en cada struct de nodo por cada nueva fase del compilador, mezclas responsabilidades dispares dentro de los nodos de datos y tienes que modificar y recompilar toda la jerarquía del AST cada vez que agregas una operación.

💡 Solución (Double Dispatch)

Coloca cada nueva operación en una clase separada llamada Visitante (p. ej., Evaluador, ImpresorAST) que declara un método específico por cada tipo concreto de nodo (VisitarNumero, VisitarSuma, ...).

Para evitar cadenas de switch de tipos desde afuera, cada nodo implementa un único método trivial Aceptar(v Visitante) que invoca de vuelta el método exacto del visitante pasándose a sí mismo (v.VisitarSuma(s)). Esta técnica se conoce como Double Dispatch (doble despacho).

🌍

Analogía en el mundo real

Un experimentado agente de seguros (Visitante) recorre todos los edificios de un barrio (estructura de objetos). Los edificios no cambian, pero el agente ejecuta una acción especializada según el tipo concreto de inmueble que visita: si visita una vivienda residencial ofrece seguro médico, si visita un banco ofrece seguro contra robos, y si visita una cafetería ofrece póliza contra incendios e inundaciones.

🧠 Comportamiento 2 / 3 · Estructura

Visitor — Estructura y análisis

┌──────────────────────────────────┐       ┌───────────────────────────────┐
│  <<interface>>                   │       │  <<interface>>                │
│  (1) VisitanteExpr               │◀──────│  (3) Expr (Elemento AST)      │
├──────────────────────────────────┤acepta ├───────────────────────────────┤
│ + VisitarNumero(n *Numero)       │       │ + Aceptar(v VisitanteExpr)    │
│ + VisitarSuma(s *Suma)           │       └───────────────△───────────────┘
│ + VisitarMultiplicacion(m *Mult) │                       │
└─────────────────△────────────────┘           ┌───────────┼───────────┐
                  │                            │           │           │
        ┌─────────┴─────────┐            ┌─────┴────┐ ┌────┴────┐ ┌────┴─────────┐
        │                   │            │(4) Numero│ │(4) Suma │ │(4) Multiplic.│
┌───────┴────────┐ ┌────────┴────────┐   ├──────────┤ ├─────────┤ ├──────────────┤
│(2) Evaluador   │ │(2) ImpresorAST  │   │v.Visitar │ │v.Visitar│ │v.Visitar     │
│ - Resultado    │ │ - Salida        │   │ Numero() │ │ Suma()  │ │ Mult()       │
└────────────────┘ └─────────────────┘   └──────────┘ └─────────┘ └──────────────┘
  1. Interfaz Visitante (VisitanteExpr): declara un método de visita para cada tipo de elemento concreto de la estructura (VisitarNumero, VisitarSuma, etc.).
  2. Visitantes Concretos (Evaluador, ImpresorAST): implementan un algoritmo completo sobre la jerarquía y pueden acumular estado intermedio (p. ej. Resultado o Salida) mientras recorren el árbol.
  3. Interfaz Elemento (Expr): declara el método Aceptar(v VisitanteExpr).
  4. Elementos Concretos (Nodos del AST): implementan Aceptar redirigiendo la llamada al método del visitante que corresponde a su tipo exacto (Double Dispatch).
  5. Cliente: construye el árbol (p. ej. un Composite AST) y le pasa distintos visitantes según la fase que desee ejecutar.

🧭 Aplicabilidad

  • Cuando necesitas ejecutar diversas operaciones independientes sobre todos los elementos de una estructura compleja (como un árbol sintáctico AST o un grafo Composite) sin contaminar las clases de los nodos.
  • Cuando la jerarquía de elementos (tipos de nodos) es estable, pero frecuentemente necesitas agregar nuevos algoritmos o pases de análisis sobre ella.

🛠️ Cómo implementarlo

  1. Declara la interfaz Visitante con un método VisitarX por cada tipo concreto de nodo.
  2. Declara la interfaz Elemento con el método Aceptar(v Visitante).
  3. Implementa Aceptar en cada nodo concreto llamando a v.VisitarX(n).
  4. Por cada nueva operación (evaluar, imprimir, chequear tipos), crea un struct visitante concreto e pásalo a la raíz del árbol.

Ventajas

  • Principio Abierto/Cerrado (OCP): añade nuevas operaciones sobre el AST sin tocar los nodos existentes.
  • Principio de Responsabilidad Única (SRP): agrupa en un mismo visitante todas las variantes de un algoritmo.
  • El visitante puede acumular estado útil a medida que recorre el árbol.

Desventajas

  • Si añades o eliminas un tipo de nodo en la jerarquía, debes actualizar la interfaz Visitante y todos los visitantes concretos.
  • Los visitantes solo pueden acceder a los campos y métodos exportados de los elementos.

🔗 Relación con otros patrones

Visitor es el compañero ideal de Composite (como un árbol AST) e Iterator para recorrer estructuras jerárquicas ejecutando operaciones tipadas, y puede verse como una versión más potente de Command capaz de operar sobre múltiples tipos de receptores.

Visitor en Go (AST de Expresiones)

package main

import "fmt"

// Visitante (Visitor): declara un método de visita por cada tipo concreto de nodo del AST.
type VisitanteExpr interface {
	VisitarNumero(n *Numero)
	VisitarSuma(s *Suma)
	VisitarMultiplicacion(m *Multiplicacion)
}

// Elemento (Element): nodo del AST que acepta un visitante (Double Dispatch).
type Expr interface {
	Aceptar(v VisitanteExpr)
}

// Elementos Concretos: nodos del árbol sintáctico abstracto (AST).
type Numero struct{ Valor int }

func (n *Numero) Aceptar(v VisitanteExpr) { v.VisitarNumero(n) }

type Suma struct{ Izq, Der Expr }

func (s *Suma) Aceptar(v VisitanteExpr) { v.VisitarSuma(s) }

type Multiplicacion struct{ Izq, Der Expr }

func (m *Multiplicacion) Aceptar(v VisitanteExpr) { v.VisitarMultiplicacion(m) }

// Visitante Concreto 1: Evaluador de expresiones (acumula el resultado en una pila/campo).
type Evaluador struct{ Resultado int }

func (e *Evaluador) VisitarNumero(n *Numero) { e.Resultado = n.Valor }
func (e *Evaluador) VisitarSuma(s *Suma) {
	s.Izq.Aceptar(e)
	izq := e.Resultado
	s.Der.Aceptar(e)
	e.Resultado = izq + e.Resultado
}
func (e *Evaluador) VisitarMultiplicacion(m *Multiplicacion) {
	m.Izq.Aceptar(e)
	izq := e.Resultado
	m.Der.Aceptar(e)
	e.Resultado = izq * e.Resultado
}

// Visitante Concreto 2: Impresor de árboles en notación infija parentizada.
type ImpresorAST struct{ Salida string }

func (i *ImpresorAST) VisitarNumero(n *Numero) {
	i.Salida = fmt.Sprintf("%d", n.Valor)
}
func (i *ImpresorAST) VisitarSuma(s *Suma) {
	s.Izq.Aceptar(i)
	izq := i.Salida
	s.Der.Aceptar(i)
	i.Salida = fmt.Sprintf("(%s + %s)", izq, i.Salida)
}
func (i *ImpresorAST) VisitarMultiplicacion(m *Multiplicacion) {
	m.Izq.Aceptar(i)
	izq := i.Salida
	m.Der.Aceptar(i)
	i.Salida = fmt.Sprintf("(%s * %s)", izq, i.Salida)
}

func main() {
	// Árbol AST para la expresión: (3 + 5) * 2
	ast := &Multiplicacion{
		Izq: &Suma{Izq: &Numero{3}, Der: &Numero{5}},
		Der: &Numero{2},
	}

	imp := &ImpresorAST{}
	ast.Aceptar(imp)
	fmt.Println("Expresión AST :", imp.Salida)

	eval := &Evaluador{}
	ast.Aceptar(eval)
	fmt.Println("Resultado eval:", eval.Resultado)
}

🔎 Explicación paso a paso

  1. Los nodos del AST (Numero, Suma, Multiplicacion) implementan Expr con una sola línea: redirigir Aceptar(v) al método tipado de VisitanteExpr.
  2. ImpresorAST recorre recursivamente los hijos izquierdo y derecho y construye la representación infija parentizada ((3 + 5) * 2).
  3. Evaluador recorre el mismo árbol sin tocar los structs de los nodos y calcula el valor numérico 16.

Salida real

Resultado eval: 16
