Go: orientación a objetos sin clases

Los patrones GoF se escribieron pensando en C++/Smalltalk. En Go se expresan con otras herramientas

// 1. struct = datos (el "estado" del objeto)
type Animal struct {
    Nombre string
}

// 2. Método = función con receptor
func (a *Animal) Presentarse() string {
    return "Soy " + a.Nombre
}

// 3. Interfaz = contrato. Se implementa IMPLÍCITAMENTE:
//    basta con tener los métodos (no existe "implements")
type Hablador interface {
    Hablar() string
}

// 4. Embedding = composición que "promueve" métodos
type Perro struct {
    Animal        // Perro obtiene Presentarse()
    Raza   string
}

func (p *Perro) Hablar() string { return "¡Guau!" }

// 5. Funciones de primera clase
type Saludo func(string) string

func main() {
    p := &Perro{Animal{"Firulais"}, "Criollo"}
    var h Hablador = p            // Perro satisface Hablador
    fmt.Println(p.Presentarse(), h.Hablar())
}

🧱 Principios SOLID

Los principios SOLID

Cinco reglas para escribir código más comprensible, flexible y fácil de mantener

📜 Un poco de historia

Robert C. Martin ("Uncle Bob") presentó estos principios en su artículo de 2000 Design Principles and Design Patterns. Más tarde, Michael Feathers propuso el acrónimo SOLID.

Su objetivo: evitar que el software se vuelva rígido (difícil de cambiar), frágil (se rompe al cambiarlo) e inmóvil (imposible de reutilizar).

🧱 SOLIDS · 1 / 2

S — Principio de Responsabilidad Única

Single Responsibility Principle (SRP)

📏 Enunciado

Un módulo (en Go: un tipo o un paquete) debe tener una sola responsabilidad, es decir, una única razón para cambiar.

type Factura struct {
    Libro         Libro
    Cantidad      int
    TasaDescuento float64
    TasaImpuesto  float64
}

// Responsabilidad 1: reglas de negocio ✔
func (f Factura) Total() float64 { ... }

// Responsabilidad 2: presentación  ✘
func (f Factura) Imprimir() {
    fmt.Printf("%dx %s ...", f.Cantidad, ...)
}

// Responsabilidad 3: persistencia  ✘
func (f Factura) GuardarArchivo(nombre string) {
    // abre archivo, escribe...
}

😟 ¿Qué está mal?

Factura tiene tres razones para cambiar:

  • Cambian las reglas de descuento o impuestos → negocio.
  • Cambia el formato de impresión (PDF, HTML...) → presentación.
  • Queremos guardar en base de datos o llamar a una API → persistencia.

Mezclar lógica de negocio con impresión o persistencia es uno de los errores más comunes: un cambio en el formato puede romper el cálculo.

💡 Solución

Separar cada responsabilidad en su propio tipo: Factura (calcula), FacturaImpresion (muestra) y FacturaPersistencia (guarda).

🧱 SOLIDS · 2 / 2 · Go

SRP aplicado en Go

type Libro struct {
    Nombre, Autor string
    Precio        float64
}

// Factura: SOLO sabe calcular. Su única razón para cambiar
// es un cambio en las reglas de negocio de la facturación.
type Factura struct {
    Libro         Libro
    Cantidad      int
    TasaDescuento float64
    TasaImpuesto  float64
}

func (f Factura) Total() float64 {
    precio := (f.Libro.Precio - f.Libro.Precio*f.TasaDescuento) * float64(f.Cantidad)
    return precio * (1 + f.TasaImpuesto)
}

// FacturaImpresion: única responsabilidad -> presentar la factura.
type FacturaImpresion struct{ factura Factura }

func (fi FacturaImpresion) Imprimir() {
    f := fi.factura
    fmt.Printf("%dx %s %.2f$\n", f.Cantidad, f.Libro.Nombre, f.Libro.Precio)
    fmt.Printf("Descuento: %.0f%%  Impuesto: %.0f%%\n", f.TasaDescuento*100, f.TasaImpuesto*100)
    fmt.Printf("Total: %.2f$\n", f.Total())
}

// FacturaPersistencia: única responsabilidad -> guardar la factura.
type FacturaPersistencia struct{ factura Factura }

func (fp FacturaPersistencia) GuardarArchivo(nombre string) {
    fmt.Printf("Guardando factura de %q en %s\n", fp.factura.Libro.Nombre, nombre)
}

func main() {
    libro := Libro{Nombre: "El Quijote", Autor: "Cervantes", Precio: 50}
    f := Factura{Libro: libro, Cantidad: 2, TasaDescuento: 0.10, TasaImpuesto: 0.19}

    FacturaImpresion{f}.Imprimir()
    FacturaPersistencia{f}.GuardarArchivo("factura.txt")
}
  1. Factura conserva solo los datos y el cálculo de Total().
  2. FacturaImpresion recibe una factura y decide cómo se ve.
  3. FacturaPersistencia decide dónde se guarda.
  4. Cambiar el formato de impresión ya no puede romper el cálculo del total.

🧱 SOLIDO · 1 / 2

O — Principio Abierto / Cerrado

Open/Closed Principle (OCP) — Bertrand Meyer, 1988

📏 Enunciado

Las entidades de software deben estar abiertas a la extensión (agregar comportamiento nuevo) pero cerradas a la modificación (sin cambiar el código existente, ya probado).

type FacturaPersistencia struct {
    factura Factura
}

func (p FacturaPersistencia) GuardarArchivo(nombre string) { ... }

// El jefe pide base de datos -> EDITAMOS el tipo
func (p FacturaPersistencia) GuardarEnBaseDatos() { ... }

// Luego MongoDB -> EDITAMOS otra vez...
func (p FacturaPersistencia) GuardarEnMongo() { ... }

// ...y todo el que lo usa debe cambiar con un switch:
switch destino {
case "archivo": p.GuardarArchivo("f.txt")
case "bd":      p.GuardarEnBaseDatos()
case "mongo":   p.GuardarEnMongo()
}

😟 El problema

Cada vez que modificamos código existente corremos el riesgo de introducir errores en algo que ya funcionaba. Además, los switch por tipo se riegan por todo el programa.

💡 La solución: abstracción

Convertir FacturaPersistencia en una interfaz con un método Guardar. Cada nuevo destino es un tipo nuevo que la implementa: extendemos agregando código, no editándolo.

Este es el principio detrás de Strategy, Decorator, Observer, Visitor...

🧱 SOLIDO · 2 / 2 · Go

OCP aplicado en Go

type Factura struct {
    ID    int
    Total float64
}

// Abstracción estable: CERRADA a modificación.
type FacturaPersistencia interface {
    Guardar(f Factura) error
}

// Extensiones: cada nueva forma de guardar es un tipo NUEVO.
type ArchivoPersistencia struct{ Ruta string }

func (a ArchivoPersistencia) Guardar(f Factura) error {
    fmt.Printf("[archivo] factura #%d -> %s\n", f.ID, a.Ruta)
    return nil
}

type BaseDeDatosPersistencia struct{ Tabla string }

func (b BaseDeDatosPersistencia) Guardar(f Factura) error {
    fmt.Printf("[postgres] INSERT INTO %s VALUES (%d, %.2f)\n", b.Tabla, f.ID, f.Total)
    return nil
}

// Agregado meses después SIN tocar nada de lo anterior.
type MongoPersistencia struct{ Coleccion string }

func (m MongoPersistencia) Guardar(f Factura) error {
    fmt.Printf("[mongo] %s.insertOne({id: %d})\n", m.Coleccion, f.ID)
    return nil
}

// Este código nunca cambia aunque aparezcan nuevos almacenamientos.
func GuardarTodas(p FacturaPersistencia, facturas []Factura) {
    for _, f := range facturas {
        if err := p.Guardar(f); err != nil {
            fmt.Println("error:", err)
        }
    }
}

func main() {
    facturas := []Factura{{1, 107.1}, {2, 59.5}}
    destinos := []FacturaPersistencia{
        ArchivoPersistencia{"facturas.txt"},
        BaseDeDatosPersistencia{"facturas"},
        MongoPersistencia{"facturas"},
    }
    for _, d := range destinos {
        GuardarTodas(d, facturas)
    }
}
  1. La interfaz FacturaPersistencia es el punto de extensión.
  2. GuardarTodas depende solo de la interfaz: está cerrada.
  3. Agregar MongoPersistencia no requirió modificar ninguna línea existente: el sistema está abierto.

🧱 SOLIDL · 1 / 2

L — Principio de Sustitución de Liskov

Liskov Substitution Principle (LSP) — Barbara Liskov, 1987

📏 Enunciado

Los subtipos deben poder sustituir a su tipo base sin alterar el correcto funcionamiento del programa. Si B es un subtipo de A, cualquier código que use un A debe funcionar igual con un B, sin resultados extraños.

🟥 El ejemplo clásico: Rectángulo vs. Cuadrado

En matemáticas un cuadrado "es un" rectángulo. Así que en Java hacemos Cuadrado extends Rectangulo y sobrescribimos los setters para que setAncho también cambie el alto (y viceversa).

Un cliente que hace setAncho(5); setAlto(4) espera un área de 20... pero con un cuadrado obtiene 16. 💥

El subtipo reduce las garantías del tipo base en lugar de extenderlas. El error es difícil de detectar porque el código compila perfectamente.

🐹 ¿Y en Go, que no tiene herencia?

LSP aplica igual a las interfaces: un tipo que satisface una interfaz debe respetar su contrato implícito, no solo sus firmas.

  • No lanzar panic("no implementado") en métodos de la interfaz.
  • No exigir más precondiciones que el contrato.
  • No entregar menos de lo prometido (postcondiciones).
  • Ej: un io.Reader debe devolver io.EOF al terminar, como todos.

⚠️ Regla práctica

Si para que un tipo "encaje" tienes que sobrescribir un método para que haga algo distinto o nada, o tu cliente necesita preguntar if _, ok := x.(Cuadrado), probablemente estás violando LSP.

🧱 SOLIDL · 2 / 2 · Go

LSP en Go: violación y corrección

// ❌ VIOLACIÓN: una interfaz con setters que Cuadrado no puede cumplir.
type RectanguloMutable interface {
    SetAncho(w float64)
    SetAlto(h float64)
    Area() float64
}

type Rectangulo struct{ ancho, alto float64 }

func (r *Rectangulo) SetAncho(w float64) { r.ancho = w }
func (r *Rectangulo) SetAlto(h float64)  { r.alto = h }
func (r *Rectangulo) Area() float64      { return r.ancho * r.alto }

type Cuadrado struct{ lado float64 }

func (c *Cuadrado) SetAncho(w float64) { c.lado = w } // cambia ambos lados
func (c *Cuadrado) SetAlto(h float64)  { c.lado = h } // cambia ambos lados
func (c *Cuadrado) Area() float64      { return c.lado * c.lado }

// El cliente confía en el contrato: "ancho y alto son independientes".
func PruebaArea(r RectanguloMutable) {
    r.SetAncho(5)
    r.SetAlto(4)
    fmt.Printf("%-16T área esperada 20, obtenida %.0f\n", r, r.Area())
}

// ✅ SOLUCIÓN: un contrato que TODOS pueden cumplir.
type Forma interface{ Area() float64 }

type Rect struct{ Ancho, Alto float64 }
type Cuad struct{ Lado float64 }

func (r Rect) Area() float64 { return r.Ancho * r.Alto }
func (c Cuad) Area() float64 { return c.Lado * c.Lado }

func AreaTotal(formas ...Forma) (t float64) {
    for _, f := range formas {
        t += f.Area()
    }
    return
}

func main() {
    PruebaArea(&Rectangulo{})
    PruebaArea(&Cuadrado{}) // 💥 rompe la expectativa del cliente

    fmt.Println("Área total:", AreaTotal(Rect{5, 4}, Cuad{3}))
}
  1. Cuadrado compila como RectanguloMutable, pero no respeta su contrato.
  2. PruebaArea obtiene 16 en lugar de 20: la sustitución no es segura.
  3. La corrección: modelar una abstracción más honesta (Forma) que todos los tipos pueden cumplir sin trucos, y valores inmutables.

*main.Cuadrado   área esperada 20, obtenida 16

I — Principio de Segregación de Interfaces

Interface Segregation Principle (ISP)

📏 Enunciado

Ningún cliente debe ser forzado a depender de métodos que no utiliza. Es mejor tener muchas interfaces pequeñas y específicas que una interfaz grande de propósito general.

type Estacionamiento interface {
    // lógica de estacionamiento
    Aparcar(c Coche)
    Sacar(c Coche)
    Capacidad() int
    // lógica de pagos
    CalcularTarifa(c Coche) float64
    HacerPago(c Coche)
}

type EstacionamientoGratis struct{ ... }

// Obligado a implementar pagos que no tienen sentido 😩
func (e *EstacionamientoGratis) CalcularTarifa(c Coche) float64 {
    return 0
}
func (e *EstacionamientoGratis) HacerPago(c Coche) {
    panic("¡este estacionamiento es gratis!")
}

😟 El problema

La interfaz mezcla dos responsabilidades: estacionar y cobrar. El estacionamiento gratuito queda obligado a escribir métodos vacíos o que hacen panic (¡lo que además viola Liskov!).

💡 La solución

Separar (segregar) la interfaz en Estacionamiento y Pagable. Cada tipo implementa solo lo que necesita. Incluso podríamos dividir Pagable por tipo de pago.

🐹

Go ama el ISP

io.Reader, io.Writer, fmt.Stringer, error: interfaces de un solo método que se combinan (io.ReadWriter).

🧱 SOLIDI · 2 / 2 · Go

ISP aplicado en Go

type Coche struct{ Placa string }

// ✅ Interfaces pequeñas y enfocadas (en vez de una "Estacionamiento" gigante).
type Estacionamiento interface {
    Aparcar(c Coche)
    Sacar(c Coche)
    Capacidad() int
}

type Pagable interface {
    CalcularTarifa(c Coche, horas int) float64
}

// base reutilizable por composición (embedding)
type base struct {
    cupos   int
    ocupado map[string]bool
}

func (b *base) Aparcar(c Coche) { b.ocupado[c.Placa] = true; fmt.Println("  entra", c.Placa) }
func (b *base) Sacar(c Coche)   { delete(b.ocupado, c.Placa); fmt.Println("  sale ", c.Placa) }
func (b *base) Capacidad() int  { return b.cupos - len(b.ocupado) }

// Gratis: implementa SOLO lo que necesita. Nada de métodos de pago vacíos.
type EstacionamientoGratis struct{ *base }

// Pagado: implementa Estacionamiento + Pagable.
type EstacionamientoPagado struct {
    *base
    precioHora float64
}

func (e EstacionamientoPagado) CalcularTarifa(_ Coche, horas int) float64 {
    return float64(horas) * e.precioHora
}

func nuevaBase(n int) *base { return &base{cupos: n, ocupado: map[string]bool{}} }

func main() {
    auto := Coche{"ABC-123"}
    lugares := []Estacionamiento{
        EstacionamientoGratis{nuevaBase(10)},
        EstacionamientoPagado{nuevaBase(5), 3000},
    }
    for _, e := range lugares {
        fmt.Printf("%T\n", e)
        e.Aparcar(auto)
        // Solo preguntamos por el pago a quien lo soporta
        if p, ok := e.(Pagable); ok {
            fmt.Printf("  tarifa 2h: $%.0f\n", p.CalcularTarifa(auto, 2))
        }
        e.Sacar(auto)
        fmt.Println("  cupos libres:", e.Capacidad())
    }
}
  1. Dos interfaces pequeñas: Estacionamiento y Pagable.
  2. La lógica común vive en base y se embebe (composición en lugar de herencia).
  3. EstacionamientoGratis ni siquiera sabe que existen los pagos.
  4. La type assertion e.(Pagable) permite preguntar por una capacidad opcional.

🧱 SOLIDD · 1 / 2

D — Principio de Inversión de Dependencias

Dependency Inversion Principle (DIP)

📏 Enunciado

Los módulos de alto nivel no deben depender de módulos de bajo nivel: ambos deben depender de abstracciones. Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones.

SIN DIP (la dependencia apunta al detalle) ┌──────────────────────────┐ │ AdministradorPersistencia│ alto nivel └────────────┬─────────────┘ │ usa directamente ▼ ┌──────────────────────────┐ │ MySQLFacturas │ bajo nivel └──────────────────────────┘ CON DIP (ambos dependen de la abstracción) ┌──────────────────────────┐ │ AdministradorPersistencia│ └────────────┬─────────────┘ │ depende de ▼ ┌──────────────────────────┐ │ «interface» │ │ FacturaPersistencia │ └────────────▲─────────────┘ │ implementa (¡la flecha se invierte!) ┌─────────┴─────────┐ MySQLFacturas FakeFacturas

🔁 ¿Qué se "invierte"?

Normalmente la lógica de negocio llama al código de infraestructura y por tanto depende de él. Con DIP, la lógica de negocio define la interfaz que necesita y la infraestructura se adapta a ella.

🤝 Relación con OCP

Como dice el artículo citando al tío Bob: "si OCP establece el objetivo de la arquitectura OO, DIP establece el mecanismo principal".

💉 Inyección de dependencias

La técnica habitual para aplicar DIP: el objeto recibe sus dependencias (por constructor) en vez de crearlas. Esto permite cambiar MySQL por un fake en las pruebas.

🧱 SOLIDD · 2 / 2 · Go

DIP aplicado en Go

type Factura struct{ ID int }
type Libro struct{ ISBN string }

// Abstracciones (las define quien las USA, no quien las implementa)
type FacturaPersistencia interface{ Guardar(Factura) }
type LibroPersistencia interface{ Guardar(Libro) }

// Módulo de ALTO nivel: depende solo de interfaces.
type AdministradorPersistencia struct {
    facturas FacturaPersistencia
    libros   LibroPersistencia
}

// Inyección de dependencias por constructor
func NewAdministrador(f FacturaPersistencia, l LibroPersistencia) *AdministradorPersistencia {
    return &AdministradorPersistencia{facturas: f, libros: l}
}

func (a *AdministradorPersistencia) Respaldar(fs []Factura, ls []Libro) {
    for _, f := range fs {
        a.facturas.Guardar(f)
    }
    for _, l := range ls {
        a.libros.Guardar(l)
    }
}

// Módulos de BAJO nivel: detalles intercambiables.
type MySQLFacturas struct{}

func (MySQLFacturas) Guardar(f Factura) { fmt.Println("MySQL   <- factura", f.ID) }

type MemoriaLibros struct{ datos []Libro }

func (m *MemoriaLibros) Guardar(l Libro) {
    m.datos = append(m.datos, l)
    fmt.Println("Memoria <- libro", l.ISBN)
}

// Un doble de prueba: cambiar el detalle no toca el alto nivel.
type FakeFacturas struct{ n int }

func (f *FakeFacturas) Guardar(Factura) { f.n++ }

func main() {
    admin := NewAdministrador(MySQLFacturas{}, &MemoriaLibros{})
    admin.Respaldar([]Factura{{1}, {2}}, []Libro{{"978-84"}})

    fake := &FakeFacturas{}
    NewAdministrador(fake, &MemoriaLibros{}).Respaldar([]Factura{{1}, {2}, {3}}, nil)
    fmt.Println("En pruebas se guardaron", fake.n, "facturas")
}
  1. AdministradorPersistencia (alto nivel) solo conoce interfaces.
  2. Las dependencias se inyectan en NewAdministrador.
  3. MySQL, memoria o un fake son detalles intercambiables.
  4. Probar la lógica no requiere una base de datos real.

¿Qué es un patrón de diseño?

Soluciones típicas a problemas comunes en el diseño de software

📐 Definición

Un patrón de diseño es como un plano prefabricado que puedes personalizar para resolver un problema de diseño que se repite en tu código. No es un fragmento de código que se copia y pega, sino un concepto general que describe cómo resolver un problema concreto.

🍳 Patrón vs. Algoritmo

A menudo se confunden porque ambos describen soluciones típicas. Pero:

  • Un algoritmo es como una receta de cocina: pasos claros y concretos para llegar a un objetivo (ej. Dijkstra).
  • Un patrón es como un plano de arquitecto: ves el resultado y sus características, pero el orden exacto de implementación depende de ti.

Por eso, el mismo patrón aplicado en dos programas distintos puede verse muy diferente en el código.

📋 ¿Qué contiene la descripción de un patrón?

  1. Propósito: describe brevemente el problema y la solución.
  2. Motivación: explica en detalle el problema y cómo el patrón lo resuelve.
  3. Estructura: muestra cada parte del patrón y cómo se relacionan (diagrama de clases).
  4. Ejemplo de código: en algún lenguaje popular, para facilitar la comprensión.

Además: aplicabilidad, pasos de implementación y relaciones con otros patrones. Así está organizada cada sección de esta clase.

Historia, ventajas y críticas

Los patrones no se inventaron: se descubrieron observando soluciones que se repetían

📜 Historia

  • 1977 — El arquitecto Christopher Alexander publica A Pattern Language: un "lenguaje" de patrones para diseñar ciudades y edificios (¿qué tan altas deben ser las ventanas?, ¿cuántos niveles debe tener un edificio?).
  • 1994 — Erich Gamma, John Vlissides, Ralph Johnson y Richard Helm aplican la idea al software en Design Patterns: Elements of Reusable Object-Oriented Software, con 23 patrones.
  • Por el largo nombre, se le conoce como "el libro de la Banda de los Cuatro" (Gang of Four, GoF).

✅ ¿Por qué aprenderlos?

  • Son un kit de herramientas de soluciones probadas a problemas comunes. Aunque nunca te topes con estos problemas, conocerlos te enseña a resolver problemas con principios de diseño orientado a objetos.
  • Definen un lenguaje común para el equipo: basta decir "usa un Observer aquí" y todos entienden la idea sin explicar clases y métodos.
  • Muchos frameworks y librerías los usan: reconocerlos te ayuda a leer código ajeno.

⚠️ Críticas

  • Parches para un lenguaje débil: algunos patrones existen porque el lenguaje carece de una abstracción. Ej: Strategy puede ser simplemente una función anónima en lenguajes modernos (¡como Go!).
  • Soluciones ineficientes: aplicarlos al pie de la letra, sin adaptarlos al contexto.
  • Uso injustificado: "Si todo lo que tienes es un martillo, todo parece un clavo". El novato quiere aplicar patrones en todas partes, incluso donde un código simple bastaría.
🐹

Patrones en Go: con criterio

La comunidad Go valora la simplicidad. Varios patrones se reducen a una interfaz pequeña o a una función de primera clase. En cada patrón veremos su forma clásica y su forma idiomática en Go. Usa un patrón cuando resuelva un problema real, no para "decorar" el código.

Patrones Creacionales

Mecanismos de creación de objetos que incrementan la flexibilidad y la reutilización del código

❓ El problema común

Crear objetos directamente con literales (&MySQL{...}) en todo el código acopla al cliente a tipos concretos. Cambiar el tipo implica tocar muchos lugares.

💡 La idea común

Encapsular el "qué" y el "cómo" de la creación: el cliente pide un objeto a través de una abstracción y no sabe (ni le importa) qué tipo concreto recibe.

Factory Method

También llamado: Método fábrica, Constructor virtual

🎯 Propósito

Define una interfaz o contrato para crear objetos en una abstracción base, pero delega en los tipos concretos (subclases o implementaciones) la decisión de qué estructura o clase específica instanciar.

😟 Problema

Imagina que desarrollas una aplicación de gestión logística. Al inicio sólo transportas carga por tierra, así que todo tu código instancia directamente objetos Camion. Cuando tu sistema crece y necesitas incorporar transporte marítimo con objetos Barco, descubres que el código cliente está fuertemente acoplado a Camion.

Añadir barcos o aviones obligaría a llenar el código de condicionales (if/switch) preguntando el tipo de transporte en decenas de archivos, haciendo el mantenimiento frágil y costoso.

💡 Solución

Sustituir las llamadas directas de construcción (&Camion{}) por invocaciones a un método fábrica especial (CrearTransporte()) declarado en una interfaz creadora común (Logistica).

Cada variante creadora (LogisticaTerrestre, LogisticaMaritima) implementa ese método devolviendo un producto concreto diferente (Camion o Barco), pero ambos cumplen la misma interfaz Transporte. El código cliente opera con Transporte sin saber cómo fue construido ni de qué tipo concreto se trata.

🌍

Analogía en el mundo real

En una empresa de mensajería nacional, el gerente de envíos sigue siempre el mismo protocolo: "preparar paquete, asignar medio de transporte y despachar". Si la sucursal es terrestre, el encargado de flota asigna un camión; si es portuaria, asigna un buque de carga. El protocolo de despacho no cambia porque confía en que cualquier transporte sabe cómo entregar la mercancía.

🔗 Relación con otros patrones

  • Muchos diseños empiezan con Factory Method (más simple) y evolucionan hacia Abstract Factory, Prototype o Builder cuando necesitan mayor flexibilidad.
  • Abstract Factory suele implementarse como un conjunto de varios Factory Methods.
  • Es una especialización de Template Method para el paso específico de creación de objetos.

🧩 Participantes

  1. Producto (Transporte): declara la interfaz común a todos los objetos que los creadores pueden producir.
  2. Productos Concretos (Camion, Barco): proveen distintas implementaciones de la interfaz del producto.
  3. Creador (Logistica): declara el método fábrica que retorna objetos del tipo Producto; suele acompañarse de lógica de negocio que opera sobre esos productos.
  4. Creadores Concretos (LogisticaTerrestre, LogisticaMaritima): implementan el método fábrica retornando una instancia de un producto concreto específico.

🧭 Aplicabilidad

  • Cuando no conoces de antemano los tipos concretos ni las dependencias exactas de los objetos con los que debe operar tu sistema.
  • Cuando deseas ofrecer a los usuarios de tu biblioteca o paquete un punto de extensión limpio para enchufar sus propios componentes.
  • Cuando necesitas reutilizar objetos existentes (p. ej., desde un pool o caché de conexiones) en vez de instanciar nuevos cada vez.

🛠️ Cómo implementarlo

  1. Haz que todos los productos implementen una misma interfaz con métodos que tengan sentido para todos ellos.
  2. Declara el método fábrica en la interfaz o estructura creadora con tipo de retorno igual a la interfaz del producto.
  3. Sustituye en la lógica de negocio las creaciones directas por llamadas al método fábrica.
  4. Crea un creador concreto para cada variante de producto para que instancie y devuelva el tipo adecuado.

✅ Pros

  • Elimina el acoplamiento fuerte entre la lógica creadora y los productos concretos.
  • Principio de Responsabilidad Única (SRP): concentra el código de creación en un único lugar fácil de mantener.
  • Principio Abierto/Cerrado (OCP): incorpora nuevos tipos de productos sin modificar el código cliente existente.

❌ Contras

  • Puede incrementar la cantidad de tipos y estructuras si se exige crear un creador concreto por cada producto sencillo.

Factory Method en Go

package main

import "fmt"

// 1. Producto (interfaz común a todos los transportes)
type Transporte interface {
	Entregar(carga string) string
}

// 2. Productos Concretos
type Camion struct{ Placa string }

func (c *Camion) Entregar(carga string) string {
	return fmt.Sprintf("🚚 Camión [%s] entrega %q por carretera", c.Placa, carga)
}

type Barco struct{ Nombre string }

func (b *Barco) Entregar(carga string) string {
	return fmt.Sprintf("🚢 Barco %q entrega %q por vía marítima", b.Nombre, carga)
}

// 3. Creador (interfaz con el Factory Method)
type Logistica interface {
	CrearTransporte() Transporte // Factory Method
}

// Lógica de negocio común que trabaja con la interfaz Creador
// sin conocer el tipo concreto de transporte que se creará.
func PlanificarEntrega(l Logistica, carga string) {
	transporte := l.CrearTransporte()
	fmt.Println("📦 Planificando:", transporte.Entregar(carga))
}

// 4. Creadores Concretos (sobrescriben el Factory Method)
type LogisticaTerrestre struct{ PlacaAsignada string }

func (lt *LogisticaTerrestre) CrearTransporte() Transporte {
	return &Camion{Placa: lt.PlacaAsignada}
}

type LogisticaMaritima struct{ BuqueAsignado string }

func (lm *LogisticaMaritima) CrearTransporte() Transporte {
	return &Barco{Nombre: lm.BuqueAsignado}
}

func main() {
	terrestre := &LogisticaTerrestre{PlacaAsignada: "ABC-123"}
	maritima := &LogisticaMaritima{BuqueAsignado: "El Navegante"}

	PlanificarEntrega(terrestre, "Electrónicos")
	PlanificarEntrega(maritima, "Contenedores de grano")
}

🔍 Explicación paso a paso

  1. Transporte define el contrato del Producto con el método Entregar.
  2. Camion y Barco implementan implícitamente Transporte cada uno a su manera.
  3. Logistica declara el Factory Method CrearTransporte() Transporte.
  4. PlanificarEntrega contiene la lógica de negocio reutilizable: pide un transporte a la fábrica y lo usa sin acoplarse a camiones ni barcos.
  5. Si mañana agregamos LogisticaAerea y Avion, PlanificarEntrega no sufre ni un solo cambio.
📦 Planificando: 🚚 Camión [ABC-123] entrega "Electrónicos" por carretera
📦 Planificando: 🚢 Barco "El Navegante" entrega "Contenedores de grano" por vía marítima
🐹

Nota idiomática en Go

Como Go no tiene clases abstractas ni herencia, la lógica común (PlanificarEntrega) se escribe como una función que recibe la interfaz Logistica (o mediante embedding), y a menudo un simple constructor NewTransporte(tipo) o un tipo función type CreadorTransporte func() Transporte basta cuando no hay estado adicional en el creador.

Abstract Factory

También llamado: Fábrica abstracta, Kit

🎯 Propósito

Permite producir familias de objetos relacionados o dependientes entre sí sin especificar sus tipos o clases concretas, garantizando que los objetos creados sean siempre compatibles.

😟 Problema

Imagina un simulador de tienda de muebles o un toolkit de interfaz gráfica multiplataforma. Tienes una familia de productos que trabajan juntos (p. ej. Boton + Casilla, o Silla + Sofa + Mesilla) y varias variantes o estilos (Windows vs. macOS, o Moderno vs. Victoriano).

Si el código cliente instancia widgets o muebles sueltos directamente, es muy fácil mezclar por error un botón de Windows con una casilla de macOS, o llenar la aplicación de condicionales cada vez que se agrega un nuevo sistema operativo o catálogo.

💡 Solución

Declarar primero una interfaz para cada producto de la familia (Boton, Casilla) y luego una interfaz Fábrica Abstracta (FabricaGUI) con métodos de creación para todos los productos de la familia (CrearBoton(), CrearCasilla()).

Por cada variante o estilo se implementa una Fábrica Concreta (FabricaWindows, FabricaMac) que produce únicamente objetos de esa misma familia. El cliente recibe una fábrica abstracta al iniciar y todos los elementos que solicita combinan entre sí automáticamente.

🛋️

Analogía en el mundo real

Cuando compras un juego de sala por catálogo, eliges primero la línea de diseño (por ejemplo, Escandinava o Industrial). A partir de ese proveedor pides una silla, un sofá y una mesa de centro: sin importar qué pieza pidas, todas comparten materiales, colores y proporciones compatibles entre sí.

🔗 Relación con otros patrones

  • Suele construirse a partir de varios Factory Methods o apoyarse en Prototype para clonar familias de productos.
  • Mientras Abstract Factory devuelve familias de objetos de inmediato, Builder construye un único objeto complejo paso a paso.
  • Las fábricas concretas suelen implementarse como Singletons.

🧩 Participantes

  1. Productos Abstractos (Boton, Casilla): interfaces para cada tipo de componente distinto que integra la familia.
  2. Productos Concretos (BotonWindows, BotonMac, etc.): implementaciones de los productos agrupadas por variante.
  3. Fábrica Abstracta (FabricaGUI): declara los métodos para crear cada uno de los productos abstractos de la familia.
  4. Fábricas Concretas (FabricaWindows, FabricaMac): implementan los métodos de creación devolviendo productos de una única variante compatible.
  5. Cliente (RenderizarPantalla): trabaja exclusivamente con las interfaces FabricaGUI, Boton y Casilla.

🧭 Aplicabilidad

  • Cuando el código necesita trabajar con diversas familias de productos relacionados sin depender de sus clases concretas.
  • Cuando es indispensable garantizar que los productos creados en un contexto pertenezcan siempre a la misma variante o tema.
  • Cuando una clase acumula múltiples Factory Methods que empañan su responsabilidad principal.

🛠️ Cómo implementarlo

  1. Traza una matriz de tipos de productos (filas) frente a variantes de familia (columnas).
  2. Declara interfaces de producto abstracto para cada tipo e impleméntalas en las variantes concretas.
  3. Define la interfaz de la fábrica abstracta con un método de creación por cada producto abstracto.
  4. Crea una estructura de fábrica concreta por cada variante e inyéctala al código cliente durante la inicialización.

✅ Pros

  • Garantiza al 100% que los productos que recibe el cliente sean compatibles entre sí.
  • Desacopla el código cliente de los tipos concretos (cumple SRP y OCP al agregar nuevas variantes completas).

❌ Contras

  • Añade bastantes interfaces y tipos nuevos; además, agregar un nuevo tipo de producto a la familia requiere modificar la interfaz de la fábrica y todas sus implementaciones.

Abstract Factory en Go

package main

import "fmt"

// 1. Productos Abstractos (familia de objetos relacionados)
type Boton interface {
	Dibujar() string
}

type Casilla interface {
	Marcar(activo bool) string
}

// 2. Productos Concretos — Variante Windows
type BotonWindows struct{}

func (BotonWindows) Dibujar() string { return "[ 🪟 Botón estilo Windows ]" }

type CasillaWindows struct{}

func (CasillaWindows) Marcar(ok bool) string {
	return fmt.Sprintf("[🪟 Casilla Windows: %v]", ok)
}

// 2. Productos Concretos — Variante Mac
type BotonMac struct{}

func (BotonMac) Dibujar() string { return "( 🍎 Botón estilo macOS )" }

type CasillaMac struct{}

func (CasillaMac) Marcar(ok bool) string {
	return fmt.Sprintf("(🍎 Casilla macOS: %v)", ok)
}

// 3. Fábrica Abstracta (crea una familia completa de productos)
type FabricaGUI interface {
	CrearBoton() Boton
	CrearCasilla() Casilla
}

// 4. Fábricas Concretas (garantizan compatibilidad de la familia)
type FabricaWindows struct{}

func (FabricaWindows) CrearBoton() Boton     { return BotonWindows{} }
func (FabricaWindows) CrearCasilla() Casilla { return CasillaWindows{} }

type FabricaMac struct{}

func (FabricaMac) CrearBoton() Boton     { return BotonMac{} }
func (FabricaMac) CrearCasilla() Casilla { return CasillaMac{} }

// 5. Cliente: usa únicamente las interfaces abstractas
func RenderizarPantalla(f FabricaGUI) {
	boton := f.CrearBoton()
	casilla := f.CrearCasilla()
	fmt.Println(boton.Dibujar(), "->", casilla.Marcar(true))
}

func main() {
	fmt.Println("=== Entorno Windows ===")
	RenderizarPantalla(FabricaWindows{})

	fmt.Println("=== Entorno macOS ===")
	RenderizarPantalla(FabricaMac{})
}

🔍 Explicación paso a paso

  1. Definimos dos productos de una misma familia UI: Boton y Casilla.
  2. Implementamos las variantes Windows y Mac para cada producto.
  3. FabricaGUI agrupa la creación de ambos productos en una sola interfaz cohesiva.
  4. RenderizarPantalla recibe cualquier FabricaGUI: es imposible que mezcle un botón Windows con una casilla Mac.
=== Entorno Windows ===
[ 🪟 Botón estilo Windows ] -> [🪟 Casilla Windows: true]
=== Entorno macOS ===
( 🍎 Botón estilo macOS ) -> (🍎 Casilla macOS: true)
🐹

Nota idiomática en Go

En Go, las fábricas concretas sin estado como FabricaWindows{} son estructuras vacías (zero-size structs, 0 bytes en memoria). Cumplen la interfaz FabricaGUI sin sobrecarga de memoria y permiten inyección de dependencias limpia en tests.

Builder

También llamado: Constructor paso a paso

🎯 Propósito

Permite construir objetos complejos paso a paso, produciendo distintos tipos y representaciones de un objeto empleando exactamente el mismo proceso de construcción.

😟 Problema

Imagina crear un objeto complejo como una Casa o una petición HTTP/SQL con docenas de opciones: paredes, tipo de techo, número de ventanas, calefacción, jardín, piscina, garaje, etc.

Si creas una subclase por cada combinación posible, la jerarquía explota. Y si pones todo en un único constructor gigante de 15 parámetros (constructor telescópico), las llamadas quedan ilegibles y propensas a errores porque la mayoría de los parámetros serán nulos o irrelevantes en el 90% de los casos.

💡 Solución

Extraer el código de ensamblaje fuera del producto y llevarlo a objetos independientes llamados constructores (builders), dividiendo la creación en pasos claros (ConstruirParedes, ConstruirTecho, ConstruirPiscina).

Se pueden definir distintos constructores concretos (p. ej. ConstructorCabana, ConstructorMansion) que ejecutan los mismos pasos con materiales diferentes, y opcionalmente una clase Directora que encapsula recetas u órdenes de construcción reutilizables sin exponer el producto hasta que esté terminado.

🏗️

Analogía en el mundo real

Un maestro de obra (Director) conoce el orden exacto para levantar una vivienda: primero cimientos, luego muros, después techo y finalmente acabados. Si contrata a una cuadrilla rústica (Constructor A), esos mismos pasos producen una cabaña de madera; si contrata a una cuadrilla de lujo (Constructor B), la misma secuencia entrega una mansión moderna con piscina.

🔗 Relación con otros patrones

  • Builder construye un objeto complejo paso a paso y entrega el resultado al final; Abstract Factory entrega familias de objetos inmediatamente.
  • Es muy útil para construir árboles Composite complejos dado que sus pasos pueden invocarse recursivamente.
  • Al combinarlo con Bridge, el Director actúa como la abstracción y los distintos Builders como las implementaciones.

🧩 Participantes

  1. Interfaz Constructora (ConstructorCasa): declara los pasos de construcción comunes a todas las representaciones.
  2. Constructores Concretos (ConstructorCabana, ConstructorMansion): implementan cada paso de manera específica y guardan el estado intermedio.
  3. Producto (Casa): el objeto complejo resultante tras completar los pasos.
  4. Director: define el orden en que se ejecutan los pasos para crear configuraciones estándar reutilizables.
  5. Cliente: asocia un constructor concreto con el director (o invoca los pasos directamente) y recoge el producto final.

🧭 Aplicabilidad

  • Para eliminar constructores con largas listas de parámetros opcionales (constructor telescópico).
  • Cuando el código debe crear distintas representaciones de un mismo producto (p. ej. cabaña vs. mansión, o automóvil vs. manual) cuyos pasos de montaje son similares.
  • Para ensamblar estructuras complejas o árboles Composite aplazando o repitiendo pasos sin exponer un objeto incompleto.

🛠️ Cómo implementarlo

  1. Identifica y declara en la interfaz constructora los pasos de producción comunes a todas las representaciones.
  2. Crea un constructor concreto por cada representación e incluye un método para extraer el producto terminado y reiniciar el estado.
  3. Opcionalmente, crea una estructura Director que reciba el constructor y ejecute rutinas de pasos predefinidas.

✅ Pros

  • Permite construir objetos paso a paso, aplazar pasos o ejecutarlos de forma condicional/recursiva.
  • Reutiliza el mismo proceso de montaje para distintas representaciones y aísla la construcción compleja de la lógica del producto (SRP).

❌ Contras

  • Aumenta la complejidad general cuando se requiere crear múltiples interfaces y estructuras constructoras para objetos simples.

func (b *ConstructorMansion) ConstruirTecho()    { b.casa.Techo = "Terraza solar" }
func (b *ConstructorMansion) ConstruirVentanas() { b.casa.Ventanas = 12 }
func (b *ConstructorMansion) ConstruirPiscina()  { b.casa.ConPiscina = true }
func (b *ConstructorMansion) ObtenerCasa() Casa  { return b.casa }

// 4. Director (define el orden de los pasos de construcción)
type Director struct{ constructor ConstructorCasa }

func (d *Director) CambiarConstructor(c ConstructorCasa) { d.constructor = c }

func (d *Director) ConstruirCompleta() Casa {
	d.constructor.Reiniciar()
	d.constructor.ConstruirParedes()
	d.constructor.ConstruirTecho()
	d.constructor.ConstruirVentanas()
	d.constructor.ConstruirPiscina()
	return d.constructor.ObtenerCasa()
}

Prototype

También llamado: Prototipo, Clon, Clone

🎯 Propósito

Permite copiar objetos existentes de forma independiente a sus clases o estructuras concretas, delegando el proceso de clonación al propio objeto que se desea duplicar.

😟 Problema

Supón que tienes un objeto complejo configurado en memoria y necesitas crear una copia exacta de él. Si intentas copiarlo "desde fuera", tu código cliente primero debe conocer la estructura concreta para instanciarla (acoplándose a ella) y luego recorrer todos sus campos.

Peor aún: muchos campos pueden ser privados (no exportados en Go) e inaccesibles desde otros paquetes, o el código cliente sólo recibe el objeto a través de una interfaz general y ni siquiera sabe cuál es su tipo concreto real.

💡 Solución

El patrón Prototype declara una interfaz común (p. ej. Prototipo) con un método Clonar(). Cada estructura concreta implementa Clonar() creando una nueva instancia de su propio tipo y copiando todos sus campos internos (incluidos los privados y las estructuras anidadas).

Así, el cliente puede duplicar cualquier objeto o árbol de objetos llamando simplemente a objeto.Clonar(), o mantener un registro de prototipos preconfigurados listos para clonarse bajo demanda.

🧬

Analogía en el mundo real

La división mitótica de una célula en biología: ningún agente externo ensambla una célula nueva átomo por átomo desde fuera; es la propia célula original (el prototipo) quien duplica su ADN e información interna para dar origen a un clon idéntico e independiente.

  • Abstract Factory puede almacenar un catálogo de prototipos y clonarlos en lugar de usar Factory Methods.
  • Los diseños con árboles Composite o Decorator usan Prototype para clonar estructuras complejas enteras de una sola vez.
  • Puede servir como alternativa sencilla a Memento o para guardar copias de Command en un historial.

🧩 Participantes

  1. Interfaz Prototipo (Prototipo): declara el método de clonación (Clonar()) que retorna la propia abstracción.
  2. Prototipos Concretos (Archivo, Carpeta): implementan Clonar() copiando sus valores primitivos y duplicando recursivamente sus referencias (slices, mapas, punteros) para evitar efectos colaterales.
  3. Cliente: solicita una copia invocando Clonar() en cualquier objeto que cumpla la interfaz, o consulta un Registro de Prototipos por nombre.

🧭 Aplicabilidad

  • Cuando tu código necesita copiar objetos pero no debe depender de sus tipos concretos (porque los recibe mediante una interfaz).
  • Cuando quieres evitar crear subclases que sólo difieren en cómo inicializan sus atributos, usando en su lugar un catálogo de prototipos preconfigurados.

🛠️ Cómo implementarlo

  1. Declara la interfaz Prototipo con el método Clonar().
  2. Implementa Clonar() en cada estructura concreta instanciando un nuevo objeto del mismo tipo y copiando todos sus campos (cuidando la copia profunda en punteros, slices y mapas).
  3. Opcionalmente, crea un mapa o registro de prototipos frecuentes indexado por clave para clonarlos cuando el cliente los pida.

✅ Pros

  • Permite clonar objetos sin acoplarse a sus clases o estructuras concretas.
  • Evita repetir código de inicialización costoso y facilita duplicar estructuras jerárquicas complejas.

❌ Contras

  • Clonar objetos complejos con punteros compartidos o referencias circulares requiere implementar copias profundas (deep copy) cuidadosas.

Prototype en Go

package main

import "fmt"

// 1. Interfaz Prototipo (declara el método de clonación)
type Prototipo interface {
	Clonar() Prototipo
	Mostrar(indent string)
}

// 2. Prototipo Concreto A: Archivo
type Archivo struct {
	Nombre   string
	Etiqueta []string // slice para demostrar copia profunda (deep copy)
}

func (a *Archivo) Mostrar(indent string) {
	fmt.Printf("%s📄 %s (tags: %v)\n", indent, a.Nombre, a.Etiqueta)
}

func (a *Archivo) Clonar() Prototipo {
	copiaTags := make([]string, len(a.Etiqueta))
	copy(copiaTags, a.Etiqueta)
	return &Archivo{Nombre: a.Nombre + "_copia", Etiqueta: copiaTags}
}

// 2. Prototipo Concreto B: Carpeta (contiene otros Prototipos)
type Carpeta struct {
	Nombre    string
	Elementos []Prototipo
}

func (c *Carpeta) Mostrar(indent string) {
	fmt.Printf("%s📁 %s/\n", indent, c.Nombre)
	for _, elem := range c.Elementos {
		elem.Mostrar(indent + "   ")
	}
}

func (c *Carpeta) Clonar() Prototipo {
	clon := &Carpeta{
		Nombre:    c.Nombre + "_clon",
		Elementos: make([]Prototipo, len(c.Elementos)),
	}
	for i, elem := range c.Elementos {
		clon.Elementos[i] = elem.Clonar() // clona recursivamente sin saber el tipo concreto
	}
	return clon
}

func main() {
	doc := &Archivo{Nombre: "informe.pdf", Etiqueta: []string{"v1", "oficial"}}
	orig := &Carpeta{
		Nombre:    "Proyecto",
		Elementos: []Prototipo{doc, &Archivo{Nombre: "datos.csv", Etiqueta: []string{"raw"}}},
	}

	// 3. El cliente clona la estructura completa a través de la interfaz Prototipo
	copia := orig.Clonar()
	doc.Etiqueta[0] = "MODIFICADO" // no afecta al clon gracias a la copia profunda

	fmt.Println("--- Original (tras modificar doc) ---")
	orig.Mostrar("")
	fmt.Println("--- Clon independiente ---")
	copia.Mostrar("")
}

🔍 Explicación paso a paso

  1. Prototipo declara Clonar() Prototipo.
  2. En Archivo.Clonar() creamos un nuevo slice con make y copy para hacer una copia profunda de Etiqueta.
  3. Carpeta.Clonar() recorre sus hijos []Prototipo e invoca polimórficamente elem.Clonar() sin saber si cada elemento es un archivo o una subcarpeta.
  4. Al mutar doc.Etiqueta[0] en el original, el clon permanece intacto.

   📄 informe.pdf (tags: [MODIFICADO oficial])
   📄 datos.csv (tags: [raw])
--- Clon independiente ---
📁 Proyecto_clon/

   📄 datos.csv_copia (tags: [raw])

Nota idiomática en Go

En Go, asignar un struct por valor (copia := *original) realiza una copia superficial (shallow copy): los campos slice, map o punteros seguirán apuntando a la misma memoria subyacente. Por eso un método Clonar() explícito con copy() o slices.Clone() es esencial.

Singleton

También llamado: Instancia única

🎯 Propósito

Garantiza que una estructura o clase tenga una única instancia en toda la ejecución del programa y proporciona un punto de acceso global y seguro a dicha instancia.

😟 Problema

El patrón Singleton aborda dos problemas a la vez:

  1. Garantizar una única instancia: recursos compartidos como un pool de base de datos, un registro de configuración o un sistema de archivos no deben instanciarse decenas de veces desperdiciando memoria o desincronizando el estado.
  2. Acceso global controlado: una variable global ordinaria permite acceder al objeto desde cualquier lugar, pero es peligrosa porque cualquier paquete podría sobrescribirla accidentalmente o provocar condiciones de carrera entre hilos/goroutines.

💡 Solución

Ocultar o restringir la construcción directa del tipo y exponer una función de acceso global (como ObtenerBD()) que actúa como único punto de entrada.

La primera vez que se invoca esta función, se crea el objeto de forma perezosa (lazy initialization) con bloqueo seguro para concurrencia y se guarda en una variable privada del paquete; todas las llamadas posteriores devuelven exactamente la misma referencia almacenada en caché.

🏛️

Analogía en el mundo real

El Gobierno oficial de un país es un Singleton natural: un país sólo puede tener un gobierno activo a la vez. Sin importar qué ciudadanos o instituciones interactúen con él, la figura "Gobierno de Colombia" funciona como el punto de acceso global que refiere siempre a la misma entidad institucional.

🔗 Relación con otros patrones

  • Una estructura Facade suele convertirse en Singleton porque un único objeto fachada basta en casi todos los casos.
  • A diferencia de Flyweight (que puede tener múltiples instancias inmutables con estado intrínseco distinto), Singleton tiene una sola instancia que suele ser mutable.
  • Abstract Factory, Builder y Prototype frecuentemente se implementan como Singletons.

🧩 Participantes

  1. Singleton (ConexionBD + ObtenerBD()): mantiene en variables privadas a nivel de paquete la referencia única (instancia) y el mecanismo de sincronización (sync.Once). La función pública ObtenerBD() garantiza que la inicialización ocurra una sola vez incluso ante miles de goroutines concurrentes.

🛠️ Cómo implementarlo

  1. Declara una variable privada en el paquete para guardar el puntero a la instancia única y un sync.Once.
  2. Escribe la función pública ObtenerInstancia() que inicializa el objeto dentro de once.Do(func() { ... }) y retorna la variable privada.
  3. Sustituye en el código cliente las creaciones directas por llamadas a ObtenerInstancia().

🧭 Aplicabilidad

  • Cuando un recurso del programa debe tener estrictamente una única instancia compartida por todos los componentes (p. ej. gestor de conexión a BD, logger centralizado, configuración en memoria).
  • Cuando necesitas reemplazar variables globales desprotegidas por un punto de acceso con inicialización diferida y protegida contra escritura externa.

✅ Pros

  • Certeza absoluta de tener una única instancia y un punto de acceso global conocido.
  • Se inicializa solo cuando se solicita por primera vez (lazy initialization).

❌ Contras

  • Vulnera el Principio de Responsabilidad Única (SRP) al resolver dos problemas a la vez.
  • Puede ocultar acoplamiento global excesivo y dificultar las pruebas unitarias (estado compartido entre tests).

Singleton en Go

package main

import (
	"fmt"
	"sync"
)

// 1. Estructura Singleton (no exportada o con inicialización controlada)
type ConexionBD struct {
	DSN       string
	Consultas int
}

var (
	instancia *ConexionBD
	once      sync.Once // garantiza ejecución única y segura entre goroutines
)

// ObtenerBD es el punto de acceso global al Singleton.
func ObtenerBD() *ConexionBD {
	once.Do(func() {
		fmt.Println("🔌 [sync.Once] Creando la ÚNICA conexión a la base de datos...")
		instancia = &ConexionBD{DSN: "postgres://localhost:5432/produccion"}
	})
	return instancia
}

func (db *ConexionBD) Ejecutar(sql string) {
	db.Consultas++
	fmt.Printf("   [Consulta #%d en %s] -> %s\n", db.Consultas, db.DSN, sql)
}

func main() {
	// Primera llamada: inicializa la instancia única
	bd1 := ObtenerBD()
	bd1.Ejecutar("SELECT * FROM usuarios")

	// Segunda llamada: reutiliza exactamente la misma instancia
	bd2 := ObtenerBD()
	bd2.Ejecutar("INSERT INTO logs VALUES ('login')")

	fmt.Printf("¿bd1 y bd2 apuntan al mismo objeto? %v (total consultas: %d)\n",
		bd1 == bd2, bd1.Consultas)
}

🔍 Explicación paso a paso

  1. instancia y once son variables privadas del paquete (minúscula inicial).
  2. ObtenerBD() envuelve la creación dentro de once.Do(...): la biblioteca estándar de Go garantiza con operaciones atómicas y mutex interno que esa función anónima se ejecute exactamente una vez, incluso si 1000 goroutines llaman a ObtenerBD() al mismo tiempo.
  3. bd1 == bd2 evalúa a true y el contador de consultas refleja que ambas variables apuntan a la misma dirección de memoria.

Adapter

También llamado: Adaptador, Envoltorio, Wrapper

🎯 Propósito

Adapter es un patrón de diseño estructural que permite que objetos con interfaces incompatibles colaboren entre sí mediante un objeto intermediario que traduce las llamadas y formatos de datos.

😟 Problema

Imagina que tu aplicación financiera procesa datos bursátiles en formato XML, o que tu tienda virtual cobra usando una interfaz uniforme ProcesadorPago en dólares. De pronto necesitas integrar una excelente biblioteca de análisis o pasarela de pagos de un tercero, pero esa biblioteca externa solo acepta datos en JSON o importes en centavos enteros con otra firma de método.

No puedes modificar la biblioteca externa (no tienes su código fuente o romperías a otros consumidores), y tampoco quieres ensuciar toda tu lógica de negocio con condicionales y conversiones acopladas al proveedor.

💡 Solución

Crear un Adaptador: una estructura especial que actúa como traductor tras bambalinas. El adaptador:

  1. Implementa la interfaz que el cliente ya conoce y espera.
  2. Envuelve internamente una referencia al objeto de servicio incompatible.
  3. Al recibir una llamada del cliente, transforma los argumentos al formato, unidades y orden que el servicio espera, delega la ejecución y traduce la respuesta si hace falta.
🔌

Analogía en el mundo real

Cuando viajas de América o Europa con tu cargador de portátil a otro continente, la clavija física no entra en el tomacorriente de la pared. No compras otro computador ni cambias el cableado del hotel: colocas un adaptador de enchufe en medio que recibe tus patas planas de un lado y expone clavijas redondas del otro.

  2. Interfaz con el Cliente: protocolo que las estructuras deben cumplir para colaborar con el cliente.
  3. Adaptador: implementa la interfaz del cliente y envuelve al servicio, traduciendo llamadas y formatos.
  4. Servicio (Adaptee): biblioteca de terceros o código legado útil pero con una interfaz incompatible.

🧭 Aplicabilidad

  • Cuando quieres usar un paquete existente (legado o de terceros), pero su interfaz no coincide con el resto de tu diseño.
  • Cuando necesitas reutilizar varios tipos existentes que carecen de cierta funcionalidad común y no puedes modificar su código original.

🛠️ Cómo implementarlo

  1. Identifica el Servicio útil que no puedes cambiar y el Cliente que lo necesita.
  2. Declara la interfaz que el cliente espera consumir.
  3. Crea la estructura adaptadora que implemente dicha interfaz y guarde un campo con referencia al servicio.
  4. Implementa cada método de la interfaz traduciendo tipos/formatos y delegando al servicio.

Ventajas

  • Responsabilidad Única (SRP): separa el código de conversión de datos de la lógica de negocio.
  • Abierto/Cerrado (OCP): puedes añadir nuevos adaptadores para otros proveedores sin tocar el cliente.

Desventajas

  • Aumenta la complejidad general al introducir nuevas interfaces y estructuras envoltorio; si controlas el servicio, a veces es más simple cambiarlo directamente.

🔗 Relación con otros patrones

Adapter cambia la interfaz de un objeto existente para hacerla compatible; Decorator mantiene o amplía la misma interfaz añadiendo responsabilidades; Proxy conserva exactamente la misma interfaz controlando el acceso; Facade define una interfaz nueva y simple para todo un subsistema completo; y Bridge se diseña por anticipado para separar abstracción de implementación.

package main

import "fmt"

// 1. Interfaz con el Cliente: protocolo que el código cliente espera usar.
type ProcesadorPago interface {
	Cobrar(montoUSD float64) string
}

// Servicio compatible existente en nuestra aplicación.
type PasarelaLocal struct{}

func (p PasarelaLocal) Cobrar(montoUSD float64) string {
	return fmt.Sprintf("[PasarelaLocal] Cobro directo procesado: $%.2f USD", montoUSD)
}

// 2. Servicio (incompatible): SDK externo de un tercero que no podemos modificar.
// Usa otro nombre de método, recibe centavos enteros y exige código de moneda.
type SDKStripeExterno struct {
	APIKey string
}

func (s *SDKStripeExterno) CreateChargeInCents(cents int, currency string) string {
	return fmt.Sprintf("[Stripe SDK key=%s] Charge OK: %d cents (%s)", s.APIKey, cents, currency)
}

// 3. Adaptador: implementa ProcesadorPago y envuelve (compone) *SDKStripeExterno.
type AdaptadorStripe struct {
	servicio *SDKStripeExterno
	moneda   string
}

func NuevoAdaptadorStripe(sdk *SDKStripeExterno, moneda string) *AdaptadorStripe {
	return &AdaptadorStripe{servicio: sdk, moneda: moneda}
}

// Cobrar traduce la llamada del cliente al formato y firma que espera el SDK externo.
func (a *AdaptadorStripe) Cobrar(montoUSD float64) string {
	centavos := int(montoUSD * 100) // Conversión de formato: dólares (float64) -> centavos (int)
	respuestaSDK := a.servicio.CreateChargeInCents(centavos, a.moneda)
	return fmt.Sprintf("[Adaptador -> Stripe] %s", respuestaSDK)
}

// 4. Cliente: trabaja únicamente con la interfaz ProcesadorPago sin acoplarse al SDK.
func FinalizarCompra(carrito string, total float64, pasarela ProcesadorPago) {
	fmt.Printf("Cliente pagando %s ($%.2f):\n", carrito, total)
	fmt.Println("  ", pasarela.Cobrar(total))
}

func main() {
	// Uso con el servicio local que ya cumple la interfaz
	local := PasarelaLocal{}
	FinalizarCompra("Curso de Compiladores", 29.99, local)

	// Uso con el servicio incompatible a través del Adaptador
	sdkExterno := &SDKStripeExterno{APIKey: "sk_live_987"}
	adaptador := NuevoAdaptadorStripe(sdkExterno, "USD")
	FinalizarCompra("Suscripción Anual Pro", 149.50, adaptador)
}

🔍 Paso a paso

  1. FinalizarCompra (cliente) exige un ProcesadorPago con el método Cobrar(float64).
  2. SDKStripeExterno no cumple esa interfaz: expone CreateChargeInCents(int, string).
  3. AdaptadorStripe envuelve un puntero *SDKStripeExterno, convierte los dólares float64 a centavos int e invoca al SDK.

Bridge

También llamado: Puente

🎯 Propósito

Bridge es un patrón de diseño estructural que permite dividir una clase grande, o un grupo de clases estrechamente relacionadas, en dos jerarquías separadas —abstracción e implementación— para que puedan evolucionar de manera independiente.

😟 Problema

Supón que tienes una jerarquía de figuras geométricas (Círculo, Cuadrado) y quieres agregarles colores (Rojo, Azul) mediante herencia. Terminas creando combinaciones como CírculoRojo, CírculoAzul, CuadradoRojo, CuadradoAzul.

Cuando extiendes un diseño en dos dimensiones ortogonales (por ejemplo: Forma × Color, o Control Remoto × Dispositivo, o GUI × Sistema Operativo), el número de tipos explota en progresión geométrica (N × M) y cualquier cambio obliga a tocar decenas de estructuras.

💡 Solución

Sustituir la combinación rígida por composición de objetos:

  1. Extraer una de las dimensiones a una jerarquía aparte llamada Implementación (p. ej. Color o Dispositivo).
  2. Mantener la capa de control de alto nivel como Abstracción (p. ej. Forma o ControlRemoto), que guarda un campo con referencia a la interfaz de implementación.
  3. Esa referencia actúa como el puente (bridge): ahora puedes añadir N abstracciones y M implementaciones creando solo N + M tipos en lugar de N × M.
📺

Analogía en el mundo real

Un control remoto universal (abstracción: básico, avanzado, con pantalla táctil) y los aparatos electrónicos (implementación: televisor, radio, proyector). No fabricas un "ControlAvanzadoExclusivoParaRadioSony": el control remoto define botones de alto nivel (subir volumen, silenciar) y se comunica mediante un protocolo común infrarrojo con cualquier dispositivo compatible.

  • Cuando quieres dividir y organizar una estructura monolítica que tiene múltiples variantes de una funcionalidad (p. ej. distintos motores de base de datos o backends de compilación).
  • Cuando necesitas extender un sistema en varias dimensiones ortogonales (independientes).
  • Cuando necesitas cambiar la implementación subyacente en tiempo de ejecución.

🛠️ Cómo implementarlo

  1. Identifica las dimensiones ortogonales (abstracción/plataforma, dominio/infraestructura, frontend/backend).
  2. Declara las operaciones primitivas en la interfaz Implementación y crea sus tipos concretos.
  3. Crea la Abstracción con un campo de tipo interfaz Implementación y delega en él.
  4. El cliente inyecta la implementación concreta al construir la abstracción.

Ventajas

  • Evita la explosión combinatoria de tipos (N + M en vez de N × M).
  • Cumple OCP y SRP: evolucionas la lógica de alto nivel y los detalles de plataforma por separado.

Desventajas

  • Puede complicar innecesariamente el código si se aplica a una clase muy cohesionada que solo varía en una dimensión.

🔗 Relación con otros patrones

Bridge se diseña desde el principio para separar jerarquías independientes, mientras que Adapter se aplica a posteriori para encajar tipos incompatibles. Su estructura de delegación se parece a Strategy, pero Bridge abarca dos jerarquías completas (estructural) mientras Strategy intercambia algoritmos puntuales (comportamiento). Puede combinarse con Abstract Factory para instanciar pares compatibles.

import "fmt"

// 1. Implementación (interfaz de plataforma): operaciones primitivas de bajo nivel.
type Dispositivo interface {
	EstaEncendido() bool
	Encender()
	Apagar()
	Volumen() int
	FijarVolumen(porcentaje int)
	Nombre() string
}

// 2. Implementación Concreta A: Televisor.
type Televisor struct {
	encendido bool
	volumen   int
}

func (t *Televisor) EstaEncendido() bool     { return t.encendido }
func (t *Televisor) Encender()               { t.encendido = true; fmt.Println("  [TV] Encendido") }
func (t *Televisor) Apagar()                 { t.encendido = false; fmt.Println("  [TV] Apagado") }
func (t *Televisor) Volumen() int            { return t.volumen }
func (t *Televisor) FijarVolumen(v int)      { t.volumen = v; fmt.Printf("  [TV] Volumen = %d%%\n", t.volumen) }
func (t *Televisor) Nombre() string          { return "Smart TV 4K" }

// 2. Implementación Concreta B: Radio.
type Radio struct {
	encendido bool
	volumen   int
}

func (r *Radio) EstaEncendido() bool     { return r.encendido }
func (r *Radio) Encender()               { r.encendido = true; fmt.Println("  [Radio] Encendida") }
func (r *Radio) Apagar()                 { r.encendido = false; fmt.Println("  [Radio] Apagada") }
func (r *Radio) Volumen() int            { return r.volumen }
func (r *Radio) FijarVolumen(v int)      { r.volumen = v; fmt.Printf("  [Radio] Volumen = %d%%\n", r.volumen) }
func (r *Radio) Nombre() string          { return "Radio FM Vintage" }

// 3. Abstracción: control de alto nivel que contiene el "puente" (dispositivo).
type ControlRemoto struct {
	dispositivo Dispositivo
}

func NuevoControlRemoto(d Dispositivo) *ControlRemoto {
	return &ControlRemoto{dispositivo: d}
}

func (c *ControlRemoto) BotonEncendido() {
	fmt.Printf("Control -> alternando energía en %s\n", c.dispositivo.Nombre())
	if c.dispositivo.EstaEncendido() {
		c.dispositivo.Apagar()
	} else {
		c.dispositivo.Encender()
	}
}

func (c *ControlRemoto) SubirVolumen() {
	c.dispositivo.FijarVolumen(c.dispositivo.Volumen() + 15)
}

// 4. Abstracción Refinada: extiende la abstracción por composición (embedding).
type ControlAvanzado struct {
	*ControlRemoto
}

func NuevoControlAvanzado(d Dispositivo) *ControlAvanzado {
	return &ControlAvanzado{ControlRemoto: NuevoControlRemoto(d)}
}

func (ca *ControlAvanzado) Silenciar() {
	fmt.Printf("Control Avanzado -> silenciando %s\n", ca.dispositivo.Nombre())
	ca.dispositivo.FijarVolumen(0)
}

func main() {
	tv := &Televisor{volumen: 30}
	controlBasico := NuevoControlRemoto(tv)
	controlBasico.BotonEncendido()
	controlBasico.SubirVolumen()

	radio := &Radio{volumen: 50}
	controlPro := NuevoControlAvanzado(radio)
	controlPro.BotonEncendido()
	controlPro.SubirVolumen()
	controlPro.Silenciar()
}

🔍 Paso a paso

  1. Dispositivo define las operaciones primitivas que cumplen tanto Televisor como Radio.
  2. ControlRemoto guarda el campo dispositivo Dispositivo (el puente) y construye operaciones de alto nivel.
  3. ControlAvanzado embebe *ControlRemoto para reutilizar sus métodos y añade Silenciar().

Control -> alternando energía en Radio FM Vintage

  [Radio] Volumen = 0%

Composite

También llamado: Objeto compuesto, Object Tree

🎯 Propósito

Composite es un patrón de diseño estructural que permite componer objetos en estructuras de árbol y trabajar con esas estructuras compuestas exactamente igual que si fueran objetos individuales.

😟 Problema

Imagina un sistema de pedidos con Productos y Cajas, o un sistema de archivos con Archivos y Carpetas, o un árbol sintáctico abstracto (AST) en un compilador. Una caja puede contener productos simples pero también cajas más pequeñas, que a su vez contienen más cajas.

Si el código cliente intenta calcular el precio o tamaño total distinguiendo manualmente tipos concretos y niveles de anidación con bucles y condicionales (if esCaja ...), el código se vuelve frágil y acoplado a la estructura interna del árbol.

💡 Solución

Definir una interfaz Componente común para los objetos simples (Hojas) y los contenedores complejos (Compuestos):

  • En una Hoja (producto o archivo), el método devuelve directamente su valor o realiza el trabajo base.
  • En un Contenedor (caja o carpeta), el método recorre recursivamente todos sus hijos (que son de tipo Componente), les delega la llamada y agrega los resultados.

Para el cliente no hay diferencia entre pedir el tamaño de un archivo suelto o de la carpeta raíz completa.

🪖

Analogía en el mundo real

Los ejércitos se organizan como un árbol jerárquico: un ejército contiene divisiones, las divisiones contienen brigadas, las brigadas pelotones, los pelotones escuadrones y los escuadrones soldados individuales (hojas). Cuando se da una orden en la cima, cada nivel la transmite recursivamente a sus subordinados hasta que cada soldado ejecuta la acción.

  1. Componente: interfaz que declara las operaciones comunes tanto para nodos simples como para contenedores del árbol.
  2. Hoja (Leaf): elemento básico sin subelementos; realiza el trabajo real directamente.
  3. Contenedor (Composite): almacena un slice de Componente (hojas u otros contenedores) y delega las operaciones recursivamente a sus hijos.
  4. Cliente: manipula todos los elementos uniformemente a través de la interfaz Componente.

🧭 Aplicabilidad

  • Cuando el modelo central de tu dominio puede representarse como una estructura jerárquica en forma de árbol (AST de un compilador, DOM HTML, sistema de archivos, menús UI).
  • Cuando quieres que el código cliente trate objetos simples y composiciones complejas de forma transparente sin distinguir sus tipos concretos.

🛠️ Cómo implementarlo

  1. Verifica que tu dominio se divida naturalmente en hojas simples y contenedores recursivos.
  2. Declara la interfaz Componente con los métodos comunes.
  3. Implementa las estructuras Hoja con el comportamiento elemental.
  4. Implementa la estructura Contenedor con un slice []Componente, métodos para añadir hijos y delegación recursiva en cada operación.

Ventajas

  • Aprovecha el polimorfismo y la recursión para recorrer árboles complejos sin condicionales de tipo.
  • Abierto/Cerrado (OCP): puedes introducir nuevos tipos de hojas o contenedores sin romper el cliente.

Desventajas

  • Si las hojas y los contenedores difieren demasiado en comportamiento, diseñar una interfaz común limpia puede obligar a generalizar en exceso.

🔗 Relación con otros patrones

Composite y Decorator comparten composición recursiva, pero Decorator solo envuelve un único hijo y le agrega comportamiento, mientras Composite agrupa múltiples hijos y recapitula sus resultados. Suele combinarse con Iterator (recorrer el árbol), Visitor (operar sobre nodos de un AST), Builder (construir árboles) y Flyweight (compartir hojas repetidas).

package main

import "fmt"

// 1. Componente (interfaz común para hojas simples y contenedores complejos).
type NodoSistema interface {
	Nombre() string
	TamanoKB() int
	Mostrar(indent string)
}

// 2. Hoja (Leaf): elemento básico del árbol que no tiene subelementos.
type Archivo struct {
	nombre   string
	tamanoKB int
}

func NuevoArchivo(nombre string, tamanoKB int) *Archivo {
	return &Archivo{nombre: nombre, tamanoKB: tamanoKB}
}

func (a *Archivo) Nombre() string   { return a.nombre }
func (a *Archivo) TamanoKB() int    { return a.tamanoKB }
func (a *Archivo) Mostrar(ind string) {
	fmt.Printf("%s📄 %s (%d KB)\n", ind, a.nombre, a.tamanoKB)
}

// 3. Contenedor / Compuesto (Composite): agrupa hojas u otros contenedores.
type Carpeta struct {
	nombre string
	hijos  []NodoSistema
}

func NuevaCarpeta(nombre string) *Carpeta {
	return &Carpeta{nombre: nombre}
}

func (c *Carpeta) Agregar(nodos ...NodoSistema) {
	c.hijos = append(c.hijos, nodos...)
}

func (c *Carpeta) Nombre() string { return c.nombre }

// TamanoKB delega recursivamente el cálculo a cada hijo del subárbol.
func (c *Carpeta) TamanoKB() int {
	total := 0
	for _, h := range c.hijos {
		total += h.TamanoKB()
	}
	return total
}

func (c *Carpeta) Mostrar(ind string) {
	fmt.Printf("%s📁 %s/ [total: %d KB]\n", ind, c.nombre, c.TamanoKB())
	for _, h := range c.hijos {
		h.Mostrar(ind + "   ")
	}
}

// 4. Cliente: trata igual a un archivo suelto que a todo un árbol de carpetas.
func ImprimirResumen(n NodoSistema) {
	fmt.Printf("Resumen de '%s' -> %d KB\n", n.Nombre(), n.TamanoKB())
}

func main() {
	src := NuevaCarpeta("src")
	src.Agregar(
		NuevoArchivo("lexer.go", 18),
		NuevoArchivo("parser.go", 42),
	)

	raiz := NuevaCarpeta("compilador")
	raiz.Agregar(
		NuevoArchivo("go.mod", 2),
		NuevoArchivo("README.md", 8),
		src,
	)

	raiz.Mostrar("")
	fmt.Println("---")
	ImprimirResumen(NuevoArchivo("lexer.go", 18)) // Hoja individual
	ImprimirResumen(raiz)                         // Árbol compuesto completo
}

🔍 Paso a paso

  1. NodoSistema declara la interfaz común con Nombre(), TamanoKB() y Mostrar().
  2. Archivo (Hoja) devuelve su tamaño directo.
  3. Carpeta (Compuesto) guarda hijos []NodoSistema y suma recursivamente h.TamanoKB().
  4. ImprimirResumen recibe tanto un *Archivo como la *Carpeta raíz sin cambiar una línea.

Salida real

📁 compilador/ [total: 70 KB]
   📄 go.mod (2 KB)
   📄 README.md (8 KB)
   📁 src/ [total: 60 KB]
      📄 lexer.go (18 KB)
      📄 parser.go (42 KB)
---
Resumen de 'lexer.go' -> 18 KB
Resumen de 'compilador' -> 70 KB

En Go respetamos el Principio de Segregación de Interfaces (ISP) dejando Agregar(...NodoSistema) solo en *Carpeta y no en la interfaz NodoSistema, evitando métodos vacíos o con panic en las hojas. En compiladores en Go (go/ast), las expresiones binarias y literales forman un Composite clásico.

Decorator

También llamado: Decorador, Envoltorio, Wrapper

🎯 Propósito

Decorator es un patrón de diseño estructural que permite añadir funcionalidades a objetos dinámicamente colocándolos dentro de objetos envoltorio (wrappers) especiales que implementan la misma interfaz.

😟 Problema

Imagina una biblioteca de notificaciones que empieza enviando solo correos electrónicos (Notificador). Luego los usuarios piden SMS, Slack, Telegram, cifrado y formato urgente. Si intentas crear una subclase para cada combinación posible (NotificadorEmailConSMSYSlack, NotificadorEmailConSMS, etc.), sufres una explosión combinatoria.

Además, la herencia es estática: no permite apilar, quitar o decidir qué canales combinar en tiempo de ejecución según la configuración del usuario.

💡 Solución

Usar composición recursiva mediante envoltorios (wrappers):

  1. Tanto el componente base como cada decorador implementan la misma interfaz (p. ej. Notificador).
  2. Cada decorador guarda un campo envuelto de ese tipo interfaz.
  3. Al recibir una llamada, el decorador ejecuta su lógica extra (antes o después) y delega la llamada al objeto envuelto. Así puedes apilar tantas capas como quieras como una muñeca rusa.
🧥

Analogía en el mundo real

Vestirse por capas cuando hace frío: tú eres el componente base; primero te pones un suéter, encima una chaqueta térmica y, si llueve, un impermeable encima. Cada prenda te "envuelve" y extiende tu protección sin modificar tu cuerpo, y puedes combinarlas o quitártelas dinámicamente en cualquier momento.

                  ┌────────────┴───┐    ┌─────┴────────────────┐   │ (1)
                  │ ② CompConcreto │    │ ③ DecoradorBase      │◇──┘
                  │ (Email)        │    │ - envuelto:Componente│
                  └────────────────┘    └──────────△───────────┘

                                        │ ④ DecoradoresConcr.  │

                                        └──────────────────────┘
  1. Componente: interfaz común tanto para el objeto envuelto como para todos los decoradores.
  2. Componente Concreto: define el comportamiento básico que será envuelto y extendido.
  3. Decorador Base: referencia un Componente envuelto y le delega las operaciones.
  4. Decoradores Concretos: añaden responsabilidades antes y/o después de delegar al objeto envuelto.
  5. Cliente: ensambla la pila de decoradores y la usa mediante la interfaz común.

🧭 Aplicabilidad

  • Cuando necesitas asignar responsabilidades adicionales a objetos en tiempo de ejecución sin afectar al código cliente que los utiliza.
  • Cuando quieres combinar comportamientos ortogonales (logging, métricas, compresión, cifrado, reintentos) mediante capas apilables.

🛠️ Cómo implementarlo

  1. Declara la interfaz Componente con los métodos compartidos por el objeto base y las capas opcionales.
  2. Crea el Componente Concreto con la funcionalidad base.
  3. Crea cada Decorador implementando la misma interfaz y guardando un campo envuelto Componente.
  4. En el método del decorador, agrega el comportamiento extra antes o después de llamar a d.envuelto.Metodo().

Ventajas

  • Extiende y combina comportamientos en tiempo de ejecución sin crear subclases.
  • Cumple SRP: cada preocupación transversal (SMS, Slack, formato) vive en su propio tipo pequeño.

Desventajas

  • Es difícil eliminar un wrapper intermedio específico una vez armada la pila.
  • El resultado puede depender del orden exacto en que se apilan los decoradores.

🔗 Relación con otros patrones

Decorator mantiene la misma interfaz y permite apilar capas recursivamente; Adapter cambia la interfaz. Se parece a Chain of Responsibility, pero en Decorator todas las capas se ejecutan sin cortar el flujo. Mientras Decorator cambia la "piel" externa del objeto, Strategy cambia sus "entrañas". A diferencia de Proxy, en Decorator el cliente controla explícitamente qué capas apilar.

package main

import (
	"fmt"
	"strings"
)

// 1. Componente: interfaz común para el objeto envuelto y para todos los decoradores.
type Notificador interface {
	Enviar(mensaje string) string
}

// 2. Componente Concreto: define el comportamiento base (enviar por correo).
type NotificadorEmail struct {
	Destinatario string
}

func (n NotificadorEmail) Enviar(mensaje string) string {
	return fmt.Sprintf("📧 Email a <%s>: %q", n.Destinatario, mensaje)
}

// 3. Decorador Concreto A: envuelve un Notificador y añade envío por SMS.
type DecoradorSMS struct {
	envuelto Notificador
	telefono string
}

func ConSMS(n Notificador, telefono string) Notificador {
	return DecoradorSMS{envuelto: n, telefono: telefono}
}

func (d DecoradorSMS) Enviar(mensaje string) string {
	previo := d.envuelto.Enviar(mensaje)
	return fmt.Sprintf("%s\n📱 SMS a [%s]: %q", previo, d.telefono, mensaje)
}

// 4. Decorador Concreto B: añade notificación a un canal de Slack.
type DecoradorSlack struct {
	envuelto Notificador
	canal    string
}

func ConSlack(n Notificador, canal string) Notificador {
	return DecoradorSlack{envuelto: n, canal: canal}
}

func (d DecoradorSlack) Enviar(mensaje string) string {
	previo := d.envuelto.Enviar(mensaje)
	return fmt.Sprintf("%s\n💬 Slack [%s]: %q", previo, d.canal, mensaje)
}

// 5. Decorador Concreto C: transforma el mensaje antes de delegarlo a la pila.
type DecoradorUrgente struct {
	envuelto Notificador
}

func ConFormatoUrgente(n Notificador) Notificador {
	return DecoradorUrgente{envuelto: n}
}

func (d DecoradorUrgente) Enviar(mensaje string) string {
	transformado := "[URGENTE] " + strings.ToUpper(mensaje)
	return d.envuelto.Enviar(transformado)
}

func main() {
	// Pila de decoradores: Urgente -> Slack -> SMS -> Email base
	var alerta Notificador = NotificadorEmail{Destinatario: "ops@empresa.co"}
	alerta = ConSMS(alerta, "+57-300-1234567")
	alerta = ConSlack(alerta, "#incidentes-prod")
	alerta = ConFormatoUrgente(alerta)

	fmt.Println(alerta.Enviar("uso de CPU al 98% en nodo principal"))
}

🔍 Paso a paso

  1. NotificadorEmail es la base de la pila.
  2. ConSMS y ConSlack envuelven cualquier Notificador y agregan su propio envío después de delegar.
  3. ConFormatoUrgente actúa antes de delegar: convierte el texto a mayúsculas y lo pasa a toda la pila interior.

Facade

También llamado: Fachada

🎯 Propósito

Facade es un patrón de diseño estructural que proporciona una interfaz simplificada y de alto nivel a una biblioteca, un framework o cualquier subsistema complejo compuesto por múltiples objetos.

😟 Problema

Imagina que tu aplicación necesita realizar una operación como procesar un pedido en línea o convertir un video o compilar código fuente. Para lograrlo debe interactuar con decenas de objetos de un subsistema: inicializarlos, controlar sus dependencias y llamar a sus métodos en un orden estricto.

Si cada cliente hace esa orquestación por su cuenta, tu lógica de negocio queda fuertemente acoplada a los detalles internos del subsistema y cualquier cambio se propaga por todo el proyecto.

💡 Solución

Crear una estructura Fachada (Facade) que ofrezca unos pocos métodos directos con exactamente lo que la mayoría de los clientes necesitan (por ejemplo, ComprarConUnClic() o ConvertirVideo()).

La fachada conoce a qué piezas internas del subsistema dirigirse y en qué orden coordinarlas, aislando al cliente de la complejidad interna sin impedir que un usuario avanzado acceda al subsistema directamente si lo requiere.

☎️

Analogía en el mundo real

Cuando haces un pedido telefónico a una tienda, el operador de atención al cliente es tu fachada. No hablas por separado con la bodega de inventario, la pasarela antifraude del banco, el departamento de facturación y la empresa de mensajería: hablas un minuto con el operador y él coordina todos los departamentos internos por ti.

  2. Fachada Adicional (opcional): evita que una única fachada crezca demasiado mezclando responsabilidades no relacionadas.
  3. Subsistema Complejo: conjunto de tipos especializados que hacen el trabajo real sin conocer la existencia de la fachada.
  4. Cliente: invoca únicamente a la fachada en vez de manejar los objetos internos del subsistema.

🧭 Aplicabilidad

  • Cuando necesitas una interfaz simple y directa hacia un subsistema complejo o una biblioteca de terceros con decenas de tipos.
  • Cuando quieres estructurar un sistema en capas (por ejemplo, fases de un compilador o módulos de negocio) definiendo una fachada como punto de entrada de cada capa.

🛠️ Cómo implementarlo

  1. Identifica qué operaciones de alto nivel necesita realmente el cliente frente al subsistema existente.
  2. Crea la estructura fachada que agrupe las referencias a los componentes del subsistema e inicialice su ciclo de vida.
  3. Haz que el código cliente se comunique con el subsistema solo a través de la fachada; si esta crece demasiado, divídela en fachadas más pequeñas.

Ventajas

  • Aísla y desacopla el código cliente de la complejidad interna de un subsistema de múltiples piezas.
  • Facilita actualizar o reemplazar el subsistema interno modificando únicamente la fachada.

Desventajas

  • Riesgo de que la fachada se convierta en un objeto todopoderoso (God Object) acoplado a todas las estructuras de la aplicación.

🔗 Relación con otros patrones

Facade define una interfaz nueva y simple para todo un subsistema de objetos, mientras que Adapter reutiliza una interfaz existente envolviendo por lo general un solo objeto. A diferencia de Mediator, en Facade los objetos del subsistema no conocen a la fachada. Abstract Factory puede usarse junto a Facade para ocultar cómo se instancian las piezas del subsistema.

package main

import "fmt"

// --- Subsistema Complejo: múltiples tipos con orden de inicialización estricto ---

type ServicioInventario struct{}

func (ServicioInventario) VerificarStock(sku string) bool {
	fmt.Printf("  1. [Inventario] Verificando disponibilidad de %s -> OK\n", sku)
	return true
}

type PasarelaFraude struct{}

func (PasarelaFraude) EvaluarRiesgo(cliente string, monto float64) bool {
	fmt.Printf("  2. [Antifraude] Analizando operación de %s por $%.2f -> APROBADO\n", cliente, monto)
	return true
}

type MotorCobros struct{}

func (MotorCobros) Debitar(cliente string, monto float64) string {
	fmt.Printf("  3. [Cobros] Debitando $%.2f a %s -> TX-9081\n", monto, cliente)
	return "TX-9081"
}

type ServicioLogistica struct{}

func (ServicioLogistica) Despachar(sku, cliente string) string {
	fmt.Printf("  4. [Logística] Generando guía de envío para %s (%s) -> GUIA-441\n", sku, cliente)
	return "GUIA-441"
}

// --- Fachada (Facade): interfaz simplificada de alto nivel para el cliente ---

type FachadaCompra struct {
	inventario ServicioInventario
	antifraude PasarelaFraude
	cobros     MotorCobros
	logistica  ServicioLogistica
}

func NuevaFachadaCompra() *FachadaCompra {
	return &FachadaCompra{}
}

// ComprarConUnClic coordina todo el subsistema en el orden correcto.
func (f *FachadaCompra) ComprarConUnClic(cliente, sku string, precio float64) string {
	fmt.Printf("Iniciando compra rápida: %s adquiere %s\n", cliente, sku)
	if !f.inventario.VerificarStock(sku) || !f.antifraude.EvaluarRiesgo(cliente, precio) {
		return "Compra rechazada"
	}
	tx := f.cobros.Debitar(cliente, precio)
	guia := f.logistica.Despachar(sku, cliente)
	return fmt.Sprintf("Pedido completado (Transacción: %s, Guía: %s)", tx, guia)
}

func main() {
	// El cliente solo conoce la Fachada; ignora los 4 subsistemas internos.
	tienda := NuevaFachadaCompra()
	resultado := tienda.ComprarConUnClic("Ana Gómez", "LAPTOP-PRO-16", 1299.00)
	fmt.Println("Resultado:", resultado)
}

🔍 Paso a paso

  1. El subsistema consta de 4 servicios independientes (ServicioInventario, PasarelaFraude, MotorCobros, ServicioLogistica).
  2. FachadaCompra encapsula las 4 piezas y expone un único método de negocio: ComprarConUnClic.
  3. main() realiza la operación completa con una sola llamada sin acoplarse al orden interno del flujo.

Flyweight

También llamado: Peso mosca, Peso ligero, Cache

🎯 Propósito

Flyweight es un patrón de diseño estructural que permite mantener una enorme cantidad de objetos dentro de la memoria RAM disponible compartiendo las partes comunes del estado entre múltiples objetos en lugar de duplicar toda la información en cada uno.

😟 Problema

Imagina un videojuego que renderiza cientos de miles de partículas (balas, misiles, metralla) o un bosque con un millón de árboles. Si cada objeto Árbol o Partícula guarda su propia copia de la textura 4K, el modelo 3D y el color además de sus coordenadas (x, y), la memoria RAM se agota en segundos y el programa colapsa.

Al inspeccionar los objetos, notas que casi todos repiten exactamente las mismas texturas y colores pesados.

💡 Solución

Separar el estado de cada objeto en dos mitades:

  • Estado intrínseco (Flyweight): datos constantes, pesados y repetidos (especie, color, textura/sprite). Se almacenan en un único objeto inmutable compartido por miles de instancias.
  • Estado extrínseco (Contexto): datos livianos y únicos de cada instancia (coordenadas x, y, velocidad). Se guardan afuera y se pasan por parámetro a los métodos del Flyweight cuando se necesitan.
🌲

Analogía en el mundo real

En un procesador de textos o libro impreso con 500 000 letras, el programa no guarda 500 000 mapas de bits vectoriales de la fuente tipográfica. Guarda una sola definición geométrica inmutable de la letra 'A' (estado intrínseco / flyweight) y en el documento solo anota en qué fila y columna dibujarla (estado extrínseco).

  1. Flyweight: almacena solo el estado intrínseco compartido (debe ser inmutable). Recibe el estado extrínseco por parámetro en sus métodos.
  2. Contexto: contiene el estado extrínseco único de cada objeto liviano más un puntero al Flyweight compartido.
  3. Fábrica Flyweight: administra un pool/caché de flyweights existentes; devuelve uno ya creado o lo instancia si aún no existe.
  4. Cliente: calcula o almacena el estado extrínseco y solicita los flyweights a la fábrica.

🧭 Aplicabilidad

  • Úsalo únicamente cuando tu programa deba instanciar una cantidad masiva de objetos similares que agoten la RAM disponible, y gran parte de sus campos contengan datos duplicados que puedan extraerse y compartirse.
  • Muy común en motores gráficos, videojuegos y tablas de internado de cadenas (string interning) en compiladores.

🛠️ Cómo implementarlo

  1. Divide los campos del objeto en estado intrínseco (inmutable, compartido) y extrínseco (único por instancia).
  2. Deja solo el estado intrínseco en el tipo Flyweight e inicialízalo una sola vez.
  3. Pasa el estado extrínseco como argumentos a los métodos del Flyweight y guárdalo en una estructura Contexto.
  4. Crea una Fábrica Flyweight con un mapa en caché para reutilizar instancias.

Ventajas

  • Ahorra enormes cantidades de memoria RAM cuando existen miles o millones de objetos similares.

Desventajas

  • Puede intercambiar ahorro de RAM por ciclos de CPU si el estado extrínseco debe recalcularse en cada llamada.
  • Aumenta la complejidad del código al separar el estado de una entidad en dos estructuras.

🔗 Relación con otros patrones

Las hojas repetidas de un árbol Composite suelen implementarse como Flyweights para ahorrar memoria. Mientras Flyweight muestra cómo tener muchos objetos pequeños compartidos, Facade muestra cómo un solo objeto representa todo un subsistema. A diferencia de Singleton, una clase Flyweight tiene múltiples instancias (una por cada estado intrínseco distinto) y sus objetos deben ser inmutables.

package main

import "fmt"

// 1. Flyweight (Estado Intrínseco): inmutable y compartido entre miles de instancias.
type TipoArbol struct {
	especie string
	color   string
	textura string // Simula un recurso pesado en RAM (malla 3D / textura HD)
}

func (t *TipoArbol) Dibujar(x, y int) {
	fmt.Printf("  🌳 [%s | %s | %s] en (%d, %d) (ptr=%p)\n",
		t.especie, t.color, t.textura, x, y, t)
}

// 2. Fábrica Flyweight: gestiona el pool/caché de objetos compartidos.
type FabricaTiposArbol struct {
	tipos map[string]*TipoArbol
}

func NuevaFabricaTipos() *FabricaTiposArbol {
	return &FabricaTiposArbol{tipos: make(map[string]*TipoArbol)}
}

func (f *FabricaTiposArbol) ObtenerTipo(especie, color, textura string) *TipoArbol {
	clave := especie + "_" + color
	if tipo, existe := f.tipos[clave]; existe {
		return tipo // Reutiliza el flyweight existente en memoria
	}
	fmt.Printf("➕ Creando nuevo Flyweight en RAM para: %s (%s)\n", especie, color)
	nuevo := &TipoArbol{especie: especie, color: color, textura: textura}
	f.tipos[clave] = nuevo
	return nuevo
}

// 3. Contexto (Estado Extrínseco): liviano, único para cada árbol del mapa.
type Arbol struct {
	x, y int
	tipo *TipoArbol // Referencia al flyweight compartido
}

// 4. Cliente / Contenedor: almacena los contextos livianos.
type Bosque struct {
	arboles []Arbol
	fabrica *FabricaTiposArbol
}

func (b *Bosque) Plantar(x, y int, especie, color, textura string) {
	tipoCompartido := b.fabrica.ObtenerTipo(especie, color, textura)
	b.arboles = append(b.arboles, Arbol{x: x, y: y, tipo: tipoCompartido})
}

func main() {
	bosque := &Bosque{fabrica: NuevaFabricaTipos()}

	bosque.Plantar(10, 20, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(15, 25, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(50, 80, "Cerezo", "Rosa", "textura_cerezo_4k.png")
	bosque.Plantar(12, 30, "Pino", "Verde Oscuro", "textura_pino_4k.png")
	bosque.Plantar(55, 85, "Cerezo", "Rosa", "textura_cerezo_4k.png")

	fmt.Printf("\nRenderizando %d árboles usando solo %d objetos TipoArbol en RAM:\n",
		len(bosque.arboles), len(bosque.fabrica.tipos))
	for _, a := range bosque.arboles {
		a.tipo.Dibujar(a.x, a.y)
	}
}

🔍 Paso a paso

  1. TipoArbol tiene campos privados (no exportados) para garantizar su inmutabilidad.
  2. FabricaTiposArbol usa un map[string]*TipoArbol: al plantar 5 árboles de 2 especies, solo reserva memoria para 2 objetos TipoArbol.
  3. Observa en la salida que todos los pinos comparten exactamente la misma dirección de memoria (ptr).

Salida real

Proxy

También llamado: Representante, Sustituto, Surrogate

🎯 Propósito

Proxy es un patrón de diseño estructural que proporciona un sustituto o marcador de posición para otro objeto. Un proxy controla el acceso al objeto original, permitiéndote ejecutar lógica (seguridad, caché, carga diferida, auditoría) antes o después de que la solicitud llegue al servicio real.

😟 Problema

Imagina que tienes un objeto de servicio masivo que consume muchos recursos (una conexión a base de datos, un cliente de almacenamiento remoto S3 o un descargador de video). Lo necesitas ocasionalmente, pero no quieres inicializarlo al arrancar si nadie lo usa, ni repetir consultas idénticas por red, ni permitir que usuarios sin permisos lo invoquen.

Si incrustas esa lógica de inicialización diferida, caché y permisos en cada cliente, duplicarás código por toda la aplicación.

💡 Solución

Crear una estructura Proxy que implemente exactamente la misma interfaz que el servicio original:

  • El proxy se camufla ante los clientes como si fuera el servicio real.
  • Intercepta cada petición: verifica permisos, consulta su caché o crea el objeto pesado solo en el instante en que realmente se necesita (lazy initialization), y luego le delega el trabajo.
💳

Analogía en el mundo real

Una tarjeta de crédito o débito es un proxy de una cuenta bancaria, que a su vez es un proxy de un fajo de billetes en efectivo. Ambos implementan la misma interfaz ("realizar un pago"), pero la tarjeta controla el acceso (verifica tu PIN y cupo disponible) antes de descontar el dinero real del banco.

  2. Servicio Real: estructura que contiene la lógica de negocio pesada o sensible.
  3. Proxy: mantiene una referencia al servicio real, gestiona su ciclo de vida y controla el acceso antes/después de delegar.
  4. Cliente: trabaja tanto con el Servicio Real como con el Proxy de forma transparente a través de la interfaz.

🧭 Aplicabilidad (tipos de Proxy)

  • Proxy virtual (inicialización diferida): retrasa la creación de un objeto muy costoso hasta que se usa por primera vez.
  • Proxy de protección (control de acceso): valida credenciales o roles antes de pasar la solicitud.
  • Proxy de caché: almacena en memoria resultados de operaciones remotas o lentas recurrentes.
  • Proxy de registro / remoto: audita llamadas o encapsula comunicación por red (gRPC/HTTP).

🛠️ Cómo implementarlo

  1. Asegúrate de tener una Interfaz de Servicio para que el proxy y el servicio real sean intercambiables.
  2. Crea la estructura Proxy con un campo que apunte al servicio real (a menudo creado por el propio proxy).
  3. Implementa los métodos de la interfaz ejecutando validaciones, caché o lazy init antes de delegar al servicio.

Ventajas

  • Controla el acceso y el ciclo de vida del objeto de servicio sin que el cliente lo note.
  • Abierto/Cerrado (OCP): puedes introducir nuevos proxies sin modificar el servicio ni los clientes.

Desventajas

  • La respuesta del servicio puede experimentar cierta latencia adicional por las validaciones o inicialización diferida.

🔗 Relación con otros patrones

Proxy mantiene exactamente la misma interfaz que su servicio; Adapter la cambia y Decorator la amplía por capas. Aunque Proxy y Decorator se construyen por composición, un Proxy suele gestionar por su cuenta el ciclo de vida del servicio real (creándolo en diferido), mientras que en Decorator el cliente inyecta y apila explícitamente los objetos.

package main

import "fmt"

// 1. Interfaz de Servicio: implementada tanto por el Servicio Real como por el Proxy.
type RepositorioDocumentos interface {
	ObtenerDocumento(id string, rolUsuario string) string
}

// 2. Servicio Real: operación costosa (consulta a BD o descarga remota).
type AlmacenRemotoS3 struct{}

func (a *AlmacenRemotoS3) ObtenerDocumento(id string, _ string) string {
	fmt.Printf("  🌐 [AlmacenRemotoS3] Descargando '%s' desde el servidor remoto...\n", id)
	return fmt.Sprintf("Contenido confidencial del archivo [%s]", id)
}

// 3. Proxy: controla acceso (protección), guarda en caché e inicializa en diferido (virtual).
type ProxyRepositorio struct {
	servicioReal *AlmacenRemotoS3 // Se crea solo cuando realmente hace falta (lazy init)
	cache        map[string]string
}

func NuevoProxyRepositorio() *ProxyRepositorio {
	return &ProxyRepositorio{cache: make(map[string]string)}
}

func (p *ProxyRepositorio) ObtenerDocumento(id string, rolUsuario string) string {
	fmt.Printf("-> Solicitud de '%s' por rol '%s'\n", id, rolUsuario)

	// a) Proxy de protección: control de acceso
	if rolUsuario != "admin" && rolUsuario != "editor" {
		return "⛔ ACCESO DENEGADO: permisos insuficientes"
	}

	// b) Proxy de caché: evita descargas repetidas
	if contenido, ok := p.cache[id]; ok {
		fmt.Printf("  ⚡ [Proxy Cache] Devolviendo '%s' desde memoria caché\n", id)
		return contenido
	}

	// c) Proxy virtual: inicialización diferida del servicio pesado
	if p.servicioReal == nil {
		fmt.Println("  🔧 [Proxy Virtual] Inicializando conexión con AlmacenRemotoS3...")
		p.servicioReal = &AlmacenRemotoS3{}
	}

	resultado := p.servicioReal.ObtenerDocumento(id, rolUsuario)
	p.cache[id] = resultado
	return resultado
}

func main() {
	var repo RepositorioDocumentos = NuevoProxyRepositorio()

	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "invitado"))
	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "admin"))
	fmt.Println("  Resultado:", repo.ObtenerDocumento("nomina_2026.pdf", "editor"))
}

🔍 Paso a paso

  1. En la primera llamada (invitado), el Proxy de protección rechaza la petición sin siquiera instanciar AlmacenRemotoS3.
  2. En la segunda llamada (admin), el Proxy virtual inicializa el servicio en diferido, descarga el documento y lo guarda en caché.
  3. En la tercera llamada (editor), el Proxy de caché responde al instante desde memoria sin tocar la red.

🧠 Comportamiento 1 / 3 · Teoría

Chain of Responsibility

También llamado: Cadena de responsabilidad, CoR, Chain of Command

🎯 Propósito

Permite enviar solicitudes a lo largo de una cadena de manejadores potenciales. Al recibir una petición, cada eslabón decide si la procesa por su cuenta, si la bloquea o si la delega al siguiente manejador de la fila.

😟 Problema

Imagina un sistema de compras en línea que debe aplicar controles secuenciales antes de registrar un pedido: primero autenticar al usuario, luego verificar permisos de rol, sanear los datos de entrada, limitar intentos repetidos por IP (fuerza bruta) y consultar si ya existe respuesta en caché.

Si programas todas estas validaciones dentro de una sola función gigante llena de condicionales anidados, el código se vuelve rígido, frágil ante cambios y casi imposible de reutilizar parcialmente en otros módulos que solo requieran un subconjunto de controles.

💡 Solución

Extrae cada control en un objeto autónomo llamado manejador (handler) que implemente una interfaz común con un método de procesamiento y una referencia al siguiente eslabón.

Las peticiones recorren la cadena eslabón por eslabón: cada manejador ejecuta su verificación y decide si detiene el flujo (por ejemplo, cuando falla la autenticación o ya resolvió el evento GUI) o si pasa la solicitud al siguiente manejador, desacoplando al emisor de los receptores concretos.

☎️

Analogía en el mundo real

Cuando llamas al soporte técnico por un driver incompatible en Linux, tu llamada atraviesa una cadena de atención: primero responde un contestador automático con opciones pregrabadas; como ninguna aplica, te transfiere a un operador de primer nivel que lee respuestas estándar del manual; al no poder resolverlo, finalmente escala la llamada a un ingeniero especialista en el sótano de servidores, quien da con la solución exacta y cierra el caso.

Arquitectura en eslabones, cuándo aplicarlo y evaluación del diseño

│ 4. Cliente   │───────▶│      <<interface>>                │
└──────────────┘        │     1. Manejador                  │
                        ├───────────────────────────────────┤
                        │ + EstablecerSiguiente(m)          │
                        │ + Manejar(solicitud)              │
                        └─────────────────△─────────────────┘
                                          │ implementa
                        ┌─────────────────┴─────────────────┐
                        │        2. ManejadorBase           │◇───┐
                        ├───────────────────────────────────┤    │ siguiente
                        │ - siguiente: Manejador            │◀───┘
                        ├───────────────────────────────────┤
                        │ + EstablecerSiguiente(m)          │
                        │ + PasarAlSiguiente(solicitud)     │
                        └─────────────────△─────────────────┘
                                          │ embebe
                        ┌─────────────────┴─────────────────┐
                        │     3. ManejadoresConcretos       │
                        ├───────────────────────────────────┤
                        │ + Manejar(solicitud):             │
                        │   si no cumple -> cortar          │
                        │   si cumple    -> PasarAlSiguiente│
                        └───────────────────────────────────┘
  1. Manejador (Interfaz): declara el contrato común para procesar peticiones y enlazar el siguiente eslabón.
  2. Manejador Base: estructura opcional que almacena la referencia al siguiente manejador e implementa el reenvío por defecto para ahorrar código repetitivo.
  3. Manejadores Concretos: contienen la regla de negocio real; deciden si procesan/detienen la solicitud o la delegan hacia adelante.
  4. Cliente: ensambla la cadena estática o dinámicamente y dispara la petición hacia el primer eslabón (o cualquiera de la cadena).

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando debas procesar distintas solicitudes sin conocer de antemano qué eslabón las atenderá, cuando sea obligatorio ejecutar filtros en un orden estricto, o cuando la tubería de manejadores deba reconfigurarse en tiempo de ejecución.
  • Paso 1: Define la interfaz Manejador y encapsula los datos de entrada en un struct Solicitud.
  • Paso 2: Crea un ManejadorBase con el campo siguiente y un método auxiliar para delegar si siguiente != nil.
  • Paso 3: Implementa cada manejador concreto decidiendo si corta la ejecución o invoca al siguiente, y conecta los eslabones desde el cliente.

Pros

  • Control total sobre el orden de ejecución de las validaciones.
  • Cumple SRP: desacopla quien inicia la petición de quien la valida o procesa.
  • Cumple OCP: puedes insertar nuevos filtros sin modificar los existentes.

Contras

  • Algunas solicitudes pueden recorrer toda la cadena y terminar sin que ningún eslabón las procese.
  • Rastrear el flujo en cadenas muy largas puede requerir depuración cuidadosa.

🔗 Relación con otros patrones

Suele combinarse con Composite (los eventos suben desde una hoja hacia sus contenedores padres), con Command (representando cada solicitud como comando), y se parece estructuralmente a Decorator, con la diferencia clave de que cualquier eslabón de CoR puede cortar el flujo libremente.

Pipeline de seguridad y validación de pedidos con composición de structs

package main

import "fmt"

// Solicitud contiene los datos que viajan a lo largo de la cadena.
type Solicitud struct {
	Usuario     string
	Autenticado bool
	Intentos    int
	Datos       string
}

// 1. Manejador (interfaz común a todos los eslabones)
type Manejador interface {
	EstablecerSiguiente(m Manejador) Manejador
	Manejar(s *Solicitud)
}

// 2. ManejadorBase (evita duplicar el enlace al siguiente eslabón)
type ManejadorBase struct {
	siguiente Manejador
}

func (b *ManejadorBase) EstablecerSiguiente(m Manejador) Manejador {
	b.siguiente = m
	return m
}

func (b *ManejadorBase) PasarAlSiguiente(s *Solicitud) {
	if b.siguiente != nil {
		b.siguiente.Manejar(s)
	}
}

// 3a. Manejador Concreto: protege contra fuerza bruta
type FiltroFuerzaBruta struct{ ManejadorBase }

func (f *FiltroFuerzaBruta) Manejar(s *Solicitud) {
	if s.Intentos >= 3 {
		fmt.Printf("  [FuerzaBruta] ✘ IP bloqueada para %q (%d intentos fallidos)\n", s.Usuario, s.Intentos)
		return // Corta la cadena
	}
	fmt.Println("  [FuerzaBruta] ✔ Intentos dentro del límite")
	f.PasarAlSiguiente(s)
}

// 3b. Manejador Concreto: verifica credenciales
type FiltroAutenticacion struct{ ManejadorBase }

func (a *FiltroAutenticacion) Manejar(s *Solicitud) {
	if !s.Autenticado {
		fmt.Printf("  [Autenticación] ✘ Acceso denegado a %q: sesión no iniciada\n", s.Usuario)
		return // Corta la cadena
	}
	fmt.Printf("  [Autenticación] ✔ Usuario %q autenticado\n", s.Usuario)
	a.PasarAlSiguiente(s)
}

// 3c. Manejador Concreto: valida y sanea el payload
type FiltroValidacion struct{ ManejadorBase }

func (v *FiltroValidacion) Manejar(s *Solicitud) {
	if s.Datos == "" {
		fmt.Println("  [Validación] ✘ Solicitud rechazada: datos del pedido vacíos")
		return
	}
	fmt.Println("  [Validación] ✔ Datos del pedido saneados")
	v.PasarAlSiguiente(s)
}

// 3d. Manejador Concreto final: procesa el pedido
type ProcesadorPedidos struct{ ManejadorBase }

func (p *ProcesadorPedidos) Manejar(s *Solicitud) {
	fmt.Printf("  [Pedidos] 🎉 Pedido procesado con éxito para %q: %s\n", s.Usuario, s.Datos)
}

func main() {
	// 4. Cliente: ensambla la cadena de responsabilidad
	fuerzaBruta := &FiltroFuerzaBruta{}
	autenticacion := &FiltroAutenticacion{}
	validacion := &FiltroValidacion{}
	procesador := &ProcesadorPedidos{}

	fuerzaBruta.EstablecerSiguiente(autenticacion).
		EstablecerSiguiente(validacion).
		EstablecerSiguiente(procesador)

	casos := []*Solicitud{
		{Usuario: "atacante", Autenticado: false, Intentos: 5, Datos: "2x Laptop"},
		{Usuario: "invitado", Autenticado: false, Intentos: 1, Datos: "1x Teclado"},
		{Usuario: "ana", Autenticado: true, Intentos: 0, Datos: "1x Monitor 4K"},
	}

	for i, req := range casos {
		fmt.Printf("Solicitud #%d (usuario=%q):\n", i+1, req.Usuario)
		fuerzaBruta.Manejar(req)
	}
}

🔍 Explicación paso a paso

  1. ManejadorBase guarda el puntero siguiente y devuelve el manejador recibido en EstablecerSiguiente para permitir encadenamiento fluido.
  2. Cada filtro concreto (FiltroFuerzaBruta, FiltroAutenticacion, FiltroValidacion) embebe ManejadorBase para heredar la lógica de enlace sin usar herencia de clases.
  3. Si una regla falla, el manejador hace return inmediato cortando la cadena; si aprueba, invoca PasarAlSiguiente(s).

Command

También llamado: Comando, Orden, Action, Transaction

🎯 Propósito

Convierte una solicitud o acción en un objeto independiente que encapsula toda la información necesaria para ejecutarla (el receptor, el método y sus argumentos), permitiendo parametrizar invocadores, encolar o diferir tareas y soportar operaciones reversibles (deshacer/rehacer).

😟 Problema

Supón que construyes un editor de texto con una barra de herramientas, menús contextuales y atajos de teclado. Si colocas la lógica de negocio (copiar, cortar, pegar) dentro de subclases como BotonCopiar, acoplas la interfaz gráfica directamente a la lógica de negocio.

Peor aún: cuando quieras activar la misma operación desde el menú contextual o con Ctrl+C, tendrás que duplicar el código en múltiples componentes o forzar a que los menús dependan de los botones.

💡 Solución

Separa por completo la capa que inicia la acción (Emisor / Invocador) de la capa que sabe cómo hacer el trabajo (Receptor) extrayendo cada petición en un objeto Comando que implementa una interfaz con un método Ejecutar().

El botón, menú o atajo solo guarda una referencia a la interfaz Comando y la dispara sin saber qué receptor actúa por detrás. Además, puedes apilar los comandos ejecutados en un historial para revertir sus efectos cuando el usuario pulse Ctrl+Z.

🍽️

Analogía en el mundo real

En un restaurante, el camarero (Invocador) toma tu orden y la escribe en una comanda de papel (Comando). Luego coloca ese papel en la fila de la cocina. El chef (Receptor) lee la comanda cuando tiene turno y cocina el plato porque el papel ya contiene todos los detalles necesarios, sin que el cliente tenga que entrar a hablar directamente con el cocinero.

  1. Emisor (Invocador): inicia la solicitud llamando al comando asignado (sin conocer al receptor) y puede registrar el historial de comandos.
  2. Comando (Interfaz): declara el método único de ejecución (y opcionalmente Deshacer()).
  3. Comandos Concretos: guardan la referencia al receptor, los argumentos de la operación y el respaldo necesario para deshacerla.
  4. Receptor: objeto de dominio que contiene la lógica real de negocio (p. ej. el EditorTexto).
  5. Cliente: instancia el receptor, crea los comandos concretos inyectándoles los parámetros y los asocia al invocador.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: para parametrizar objetos UI con acciones intercambiables, para encolar/programar tareas o enviarlas por red (serializando el comando), y para implementar deshacer/rehacer mediante un historial.
  • Paso 1: Declara la interfaz Comando con su método Ejecutar().
  • Paso 2: Crea structs de comando concretos que almacenen al receptor y los argumentos de la llamada.
  • Paso 3: Haz que el invocador reciba y dispare la interfaz Comando en vez de llamar directamente al receptor.

Pros

  • Cumple SRP y OCP: separa quien invoca de quien ejecuta y permite añadir comandos sin romper clases existentes.
  • Facilita implementar undo/redo, ejecución diferida, colas de trabajo y comandos compuestos (macros).

Contras

  • Introduce una capa adicional de structs e interfaces entre los emisores y los receptores.

🔗 Relación con otros patrones

Se combina con Memento para guardar instantáneas antes de ejecutar un comando reversible; a diferencia de Strategy (que cambia cómo se hace una tarea), Command convierte cualquier acción y sus argumentos en un objeto ejecutable.

package main

import "fmt"

// 2. Comando (interfaz con método de ejecución y reversión)
type Comando interface {
	Ejecutar() bool
	Deshacer()
	Nombre() string
}

// 4. Receptor: contiene la lógica de negocio real
type EditorTexto struct {
	Texto string
}

func (e *EditorTexto) Agregar(fragmento string) { e.Texto += fragmento }
func (e *EditorTexto) BorrarUltimos(n int) {
	if n > len(e.Texto) {
		n = len(e.Texto)
	}
	e.Texto = e.Texto[:len(e.Texto)-n]
}

// 3a. Comando Concreto: insertar texto
type ComandoEscribir struct {
	editorRespaldo *EditorTexto
	nuevoTexto     string
	estadoPrevio   string
}

func (c *ComandoEscribir) Ejecutar() bool {
	c.estadoPrevio = c.editorRespaldo.Texto
	c.editorRespaldo.Agregar(c.nuevoTexto)
	return true // modifica el estado -> guardar en historial
}

func (c *ComandoEscribir) Deshacer()      { c.editorRespaldo.Texto = c.estadoPrevio }
func (c *ComandoEscribir) Nombre() string { return "Escribir(" + c.nuevoTexto + ")" }

// 3b. Comando Concreto: borrar los últimos N caracteres
type ComandoBorrar struct {
	editor       *EditorTexto
	cantidad     int
	estadoPrevio string
}

func (c *ComandoBorrar) Ejecutar() bool {
	c.estadoPrevio = c.editor.Texto
	c.editor.BorrarUltimos(c.cantidad)
	return true
}

func (c *ComandoBorrar) Deshacer()      { c.editor.Texto = c.estadoPrevio }
func (c *ComandoBorrar) Nombre() string { return fmt.Sprintf("Borrar(%d)", c.cantidad) }

// 1. Emisor / Invocador: dispara comandos y administra la pila de historial
type Aplicacion struct {
	historial []Comando
}

func (a *Aplicacion) EjecutarComando(c Comando) {
	if c.Ejecutar() {
		a.historial = append(a.historial, c)
	}
	fmt.Printf("  ▶ Ejecutado %-20s →", c.Nombre())
}

func (a *Aplicacion) DeshacerUltimo() {
	if len(a.historial) == 0 {
		return
	}
	ultimo := a.historial[len(a.historial)-1]
	a.historial = a.historial[:len(a.historial)-1]
	ultimo.Deshacer()
	fmt.Printf("  ⮌ Deshecho  %-20s →", ultimo.Nombre())
}

func main() {
	// 5. Cliente: crea el receptor, los comandos y el invocador
	editor := &EditorTexto{}
	app := &Aplicacion{}

	pasos := []Comando{
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Hola "},
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Mundo"},
		&ComandoBorrar{editor: editor, cantidad: 5},
		&ComandoEscribir{editorRespaldo: editor, nuevoTexto: "Patrones en Go!"},
	}

	for _, cmd := range pasos {
		app.EjecutarComando(cmd)
		fmt.Printf(" %q\n", editor.Texto)
	}

	fmt.Println("\nRevirtiendo las últimas 2 operaciones (Ctrl+Z):")
	app.DeshacerUltimo()
	fmt.Printf(" %q\n", editor.Texto)
	app.DeshacerUltimo()
	fmt.Printf(" %q\n", editor.Texto)
}

Iterator

También llamado: Iterador

🎯 Propósito

Permite recorrer secuencialmente los elementos de una colección compleja sin exponer su representación interna subyacente (ya sea un arreglo, lista enlazada, pila, árbol o grafo).

😟 Problema

Las colecciones almacenan datos en estructuras muy diversas: listas simples, árboles binarios o grafos. Incluso sobre un mismo árbol o grafo, un día necesitas un recorrido en profundidad (DFS), al siguiente en anchura (BFS) y luego un recorrido filtrado.

Si metes todos esos algoritmos de recorrido dentro de la propia colección, contaminas su responsabilidad principal (almacenar datos eficientemente). Además, el cliente quedaría acoplado a los detalles internos de cada estructura para poder iterarla.

💡 Solución

Extrae la lógica y el estado del recorrido hacia un objeto independiente llamado iterador. Este objeto lleva la cuenta de la posición actual y de qué elementos faltan por visitar.

Como cada iterador mantiene su propio cursor de avance, múltiples iteradores pueden recorrer la misma colección en paralelo sin interferirse. Y como todos implementan la misma interfaz, el cliente puede cambiar de algoritmo de recorrido sin tocar su propio bucle.

🗺️

Analogía en el mundo real

Imagina que visitas Roma: la ciudad con todos sus monumentos es la Colección. Puedes recorrerla caminando al azar por tu cuenta, usando una app GPS turística en tu teléfono o contratando a un guía local experto en historia. Los tres actúan como iteradores distintos sobre la misma colección de atracciones, cada uno con su propio orden y criterio sin cambiar la ciudad.

  4. Colección Concreta: almacena los elementos y crea instancias del iterador concreto pasándose a sí misma como referencia.
  5. Cliente: consume tanto la colección como el iterador a través de sus interfaces, sin conocer la estructura interna de datos.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando quieras ocultar la complejidad interna de una estructura de datos, evitar duplicar lógica de recorrido por toda la aplicación, o recorrer colecciones heterogéneas bajo un contrato uniforme.
  • Paso 1: Declara la interfaz Iterador con al menos HayMas() y Siguiente().
  • Paso 2: Declara la interfaz Coleccion con métodos que fabriquen iteradores.
  • Paso 3: Implementa cada iterador concreto vinculándolo a la colección y sustituye los bucles acoplados del cliente por llamadas al iterador.

Pros

  • Cumple SRP y OCP: aísla algoritmos de recorrido complejos y permite agregar nuevas vistas sin modificar la colección.
  • Permite recorridos simultáneos e independientes sobre la misma colección y pausar/reanudar la iteración.

Contras

  • Puede ser excesivo si la aplicación solo recorre slices o listas simples de forma directa.

🔗 Relación con otros patrones

Se usa frecuentemente para recorrer árboles Composite, emplea Factory Method en las colecciones para instanciar el iterador adecuado, y puede apoyarse en Memento o Visitor durante el recorrido.

Iterator en Go

Iterador clásico con interfaz frente a iteradores nativos con iter.Seq (Go 1.23+)

package main

import (
	"fmt"
	"iter"
)

type Libro struct {
	Titulo string
	Tema   string
}

// 1. Iterador (interfaz común para recorrer elementos)
type Iterador interface {
	HayMas() bool
	Siguiente() Libro
}

// 3. Colección (interfaz que fabrica iteradores)
type ColeccionLibros interface {
	CrearIteradorPorTema(tema string) Iterador
}

// 4. Colección Concreta
type Biblioteca struct {
	libros []Libro
}

func (b *Biblioteca) Agregar(l Libro) { b.libros = append(b.libros, l) }

func (b *Biblioteca) CrearIteradorPorTema(tema string) Iterador {
	return &IteradorPorTema{biblio: b, tema: tema, posicion: 0}
}

// Método idiomático en Go 1.23+: iterador funcional compatible con for-range
func (b *Biblioteca) TodosEnOrdenInverso() iter.Seq[Libro] {
	return func(yield func(Libro) bool) {
		for i := len(b.libros) - 1; i >= 0; i-- {
			if !yield(b.libros[i]) {
				return
			}
		}
	}
}

// 2. Iterador Concreto: guarda su propio cursor de recorrido
type IteradorPorTema struct {
	biblio   *Biblioteca
	tema     string
	posicion int
}

func (it *IteradorPorTema) HayMas() bool {
	for it.posicion < len(it.biblio.libros) {
		if it.biblio.libros[it.posicion].Tema == it.tema {
			return true
		}
		it.posicion++
	}
	return false
}

func (it *IteradorPorTema) Siguiente() Libro {
	libro := it.biblio.libros[it.posicion]
	it.posicion++
	return libro
}

func main() {
	// 5. Cliente: usa la interfaz Iterador sin conocer el slice interno
	biblio := &Biblioteca{}
	biblio.Agregar(Libro{Titulo: "Diseño de Compiladores", Tema: "Sistemas"})
	biblio.Agregar(Libro{Titulo: "Patrones de Diseño GoF", Tema: "Arquitectura"})
	biblio.Agregar(Libro{Titulo: "El Lenguaje Go", Tema: "Sistemas"})
	biblio.Agregar(Libro{Titulo: "Arquitectura Limpia", Tema: "Arquitectura"})

	fmt.Println("Recorrido con Iterador clásico (Tema = Sistemas):")
	it := biblio.CrearIteradorPorTema("Sistemas")
	for it.HayMas() {
		l := it.Siguiente()
		fmt.Printf("  📖 %s [%s]\n", l.Titulo, l.Tema)
	}

	fmt.Println("\nRecorrido con iter.Seq de Go 1.23+ (orden inverso):")
	for l := range biblio.TodosEnOrdenInverso() {
		fmt.Printf("  🔄 %s [%s]\n", l.Titulo, l.Tema)
	}
}

🔍 Explicación paso a paso

  1. Biblioteca encapsula el slice privado libros y ofrece dos formas de recorrerlo sin exponerlo.
  2. IteradorPorTema implementa el patrón GoF clásico: mantiene su índice posicion y salta los libros que no coincidan con el tema buscado.
  3. TodosEnOrdenInverso() devuelve un iter.Seq[Libro] que empuja cada elemento a la función yield dentro de un for ... range nativo.
Recorrido con Iterador clásico (Tema = Sistemas):
  📖 Diseño de Compiladores [Sistemas]
  📖 El Lenguaje Go [Sistemas]

Recorrido con iter.Seq de Go 1.23+ (orden inverso):
  🔄 Arquitectura Limpia [Arquitectura]
  🔄 El Lenguaje Go [Sistemas]
  🔄 Patrones de Diseño GoF [Arquitectura]
  🔄 Diseño de Compiladores [Sistemas]

Mediator

También llamado: Mediador, Intermediary, Controller

🎯 Propósito

Reduce las dependencias caóticas (todos contra todos) entre objetos. Restringe la comunicación directa entre los componentes y los fuerza a colaborar únicamente a través de un objeto mediador central.

😟 Problema

Imagina un formulario complejo de perfil de usuario donde marcar la casilla "Tengo mascota" muestra un campo oculto, cambiar el país recarga la lista de ciudades y el botón "Guardar" valida una docena de controles distintos.

Si cada control conoce y llama directamente a los demás componentes, se forma una telaraña de dependencias cruzadas: modificar un componente rompe los otros y resulta imposible reutilizar un botón o casilla en otra ventana de la aplicación.

💡 Solución

Corta toda comunicación directa entre los componentes y haz que cada uno conozca únicamente la interfaz de un Mediador.

Cuando ocurre un evento en un componente (por ejemplo, un clic o una solicitud de recurso), este simplemente notifica al mediador. El mediador encapsula toda la coordinación y decide qué otros componentes deben reaccionar, transformando una red caótica muchos-a-muchos en una estrella limpia uno-a-muchos.

🗼

Analogía en el mundo real

Los pilotos de decenas de aviones que se aproximan a un aeropuerto no negocian entre sí por radio quién aterriza primero (lo que causaría un caos aéreo). En su lugar, todos se comunican exclusivamente con la torre de control de tráfico aéreo (el Mediador), que conoce el estado de la pista y coordina el orden de aterrizaje y despegue de forma segura.

  2. Mediador (Interfaz): declara los métodos de notificación mediante los cuales los componentes informan cualquier evento relevante.
  3. Mediador Concreto: encapsula las reglas de coordinación, mantiene referencias a los componentes administrados y redirige las acciones.
  4. Aislamiento entre colegas: los componentes concretos jamás se referencian entre sí; para cada uno, el resto del sistema es una caja negra detrás del mediador.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando un grupo de clases esté tan acoplado que sea difícil modificarlo, cuando no puedas reutilizar un componente porque arrastra dependencias hacia muchos colegas, o para evitar crear decenas de subclases solo para variar cómo colaboran.
  • Paso 1: Identifica el grupo de componentes acoplados y declara la interfaz Mediador con su protocolo de notificación.
  • Paso 2: Implementa el mediador concreto que guarde las referencias o colas de coordinación entre componentes.
  • Paso 3: Inyecta la interfaz mediadora al construir cada componente y reemplaza las llamadas directas entre colegas por notificaciones al mediador.

Pros

  • Cumple SRP: concentra la lógica de comunicación en un solo lugar fácil de auditar.
  • Cumple OCP: puedes cambiar las reglas de colaboración creando otro mediador sin tocar los componentes.
  • Reduce drásticamente el acoplamiento y facilita reutilizar componentes individuales.

Contras

  • Con el tiempo, el mediador puede acumular demasiadas responsabilidades y convertirse en un Objeto Todopoderoso (God Object).

🔗 Relación con otros patrones

A diferencia de Facade (que solo simplifica la interfaz hacia un subsistema sin que los objetos internos la conozcan), en Mediator los componentes conocen al mediador y colaboran bidireccionalmente; además, suele apoyarse en Observer para recibir eventos.

Torre de control de tráfico aéreo coordinando aterrizajes y cola de espera

package main

import "fmt"

// 2. Mediador (interfaz de comunicación centralizada)
type MediadorTorre interface {
	SolicitarPista(a Aeronave) bool
	NotificarDespegue(a Aeronave)
}

// 1. Componente (interfaz de las aeronaves que colaboran sin conocerse)
type Aeronave interface {
	Identificador() string
	Aterrizar()
	Despegar()
	PermitirAterrizaje()
}

// 3. Mediador Concreto: coordina la pista y la cola de espera
type TorreControl struct {
	pistaLibre bool
	colaEspera []Aeronave
}

func NuevaTorreControl() *TorreControl {
	return &TorreControl{pistaLibre: true}
}

func (t *TorreControl) SolicitarPista(a Aeronave) bool {
	if t.pistaLibre {
		t.pistaLibre = false
		return true
	}
	t.colaEspera = append(t.colaEspera, a)
	return false
}

func (t *TorreControl) NotificarDespegue(a Aeronave) {
	if len(t.colaEspera) > 0 {
		siguiente := t.colaEspera[0]
		t.colaEspera = t.colaEspera[1:]
		siguiente.PermitirAterrizaje()
	} else {
		t.pistaLibre = true
	}
}

// 4. Componente Concreto: solo se comunica con el mediador
type Avion struct {
	codigo string
	torre  MediadorTorre
}

func (av *Avion) Identificador() string { return av.codigo }

func (av *Avion) Aterrizar() {
	if av.torre.SolicitarPista(av) {
		fmt.Printf("  ✈️  [%s] Pista asignada → aterrizando ahora\n", av.codigo)
	} else {
		fmt.Printf("  ⏳ [%s] Pista ocupada → esperando turno en el aire\n", av.codigo)
	}
}

func (av *Avion) Despegar() {
	fmt.Printf("  🛫 [%s] Ha liberado la pista → notificando a la torre\n", av.codigo)
	av.torre.NotificarDespegue(av)
}

func (av *Avion) PermitirAterrizaje() {
	fmt.Printf("  🗼 [Torre → %s] Pista libre, autorizado para aterrizar\n", av.codigo)
	fmt.Printf("  ✈️  [%s] Aterrizando tras espera\n", av.codigo)
}

func main() {
	torre := NuevaTorreControl()
	vuelo1 := &Avion{codigo: "AV-101", torre: torre}
	vuelo2 := &Avion{codigo: "LA-205", torre: torre}
	vuelo3 := &Avion{codigo: "CM-309", torre: torre}

	vuelo1.Aterrizar()
	vuelo2.Aterrizar()
	vuelo3.Aterrizar()
	fmt.Println()
	vuelo1.Despegar()
	vuelo2.Despegar()
}

🔍 Explicación paso a paso

  1. Ningún Avion guarda referencias a otros aviones; su único campo de enlace es la interfaz MediadorTorre.
  2. Cuando vuelo2 y vuelo3 intentan aterrizar mientras la pista está ocupada por vuelo1, la TorreControl los encola en colaEspera.
  3. Al despegar un avión, este invoca NotificarDespegue y el mediador autoriza automáticamente al siguiente vuelo en espera.
  ✈️  [AV-101] Pista asignada → aterrizando ahora
  ⏳ [LA-205] Pista ocupada → esperando turno en el aire
  ⏳ [CM-309] Pista ocupada → esperando turno en el aire

  🛫 [AV-101] Ha liberado la pista → notificando a la torre
  🗼 [Torre → LA-205] Pista libre, autorizado para aterrizar
  ✈️  [LA-205] Aterrizando tras espera
  🛫 [LA-205] Ha liberado la pista → notificando a la torre
  🗼 [Torre → CM-309] Pista libre, autorizado para aterrizar
  ✈️  [CM-309] Aterrizando tras espera

Memento

También llamado: Recuerdo, Instantánea, Snapshot

🎯 Propósito

Permite capturar, externalizar y restaurar el estado interno previo de un objeto sin violar su encapsulación ni revelar los detalles privados de su implementación.

😟 Problema

Quieres implementar la función "Deshacer" o puntos de control transaccionales en un editor que maneja texto, posición del cursor, selección y estilos. Si un objeto externo intenta hacer la copia de seguridad leyendo campo por campo, chocará con los atributos privados del editor.

Si decides volver públicos todos los campos internos del editor y de la copia de seguridad para que cualquiera los lea o escriba, rompes por completo la encapsulación y acoplas el historial a cada cambio interno del editor.

💡 Solución

Delega la creación de la instantánea al propio dueño del estado: el objeto Originador. Este empaqueta una copia de sus campos privados dentro de un objeto inmutable llamado Memento.

Otro objeto llamado Cuidador (Caretaker, p. ej. el historial) almacena la pila de mementos, pero solo puede ver sus metadatos públicos (fecha, etiqueta) sin poder leer ni alterar el estado interno guardado. Cuando hay que revertir, el cuidador devuelve el memento al originador para que se restaure a sí mismo.

💾

Analogía en el mundo real

Piensa en los puntos de guardado (savegames) de un videojuego: el motor de la partida (Originador) empaqueta la vida, inventario y coordenadas exactas del jugador en una ranura de guardado sellada (Memento). El menú de partidas guardadas (Cuidador) te muestra la lista con la hora y el nombre del nivel para que elijas cuál cargar, pero el menú no modifica las estadísticas internas del archivo.

                     └───────────────────────────┘
  1. Originador: objeto cuyo estado cambia con el tiempo; sabe crear instantáneas de sus propios campos y restaurarse a partir de ellas.
  2. Memento: objeto de valor inmutable que guarda el estado capturado; oculta los datos internos a todos excepto al originador y solo expone metadatos seguros (como nombre o fecha).
  3. Cuidador (Caretaker): administra cuándo capturar y cuándo restaurar el estado manteniendo una pila de mementos, sin inspeccionar ni mutar su contenido interno.

🧭 Aplicabilidad y 🛠️ Cómo implementarlo

  • Cuándo usarlo: cuando necesites producir instantáneas para deshacer operaciones o hacer rollback ante errores transaccionales, y cuando exponer getters/setters directos del estado interno violaría la encapsulación del objeto.
  • Paso 1: Identifica la clase originadora y crea el struct Memento con campos privados que reflejen el estado del originador.
  • Paso 2: Haz que el memento sea inmutable (inicializado solo al crearse, sin setters) y expón únicamente métodos de metadatos.
  • Paso 3: Añade Guardar() y Restaurar(m) en el originador y haz que el Cuidador gestione la pila de mementos.

Pros

  • Captura copias de seguridad completas sin romper la encapsulación de los campos privados.
  • Simplifica al originador delegando la gestión del historial al cuidador.

Contras

  • Puede consumir bastante memoria RAM si se crean instantáneas de objetos grandes con demasiada frecuencia.

🔗 Relación con otros patrones

Trabaja de la mano con Command para implementar undo/redo (el comando ejecuta la acción y guarda un memento previo), con Iterator para congelar el estado de un recorrido, y tiene a Prototype como alternativa cuando el objeto es simple de clonar.

Memento en Go

Puntos de control inmutables y restauración segura del estado de un editor

package main

import "fmt"

// 1. Originador: objeto cuyo estado interno queremos salvaguardar
type Editor struct {
	texto  string
	cursor int
}

func (e *Editor) Escribir(fragmento string) {
	e.texto += fragmento
	e.cursor = len(e.texto)
}

func (e *Editor) Mostrar() string {
	return fmt.Sprintf("texto=%q (cursor=%d)", e.texto, e.cursor)
}

// Crea una instantánea inmutable de su estado actual
func (e *Editor) Guardar(etiqueta string) *Memento {
	return &Memento{
		etiqueta: etiqueta,
		texto:    e.texto,
		cursor:   e.cursor,
	}
}

// Restaura su estado interno a partir de un memento
func (e *Editor) Restaurar(m *Memento) {
	if m == nil {
		return
	}
	e.texto = m.texto
	e.cursor = m.cursor
}

// 2. Memento: almacena el estado del originador en campos privados
type Memento struct {
	etiqueta string
	texto    string
	cursor   int
}

// El cuidador solo puede consultar metadatos públicos, nunca alterar el estado
func (m *Memento) Etiqueta() string { return m.etiqueta }

// 3. Cuidador (Caretaker): administra la pila de instantáneas
type Historial struct {
	instantaneas []*Memento
}

func (h *Historial) Registrar(m *Memento) {
	fmt.Printf("  💾 Guardada instantánea [%s]\n", m.Etiqueta())
	h.instantaneas = append(h.instantaneas, m)
}

func (h *Historial) ExtraerUltima() *Memento {
	if len(h.instantaneas) == 0 {
		return nil
	}
	idx := len(h.instantaneas) - 1
	m := h.instantaneas[idx]
	h.instantaneas = h.instantaneas[:idx]
	return m
}

func main() {
	editor := &Editor{}
	historial := &Historial{}

	editor.Escribir("package main; ")
	historial.Registrar(editor.Guardar("v1: encabezado"))

	editor.Escribir("func main() { ")
	historial.Registrar(editor.Guardar("v2: firma main"))

	editor.Escribir("syntax_error??? }")
	fmt.Println("  Estado actual:", editor.Mostrar())

	fmt.Println("\nRestaurando estados previos desde el historial:")
	snap := historial.ExtraerUltima()
	editor.Restaurar(snap)
	fmt.Printf("  ⮌ Restaurado [%s] → %s\n", snap.Etiqueta(), editor.Mostrar())

	snap = historial.ExtraerUltima()
	editor.Restaurar(snap)
	fmt.Printf("  ⮌ Restaurado [%s] → %s\n", snap.Etiqueta(), editor.Mostrar())
}

🔍 Explicación paso a paso

  1. Editor (Originador) mantiene los campos no exportados texto y cursor y produce un *Memento en Guardar().
  2. Memento mantiene sus campos en minúscula (no exportados) y ofrece únicamente el método de lectura de metadatos Etiqueta().
  3. Historial (Cuidador) apila punteros *Memento y, cuando ocurre un error en el código editado, desapila las instantáneas para que editor.Restaurar(snap) recupere el estado exacto anterior.
  💾 Guardada instantánea [v1: encabezado]
  💾 Guardada instantánea [v2: firma main]
  Estado actual: texto="package main; func main() { syntax_error??? }" (cursor=45)

Restaurando estados previos desde el historial:
  ⮌ Restaurado [v2: firma main] → texto="package main; func main() { " (cursor=28)
  ⮌ Restaurado [v1: encabezado] → texto="package main; " (cursor=14)
🐹

Nota idiomática en Go

En Go la visibilidad es a nivel de paquete (identificadores con minúscula inicial). Colocar Editor y Memento en su propio paquete permite que Editor acceda a los campos privados de Memento, mientras que un Historial externo solo ve el método exportado Etiqueta().

Observer

También llamado: Observador, Publicación-Suscripción (Pub/Sub), Event-Subscriber, Listener

🎯 Propósito

Observer es un patrón de diseño de comportamiento que define un mecanismo de suscripción para notificar automáticamente a múltiples objetos (suscriptores) sobre cualquier evento o cambio de estado que ocurra en el objeto que están observando (notificador o sujeto).

😟 Problema

Imagina dos objetos: un Cliente interesado en un producto nuevo y una Tienda que lo recibirá pronto. Si el cliente consulta a la tienda cada pocos minutos (polling activo), desperdicia tiempo y recursos en viajes inútiles mientras el producto no llega.

Si, por el contrario, la tienda envía correos masivos a absolutamente todos los usuarios registrados cada vez que entra mercancía, inundará de spam a quienes no les interesa ese artículo. Surge una disyuntiva clara: o el interesado gasta recursos preguntando sin parar, o el emisor acopla y satura a receptores equivocados.

💡 Solución

El objeto cuyo estado es relevante se denomina Notificador (Subject / Publisher) y quienes desean reaccionar a sus cambios son los Suscriptores (Observers). El patrón añade al notificador una lista dinámica de suscripción con métodos públicos para registrarse (Suscribir) y darse de baja (Desuscribir).

Para no acoplar el notificador a decenas de clases concretas distintas, todos los observadores implementan una misma interfaz Suscriptor con un único método de aviso (Actualizar). Cuando ocurre un evento importante, el notificador recorre su lista e invoca esa interfaz común pasándole los datos contextuales del evento.

🌍

Analogía en el mundo real

Cuando te suscribes a una revista o periódico impreso, dejas de ir todos los días al quiosco a preguntar si ya salió la nueva edición. La editorial (notificador) mantiene un padrón de suscriptores por temática y entrega cada ejemplar directamente en tu buzón tan pronto se publica. En cualquier momento puedes cancelar tu suscripción y dejarás de recibir números sin afectar a la editorial ni a los demás lectores.

└──────────────────────────────┘  └─────────────────┘   └──────────────────┘

  1. Notificador (Publisher / Subject): mantiene la infraestructura de suscripción (mapa o lista de oyentes) y permite agregar o quitar suscriptores en tiempo de ejecución.
  2. Emisión de notificaciones: al cambiar su estado o ejecutar una acción de negocio, recorre la lista de suscriptores e invoca el método de la interfaz común.
  3. Interfaz Suscriptora (Observer): declara el contrato de notificación (p. ej., Actualizar(evento, datos)).
  4. Suscriptores Concretos: ejecutan reacciones específicas ante el evento sin que el notificador conozca sus tipos concretos.
  5. Contexto del evento: parámetros que el notificador envía en la llamada (tipo de evento, archivo afectado o referencia a sí mismo).
  6. Cliente: instancia por separado al notificador y a los suscriptores, y los conecta mediante Suscribir.

🧭 Aplicabilidad

  • Cuando el cambio de estado de un objeto requiere actualizar a otros objetos cuyo conjunto es desconocido de antemano o varía dinámicamente (p. ej., eventos de interfaz gráfica, hooks de compilación o guardado en un IDE).
  • Cuando algunos objetos de la aplicación deben observar a otros únicamente durante un tiempo limitado o bajo condiciones específicas, pudiendo darse de baja en caliente.

🛠️ Cómo implementarlo

  1. Divide la lógica en dos: el núcleo de negocio independiente será el notificador y las reacciones secundarias serán suscriptores.
  2. Declara la interfaz Suscriptor con el método Actualizar.
  3. Crea el componente gestor de suscripciones (por composición, ideal en Go) con métodos para suscribir, desuscribir y notificar.
  4. Implementa cada reacción en un struct suscriptor concreto y regístralos desde el cliente.

Ventajas

  • Principio Abierto/Cerrado (OCP): puedes añadir nuevos tipos de suscriptores sin modificar jamás el código del notificador.
  • Permite establecer y romper relaciones entre objetos dinámicamente en tiempo de ejecución.

Desventajas

  • Los suscriptores suelen ser notificados en un orden arbitrario o sin garantías de precedencia entre ellos.
  • Si no se dan de baja, las referencias retenidas en la lista pueden causar fugas de memoria (lapsed listener).

🔗 Relación con otros patrones

Chain of Responsibility, Command, Mediator y Observer conectan emisores y receptores de formas distintas: Observer permite suscripción dinámica unidireccional a múltiples oyentes, mientras que Mediator centraliza la comunicación bidireccional entre componentes para eliminar dependencias mutuas (aunque un Mediator suele implementarse internamente apoyándose en un Observer).

package main

import "fmt"

// Suscriptor (Observer): interfaz común para todos los observadores.
type Suscriptor interface {
	ID() string
	Actualizar(evento, archivo string)
}

// Notificador (Subject / Publisher): gestiona suscripciones y emite eventos.
type GestorEventos struct {
	oyentes map[string][]Suscriptor
}

func NuevoGestorEventos() *GestorEventos {
	return &GestorEventos{oyentes: make(map[string][]Suscriptor)}
}

func (g *GestorEventos) Suscribir(evento string, s Suscriptor) {
	g.oyentes[evento] = append(g.oyentes[evento], s)
}

func (g *GestorEventos) Desuscribir(evento string, id string) {
	lista := g.oyentes[evento]
	for i, s := range lista {
		if s.ID() == id {
			g.oyentes[evento] = append(lista[:i], lista[i+1:]...)
			return
		}
	}
}

func (g *GestorEventos) Notificar(evento, archivo string) {
	for _, s := range g.oyentes[evento] {
		s.Actualizar(evento, archivo)
	}
}

// Notificador concreto: Editor de código que delega la suscripción por composición.
type EditorCodigo struct {
	Eventos *GestorEventos
	archivo string
}

func NuevoEditor() *EditorCodigo {
	return &EditorCodigo{Eventos: NuevoGestorEventos()}
}

func (e *EditorCodigo) Abrir(ruta string) {
	e.archivo = ruta
	e.Eventos.Notificar("abrir", e.archivo)
}

func (e *EditorCodigo) Guardar() {
	e.Eventos.Notificar("guardar", e.archivo)
}

// Suscriptor Concreto 1: registra eventos en bitácora.
type LoggerListener struct{ nombre string }

func (l *LoggerListener) ID() string { return l.nombre }
func (l *LoggerListener) Actualizar(ev, arch string) {
	fmt.Printf("[LOG:%s] evento=%q sobre %s\n", l.nombre, ev, arch)
}

// Suscriptor Concreto 2: ejecuta análisis estático al guardar.
type LinterListener struct{ regla string }

func (l *LinterListener) ID() string { return "linter-" + l.regla }
func (l *LinterListener) Actualizar(ev, arch string) {
	fmt.Printf("[LINTER:%s] verificando sintaxis de %s tras %q\n", l.regla, arch, ev)
}

func main() {
	editor := NuevoEditor()
	logger := &LoggerListener{nombre: "auditoria"}
	linter := &LinterListener{regla: "gofmt"}

	editor.Eventos.Suscribir("abrir", logger)
	editor.Eventos.Suscribir("guardar", logger)
	editor.Eventos.Suscribir("guardar", linter)

	editor.Abrir("parser.go")
	editor.Guardar()

	fmt.Println("--- Dando de baja al linter ---")
	editor.Eventos.Desuscribir("guardar", linter.ID())
	editor.Guardar()
}

🔎 Explicación paso a paso

  1. Suscriptor define la interfaz mínima: un identificador único ID() para poder desuscribirse con seguridad y Actualizar(evento, archivo).
  2. GestorEventos encapsula un mapa map[string][]Suscriptor que permite suscribirse por tipo de evento ("abrir", "guardar").
  3. EditorCodigo compone a *GestorEventos en lugar de heredar de una clase base, manteniendo limpia su lógica de archivos.
  4. En main() suscribimos tanto el LoggerListener como el LinterListener al evento "guardar", y luego demostramos la baja en caliente con Desuscribir.

[LINTER:gofmt] verificando sintaxis de parser.go tras "guardar"

[LOG:auditoria] evento="guardar" sobre parser.go

State

También llamado: Estado, Objects for States

🎯 Propósito

State es un patrón de diseño de comportamiento que permite a un objeto alterar su comportamiento cuando su estado interno cambia. Desde afuera, parece como si el objeto hubiera cambiado su propia clase.

😟 Problema

Está estrechamente ligado al concepto de Máquina de Estados Finitos (FSM): un objeto puede encontrarse en un conjunto finito de estados (p. ej. un Documento en Borrador, Moderación o Publicado) y sus métodos se comportan distinto según el estado activo.

Cuando se implementa con enormes bloques switch o cadenas de if/else repetidas dentro de cada método del objeto, el código se vuelve frágil y difícil de mantener: añadir un nuevo estado o cambiar una regla de transición obliga a editar todos los métodos de la clase.

💡 Solución

El patrón State propone crear una clase (o struct) separada para cada estado posible del objeto y extraer allí toda la lógica dependiente de ese estado. El objeto original, denominado Contexto, conserva una referencia a un objeto estado activo y le delega todo el trabajo.

Para transicionar a otro estado, basta con sustituir el objeto de estado referenciado en el contexto por la instancia del nuevo estado. A diferencia de Strategy, en State los estados concretos sí suelen conocerse entre sí y disparan ellos mismos las transiciones en el contexto.

🌍

Analogía en el mundo real

Los botones físicos de tu smartphone reaccionan de forma completamente distinta según el estado en que se encuentre el teléfono: si está desbloqueado, pulsar un botón abre aplicaciones o sube el volumen; si está bloqueado, el mismo botón solo enciende la pantalla de PIN; y si tiene la batería agotada, muestra únicamente el ícono de carga.

  1. Contexto (Documento): almacena la referencia al objeto de estado actual, delega en él las operaciones dependientes del estado y ofrece un setter (CambiarEstado) para actualizar el estado activo.
  2. Interfaz Estado (EstadoDocumento): declara los métodos específicos del estado que tienen sentido para todos los estados concretos.
  3. Estados Concretos: cada struct implementa el comportamiento propio de un estado y recibe o guarda una referencia al contexto para consultar datos e iniciar transiciones.
  4. Transiciones de estado: tanto el contexto como los propios estados concretos pueden sustituir el objeto estado activo llamando a d.CambiarEstado(...).

🧭 Aplicabilidad

  • Cuando un objeto se comporta de manera drásticamente distinta según su estado actual, el número de estados es considerable y su lógica cambia con frecuencia.
  • Cuando una clase está contaminada con condicionales masivos (switch / if-else) que inspeccionan banderas o campos internos para decidir qué hacer en cada método (como en un analizador léxico o el ciclo de vida de una conexión TCP).

🛠️ Cómo implementarlo

  1. Identifica la clase Contexto y declara la interfaz Estado con las operaciones dependientes del estado.
  2. Por cada estado de la máquina, crea un struct concreto que implemente la interfaz.
  3. Añade en el contexto un campo del tipo de la interfaz Estado y delega allí las llamadas en vez de usar condicionales.
  4. Pasa una referencia del contexto a los métodos del estado para que cada estado pueda disparar transiciones hacia el siguiente estado.

Ventajas

  • Principio de Responsabilidad Única (SRP): aísla el código de cada estado en su propio tipo.
  • Principio Abierto/Cerrado (OCP): añade nuevos estados sin alterar el contexto ni los estados ya existentes.
  • Elimina condicionales gigantescos y simplifica el contexto.

Desventajas

  • Puede resultar excesivo (sobreingeniería) si la máquina solo tiene dos o tres estados muy simples que rara vez cambian.

🔗 Relación con otros patrones

State puede verse como una extensión de Strategy: ambos usan composición y delegación, pero en Strategy los algoritmos son independientes y no se conocen entre sí, mientras que en State los estados concretos conocen las reglas de transición y cambian activamente el estado del contexto.

package main

import "fmt"

// Estado (State): interfaz con las acciones dependientes del estado.
type EstadoDocumento interface {
	Nombre() string
	Revisar(d *Documento)
	Publicar(d *Documento, esAdmin bool)
}

// Contexto (Context): mantiene referencia al estado actual y delega en él.
type Documento struct {
	Titulo string
	estado EstadoDocumento
}

func NuevoDocumento(titulo string) *Documento {
	doc := &Documento{Titulo: titulo}
	doc.CambiarEstado(&EstadoBorrador{})
	return doc
}

func (d *Documento) CambiarEstado(nuevo EstadoDocumento) {
	d.estado = nuevo
	fmt.Printf("  -> [%s] ahora está en estado: %s\n", d.Titulo, nuevo.Nombre())
}

func (d *Documento) Revisar()                 { d.estado.Revisar(d) }
func (d *Documento) Publicar(esAdmin bool)    { d.estado.Publicar(d, esAdmin) }

// Estado Concreto 1: Borrador
type EstadoBorrador struct{}

func (e *EstadoBorrador) Nombre() string { return "Borrador" }
func (e *EstadoBorrador) Revisar(d *Documento) {
	fmt.Println("[Borrador] Enviando documento a moderación...")
	d.CambiarEstado(&EstadoModeracion{})
}
func (e *EstadoBorrador) Publicar(d *Documento, esAdmin bool) {
	fmt.Println("[Borrador] No se puede publicar directamente sin revisión.")
}

// Estado Concreto 2: Moderación
type EstadoModeracion struct{}

func (e *EstadoModeracion) Nombre() string { return "Moderación" }
func (e *EstadoModeracion) Revisar(d *Documento) {
	fmt.Println("[Moderación] El documento ya está en revisión.")
}
func (e *EstadoModeracion) Publicar(d *Documento, esAdmin bool) {
	if !esAdmin {
		fmt.Println("[Moderación] Permiso denegado: solo un admin puede aprobar. Vuelve a borrador.")
		d.CambiarEstado(&EstadoBorrador{})
		return
	}
	fmt.Println("[Moderación] Aprobado por administrador.")
	d.CambiarEstado(&EstadoPublicado{})
}

// Estado Concreto 3: Publicado
type EstadoPublicado struct{}

func (e *EstadoPublicado) Nombre() string { return "Publicado" }
func (e *EstadoPublicado) Revisar(d *Documento) {
	fmt.Println("[Publicado] Ya está publicado; no requiere revisión.")
}
func (e *EstadoPublicado) Publicar(d *Documento, esAdmin bool) {
	fmt.Println("[Publicado] Operación ignorada: el documento ya es público.")
}

func main() {
	doc := NuevoDocumento("Especificación Gramática LL(1)")
	doc.Publicar(false)
	doc.Revisar()
	doc.Publicar(false) // Falla y regresa a Borrador
	doc.Revisar()
	doc.Publicar(true)  // Admin aprueba -> Publicado
	doc.Revisar()
}

  1. EstadoDocumento define las operaciones del ciclo de vida (Revisar y Publicar) recibiendo el puntero *Documento como contexto.
  2. Documento no tiene ni un solo if ni switch: delega en d.estado.Revisar(d) y d.estado.Publicar(d, esAdmin).
  3. Cada estado concreto (EstadoBorrador, EstadoModeracion, EstadoPublicado) decide qué acción ejecutar y a qué estado transicionar invocando d.CambiarEstado(...).

Strategy

También llamado: Estrategia, Policy

🎯 Propósito

Strategy es un patrón de diseño de comportamiento que te permite definir una familia de algoritmos, encapsular cada uno de ellos en una clase (o struct) separada y hacer que sus objetos sean completamente intercambiables en tiempo de ejecución.

😟 Problema

Imagina que desarrollas una aplicación de navegación con mapas. Empiezas calculando rutas solo para automóviles por carretera, pero pronto los usuarios piden rutas a pie, luego en transporte público, después en bicicleta y finalmente rutas turísticas.

Cada vez que agregas un algoritmo de enrutamiento dentro de la clase principal Navegador, su tamaño se duplica. Cualquier ajuste en el cálculo de bicicletas arriesga romper el código de automóviles y genera constantes conflictos de integración (merge conflicts) en el equipo.

💡 Solución

Extrae cada variante del algoritmo a su propia clase llamada Estrategia, todas implementando una interfaz común (p. ej., EstrategiaRuta con el método CalcularRuta(origen, destino)).

La clase original Navegador actúa como Contexto: guarda una referencia a una estrategia y delega en ella el cálculo sin saber cómo funciona por dentro. El cliente puede inyectar o cambiar en caliente la estrategia activa según la preferencia del usuario.

🌍

Analogía en el mundo real

Necesitas ir desde la universidad hasta el aeropuerto. Puedes elegir entre varias estrategias de transporte: tomar el metro/autobús, pedir un taxi o ir en bicicleta. El objetivo es idéntico (trasladarte del punto A al punto B), pero eliges e intercambias el algoritmo según tu presupuesto, equipaje o prisa del momento.

  1. Contexto (Navegador): mantiene una referencia a una de las estrategias concretas y se comunica con ella únicamente a través de la interfaz común.
  2. Interfaz Estrategia (EstrategiaRuta): declara el método común que el contexto usa para ejecutar cualquier variante del algoritmo.
  3. Estrategias Concretas: implementan las distintas variaciones del algoritmo (enrutamiento en auto, transporte público, bicicleta; o p. ej. distintos pases de optimización en un compilador).
  4. Ejecución delegada: el contexto invoca el método de la estrategia sin conocer cómo se calcula internamente.
  5. Cliente: elige la estrategia concreta adecuada, la pasa al contexto y puede sustituirla en cualquier momento con un modificador (CambiarEstrategia).

🧭 Aplicabilidad

  • Cuando necesitas usar distintas variantes de un algoritmo dentro de un objeto y poder intercambiarlas durante el tiempo de ejecución.
  • Cuando tienes muchas clases similares que solo difieren en cómo ejecutan cierto comportamiento, o un condicional enorme que selecciona entre variantes del mismo algoritmo.
  • Para aislar la lógica de negocio principal de los detalles complejos y estructuras de datos internas de los algoritmos (p. ej. algoritmos de grafos, compresión o asignación de registros).

🛠️ Cómo implementarlo

  1. Identifica en el contexto el algoritmo que cambia con frecuencia o está atrapado en un gran switch.
  2. Declara la interfaz Estrategia común a todas las variantes.
  3. Extrae cada algoritmo en un struct independiente que implemente dicha interfaz.
  4. Añade en el contexto un campo para la interfaz y un método setter para cambiarla en tiempo de ejecución.

Ventajas

  • Permite intercambiar algoritmos dentro de un objeto en caliente (en tiempo de ejecución).
  • Aísla los detalles internos del algoritmo del código que lo consume.
  • Sustituye la herencia por composición y cumple el Principio Abierto/Cerrado (OCP).

Desventajas

  • Los clientes deben conocer las diferencias entre estrategias para poder elegir la adecuada.
  • Si solo existen un par de algoritmos que casi nunca cambian, crear tipos e interfaces extra puede ser innecesario.

🔗 Relación con otros patrones

Decorator cambia la piel de un objeto envolviéndolo en capas, mientras que Strategy cambia sus entrañas sustituyendo el algoritmo interno. Frente a Template Method (que varía pasos mediante herencia/esqueleto fijo), Strategy reemplaza el algoritmo entero por composición en tiempo de ejecución.

package main

import (
	"fmt"
	"strings"
)

// Estrategia (Strategy): interfaz común para toda la familia de algoritmos.
type EstrategiaRuta interface {
	Nombre() string
	CalcularRuta(origen, destino string) ([]string, int)
}

// Estrategia Concreta 1: Automóvil (prioriza autopistas y velocidad).
type RutaAutomovil struct{}

func (r RutaAutomovil) Nombre() string { return "Automóvil" }
func (r RutaAutomovil) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Autopista Central", "Peaje Norte", destino}, 25
}

// Estrategia Concreta 2: Transporte Público (combina metro y bus).
type RutaTransportePublico struct{}

func (r RutaTransportePublico) Nombre() string { return "Transporte Público" }
func (r RutaTransportePublico) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Estación Metro A", "Transbordo Línea B", destino}, 40
}

// Estrategia Concreta 3: Bicicleta (prioriza ciclovías y parques).
type RutaBicicleta struct{}

func (r RutaBicicleta) Nombre() string { return "Bicicleta" }
func (r RutaBicicleta) CalcularRuta(origen, destino string) ([]string, int) {
	return []string{origen, "Ciclovía del Río", "Parque Lineal", destino}, 55
}

// Contexto (Context): delega el cálculo en la estrategia activa sin usar switch.
type Navegador struct {
	estrategia EstrategiaRuta
}

func NuevoNavegador(e EstrategiaRuta) *Navegador {
	return &Navegador{estrategia: e}
}

func (n *Navegador) CambiarEstrategia(e EstrategiaRuta) {
	n.estrategia = e
}

func (n *Navegador) MostrarRuta(origen, destino string) {
	tramos, minutos := n.estrategia.CalcularRuta(origen, destino)
	fmt.Printf("[%s] (%d min): %s\n",
		n.estrategia.Nombre(), minutos, strings.Join(tramos, " -> "))
}

func main() {
	nav := NuevoNavegador(RutaAutomovil{})
	nav.MostrarRuta("Campus", "Aeropuerto")

	nav.CambiarEstrategia(RutaTransportePublico{})
	nav.MostrarRuta("Campus", "Aeropuerto")

	nav.CambiarEstrategia(RutaBicicleta{})
	nav.MostrarRuta("Campus", "Aeropuerto")
}

🔎 Explicación paso a paso

  1. EstrategiaRuta define el contrato común para calcular el recorrido entre dos puntos devolviendo los tramos y el tiempo estimado.
  2. RutaAutomovil, RutaTransportePublico y RutaBicicleta implementan de forma autónoma cada algoritmo sin tocar a las demás.
  3. Navegador (Contexto) recibe cualquier EstrategiaRuta y permite intercambiarla en caliente con CambiarEstrategia.

Salida real

[Transporte Público] (40 min): Campus -> Estación Metro A -> Transbordo Línea B -> Aeropuerto
[Bicicleta] (55 min): Campus -> Ciclovía del Río -> Parque Lineal -> Aeropuerto

Template Method

También llamado: Método plantilla

🎯 Propósito

Template Method es un patrón de diseño de comportamiento que define el esqueleto invariante de un algoritmo en una operación plantilla, delegando o permitiendo redefinir ciertos pasos específicos en implementaciones concretas sin alterar la estructura ni el orden general del algoritmo.

😟 Problema

Imagina una aplicación de minería de datos que procesa documentos corporativos en formatos CSV, DOC y PDF. Aunque la lectura y extracción de bytes cambia según el formato, la secuencia global (Abrir → Extraer → Parsear → Analizar → Cerrar) y el análisis estadístico final son idénticos en los tres casos.

Si cada formato duplica todo el flujo por separado, cualquier cambio en el orden de etapas o en el análisis común obliga a editar todas las clases, rompiendo el principio DRY.

💡 Solución (y cómo se adapta a Go)

Se descompone el algoritmo en pasos bien definidos: pasos obligatorios (variables según el formato), pasos comunes fijos y ganchos (hooks) opcionales con comportamiento por defecto vacío antes o después de etapas críticas.

¿Cómo se resuelve en Go si no hay herencia ni clases abstractas? En Go se define una interfaz de pasos (PasosMineria) junto con una función o struct ejecutor (MineroDatos.Ejecutar) que codifica el esqueleto fijo e invoca la interfaz en orden. Los pasos opcionales o hooks por defecto se reutilizan embebiendo un struct base (BaseMineria) por composición.

🌍

Analogía en el mundo real

En la construcción residencial en serie, un plano arquitectónico maestro fija la secuencia obligatoria de etapas: colocar cimientos, levantar estructura, instalar plomería/electricidad y pintar acabados. No puedes instalar el techo antes que los cimientos (el esqueleto es fijo), pero cada propietario puede personalizar pasos específicos como el tipo de piso o el diseño de las ventanas.

  1. Método Plantilla (MineroDatos.Ejecutar): define el esqueleto invariante del algoritmo invocando los pasos en un orden estricto y ejecutando directamente los pasos comunes fijos.
  2. Interfaz de Pasos (PasosMineria): sustituye a los métodos abstractos de POO clásica; declara las operaciones primitivas que cada variante debe suministrar.
  3. Struct Base opcional (BaseMineria): proporciona implementaciones por defecto para pasos comunes y ganchos (hooks) mediante struct embedding.
  4. Implementaciones Concretas (MineroCSV, MineroPDF): implementan los pasos de su formato y, si lo necesitan, redefinen los hooks sin poder alterar el método plantilla.

🧭 Aplicabilidad

  • Cuando quieres que los clientes personalicen únicamente ciertos pasos de un algoritmo (p. ej., fases específicas del pipeline de un compilador o exportador) sin permitirles modificar la estructura ni el orden general.
  • Cuando tienes varios tipos con algoritmos casi idénticos que solo varían en pasos puntuales y deseas eliminar la duplicación de código.

🛠️ Cómo implementarlo en Go

  1. Divide el algoritmo en pasos e identifica cuáles son fijos, cuáles son obligatorios por variante y cuáles son ganchos (hooks) opcionales.
  2. Declara la interfaz de pasos (PasosMineria) con los pasos variables y hooks.
  3. Crea un struct Base con métodos por defecto para los hooks (para embeberlo en los structs concretos).
  4. Escribe el método plantilla Ejecutar(p PasosMineria, ...) que orquesta la secuencia completa.

Ventajas

  • Permite redefinir solo ciertas partes de un algoritmo grande sin verse afectado por cambios en el resto del flujo.
  • Concentra el código compartido y el orden de ejecución en un único lugar (evita duplicación).

Desventajas

  • Algunos clientes pueden verse limitados por la rigidez del esqueleto predefinido.
  • Cuantos más pasos y hooks tenga la plantilla, más difícil resulta mantenerla y comprenderla.

🔗 Relación con otros patrones

Factory Method es una especialización de Template Method aplicada a la creación de objetos. En Go, como no existe herencia de clases, Template Method converge estructuralmente con Strategy (usa interfaces y composición), con la diferencia de que aquí el esqueleto multi-paso es el protagonista.

Template Method en Go

package main

import (
	"fmt"
	"strings"
)

// PasosMineria define los pasos primitivos y ganchos (hooks) del algoritmo.
// En Go no hay herencia ni métodos abstractos: modelamos los pasos variables con una interfaz.
type PasosMineria interface {
	Abrir(ruta string) string
	ExtraerDatos(contenido string) []string
	Parsear(crudos []string) map[string]int
	Cerrar(ruta string)
	AntesDeAnalizar() // Gancho (hook) opcional
}

// BaseMineria aporta implementaciones por defecto para pasos opcionales y hooks
// mediante composición (struct embedding).
type BaseMineria struct{}

func (BaseMineria) AntesDeAnalizar() {}
func (BaseMineria) Cerrar(ruta string) {
	fmt.Printf("  [Base] Cerrando descriptor de %s\n", ruta)
}

// MineroDatos contiene el "Método Plantilla" (Ejecutar) que fija el esqueleto del algoritmo.
type MineroDatos struct{}

func (m MineroDatos) Ejecutar(p PasosMineria, ruta string) {
	fmt.Printf("=== Procesando %s ===\n", ruta)
	raw := p.Abrir(ruta)
	crudos := p.ExtraerDatos(raw)
	datos := p.Parsear(crudos)
	p.AntesDeAnalizar() // Hook
	m.analizarYReportar(datos)
	p.Cerrar(ruta)
}

// Paso común fijo en el esqueleto (no sobrescribible).
func (MineroDatos) analizarYReportar(datos map[string]int) {
	fmt.Printf("  [Análisis común] Total claves=%d -> %v\n", len(datos), datos)
}

// Implementación Concreta 1: CSV (embebe BaseMineria y usa el hook por defecto).
type MineroCSV struct{ BaseMineria }

func (MineroCSV) Abrir(ruta string) string {
	fmt.Println("  [CSV] Leyendo texto separado por comas")
	return " compilador,3 ; lexer,2 ; parser,5 "
}
func (MineroCSV) ExtraerDatos(c string) []string { return strings.Split(c, ";") }
func (MineroCSV) Parsear(crudos []string) map[string]int {
	res := make(map[string]int)
	for _, fila := range crudos {
		partes := strings.Split(strings.TrimSpace(fila), ",")
		res[partes[0]] = len(partes[0])
	}
	return res
}

// Implementación Concreta 2: PDF (sobrescribe el hook AntesDeAnalizar).
type MineroPDF struct{ BaseMineria }

func (MineroPDF) Abrir(ruta string) string {
	fmt.Println("  [PDF] Descomprimiendo flujos de objetos PDF")
	return "AST|SSA|IR"
}
func (MineroPDF) ExtraerDatos(c string) []string { return strings.Split(c, "|") }
func (MineroPDF) Parsear(crudos []string) map[string]int {
	res := make(map[string]int)
	for i, tok := range crudos {
		res[tok] = (i + 1) * 10
	}
	return res
}
func (MineroPDF) AntesDeAnalizar() {
	fmt.Println("  [Hook PDF] Limpiando metadatos OCR antes del análisis")
}

func main() {
	plantilla := MineroDatos{}
	plantilla.Ejecutar(MineroCSV{}, "metricas.csv")
	plantilla.Ejecutar(MineroPDF{}, "articulo.pdf")
}

🔎 Explicación paso a paso

  1. PasosMineria declara los pasos personalizables del algoritmo y el gancho AntesDeAnalizar().
  2. BaseMineria ofrece un cuerpo vacío para el hook y un cierre estándar. MineroCSV y MineroPDF lo embeben para no repetir código.
  3. MineroDatos.Ejecutar es el Método Plantilla: fija el orden de los 6 pasos e invoca el paso privado invariante analizarYReportar.
  4. MineroPDF redefine AntesDeAnalizar() para limpiar metadatos OCR, mientras MineroCSV conserva el gancho silencioso por defecto.

Visitor

También llamado: Visitante

🎯 Propósito

Visitor es un patrón de diseño de comportamiento que te permite separar los algoritmos de la estructura de objetos sobre la que operan, pudiendo añadir nuevas operaciones a una jerarquía de tipos (como un Árbol Sintáctico Abstracto — AST) sin modificar sus estructuras.

😟 Problema

En un compilador tienes una jerarquía de nodos del AST (Numero, Suma, Multiplicacion, etc.). Primero necesitas evaluar las expresiones; luego te piden imprimir el árbol en formato infijo; después verificar tipos, exportar a XML/JSON y generar código intermedio.

Si añades un método nuevo en cada struct de nodo por cada nueva fase del compilador, mezclas responsabilidades dispares dentro de los nodos de datos y tienes que modificar y recompilar toda la jerarquía del AST cada vez que agregas una operación.

💡 Solución (Double Dispatch)

Coloca cada nueva operación en una clase separada llamada Visitante (p. ej., Evaluador, ImpresorAST) que declara un método específico por cada tipo concreto de nodo (VisitarNumero, VisitarSuma, ...).

Para evitar cadenas de switch de tipos desde afuera, cada nodo implementa un único método trivial Aceptar(v Visitante) que invoca de vuelta el método exacto del visitante pasándose a sí mismo (v.VisitarSuma(s)). Esta técnica se conoce como Double Dispatch (doble despacho).

🌍

Analogía en el mundo real

Un experimentado agente de seguros (Visitante) recorre todos los edificios de un barrio (estructura de objetos). Los edificios no cambian, pero el agente ejecuta una acción especializada según el tipo concreto de inmueble que visita: si visita una vivienda residencial ofrece seguro médico, si visita un banco ofrece seguro contra robos, y si visita una cafetería ofrece póliza contra incendios e inundaciones.

🧠 Comportamiento 2 / 3 · Estructura

Visitor — Estructura y análisis

┌──────────────────────────────────┐       ┌───────────────────────────────┐
│  <<interface>>                   │       │  <<interface>>                │
│  (1) VisitanteExpr               │◀──────│  (3) Expr (Elemento AST)      │
├──────────────────────────────────┤acepta ├───────────────────────────────┤
│ + VisitarNumero(n *Numero)       │       │ + Aceptar(v VisitanteExpr)    │
│ + VisitarSuma(s *Suma)           │       └───────────────△───────────────┘
│ + VisitarMultiplicacion(m *Mult) │                       │
└─────────────────△────────────────┘           ┌───────────┼───────────┐
                  │                            │           │           │
        ┌─────────┴─────────┐            ┌─────┴────┐ ┌────┴────┐ ┌────┴─────────┐
        │                   │            │(4) Numero│ │(4) Suma │ │(4) Multiplic.│
┌───────┴────────┐ ┌────────┴────────┐   ├──────────┤ ├─────────┤ ├──────────────┤
│(2) Evaluador   │ │(2) ImpresorAST  │   │v.Visitar │ │v.Visitar│ │v.Visitar     │
│ - Resultado    │ │ - Salida        │   │ Numero() │ │ Suma()  │ │ Mult()       │
└────────────────┘ └─────────────────┘   └──────────┘ └─────────┘ └──────────────┘
  1. Interfaz Visitante (VisitanteExpr): declara un método de visita para cada tipo de elemento concreto de la estructura (VisitarNumero, VisitarSuma, etc.).
  2. Visitantes Concretos (Evaluador, ImpresorAST): implementan un algoritmo completo sobre la jerarquía y pueden acumular estado intermedio (p. ej. Resultado o Salida) mientras recorren el árbol.
  3. Interfaz Elemento (Expr): declara el método Aceptar(v VisitanteExpr).
  4. Elementos Concretos (Nodos del AST): implementan Aceptar redirigiendo la llamada al método del visitante que corresponde a su tipo exacto (Double Dispatch).
  5. Cliente: construye el árbol (p. ej. un Composite AST) y le pasa distintos visitantes según la fase que desee ejecutar.

🧭 Aplicabilidad

  • Cuando necesitas ejecutar diversas operaciones independientes sobre todos los elementos de una estructura compleja (como un árbol sintáctico AST o un grafo Composite) sin contaminar las clases de los nodos.
  • Cuando la jerarquía de elementos (tipos de nodos) es estable, pero frecuentemente necesitas agregar nuevos algoritmos o pases de análisis sobre ella.

🛠️ Cómo implementarlo

  1. Declara la interfaz Visitante con un método VisitarX por cada tipo concreto de nodo.
  2. Declara la interfaz Elemento con el método Aceptar(v Visitante).
  3. Implementa Aceptar en cada nodo concreto llamando a v.VisitarX(n).
  4. Por cada nueva operación (evaluar, imprimir, chequear tipos), crea un struct visitante concreto e pásalo a la raíz del árbol.

Ventajas

  • Principio Abierto/Cerrado (OCP): añade nuevas operaciones sobre el AST sin tocar los nodos existentes.
  • Principio de Responsabilidad Única (SRP): agrupa en un mismo visitante todas las variantes de un algoritmo.
  • El visitante puede acumular estado útil a medida que recorre el árbol.

Desventajas

  • Si añades o eliminas un tipo de nodo en la jerarquía, debes actualizar la interfaz Visitante y todos los visitantes concretos.
  • Los visitantes solo pueden acceder a los campos y métodos exportados de los elementos.

🔗 Relación con otros patrones

Visitor es el compañero ideal de Composite (como un árbol AST) e Iterator para recorrer estructuras jerárquicas ejecutando operaciones tipadas, y puede verse como una versión más potente de Command capaz de operar sobre múltiples tipos de receptores.

Visitor en Go (AST de Expresiones)

package main

import "fmt"

// Visitante (Visitor): declara un método de visita por cada tipo concreto de nodo del AST.
type VisitanteExpr interface {
	VisitarNumero(n *Numero)
	VisitarSuma(s *Suma)
	VisitarMultiplicacion(m *Multiplicacion)
}

// Elemento (Element): nodo del AST que acepta un visitante (Double Dispatch).
type Expr interface {
	Aceptar(v VisitanteExpr)
}

// Elementos Concretos: nodos del árbol sintáctico abstracto (AST).
type Numero struct{ Valor int }

func (n *Numero) Aceptar(v VisitanteExpr) { v.VisitarNumero(n) }

type Suma struct{ Izq, Der Expr }

func (s *Suma) Aceptar(v VisitanteExpr) { v.VisitarSuma(s) }

type Multiplicacion struct{ Izq, Der Expr }

func (m *Multiplicacion) Aceptar(v VisitanteExpr) { v.VisitarMultiplicacion(m) }

// Visitante Concreto 1: Evaluador de expresiones (acumula el resultado en una pila/campo).
type Evaluador struct{ Resultado int }

func (e *Evaluador) VisitarNumero(n *Numero) { e.Resultado = n.Valor }
func (e *Evaluador) VisitarSuma(s *Suma) {
	s.Izq.Aceptar(e)
	izq := e.Resultado
	s.Der.Aceptar(e)
	e.Resultado = izq + e.Resultado
}
func (e *Evaluador) VisitarMultiplicacion(m *Multiplicacion) {
	m.Izq.Aceptar(e)
	izq := e.Resultado
	m.Der.Aceptar(e)
	e.Resultado = izq * e.Resultado
}

// Visitante Concreto 2: Impresor de árboles en notación infija parentizada.
type ImpresorAST struct{ Salida string }

func (i *ImpresorAST) VisitarNumero(n *Numero) {
	i.Salida = fmt.Sprintf("%d", n.Valor)
}
func (i *ImpresorAST) VisitarSuma(s *Suma) {
	s.Izq.Aceptar(i)
	izq := i.Salida
	s.Der.Aceptar(i)
	i.Salida = fmt.Sprintf("(%s + %s)", izq, i.Salida)
}
func (i *ImpresorAST) VisitarMultiplicacion(m *Multiplicacion) {
	m.Izq.Aceptar(i)
	izq := i.Salida
	m.Der.Aceptar(i)
	i.Salida = fmt.Sprintf("(%s * %s)", izq, i.Salida)
}

func main() {
	// Árbol AST para la expresión: (3 + 5) * 2
	ast := &Multiplicacion{
		Izq: &Suma{Izq: &Numero{3}, Der: &Numero{5}},
		Der: &Numero{2},
	}

	imp := &ImpresorAST{}
	ast.Aceptar(imp)
	fmt.Println("Expresión AST :", imp.Salida)

	eval := &Evaluador{}
	ast.Aceptar(eval)
	fmt.Println("Resultado eval:", eval.Resultado)
}

🔎 Explicación paso a paso

  1. Los nodos del AST (Numero, Suma, Multiplicacion) implementan Expr con una sola línea: redirigir Aceptar(v) al método tipado de VisitanteExpr.
  2. ImpresorAST recorre recursivamente los hijos izquierdo y derecho y construye la representación infija parentizada ((3 + 5) * 2).
  3. Evaluador recorre el mismo árbol sin tocar los structs de los nodos y calcula el valor numérico 16.
